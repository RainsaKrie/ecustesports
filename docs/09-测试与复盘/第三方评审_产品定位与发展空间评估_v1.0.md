# 第三方评审：赛事运营平台的产品定位与发展空间

- 评审对象：《无畏契约》校园赛事 AI 排程协同助手（`ecustesports.top`）
- 评审立场：**外部评审顾问视角**，不参与建设、不预设结论
- 依据：仓库代码（193 个源文件 / 约 3 万行）、线上公开数据快照（2026-10-12）、项目文档
- 日期：2026-10-12

> 本报告的判断全部标注依据。「实测」= 我实际读到的数据或代码；「推断」= 由事实推出的看法，可信度较低。

---

## 一、结论先行

**这个平台不是「待打磨的小工具」，而是一个定位没有被收敛的完整系统。**

它的工程量已经越过「小工具」的门槛——31 个页面（玩家侧 16 / 管理端 14 / 裁判端 1）、
36 个接口、一套能处理四阶段赛制收敛的排程引擎，
并且**正在真实运行**（36 支队 / 205 名选手 / 20 场赛程，其中 10 场已完成）。
说它「像小工具」，问题不在规模，在于**它没有把最锋利的那一件事说出来**。

三句话概括我的判断：

1. **它真正的差异化是「为随时要改的赛程而设计」**，而这一点被埋在功能列表里，没有被当成主线；
2. **它的 AI 部分目前不构成价值** —— 识别准确率未达自己定的门槛，这一点必须正面处理，而不是回避；
3. **它没有商业化空间，但作为求职作品的发展空间很大** —— 前提是换一套讲法。

---

## 二、事实基线

以下是我实际核到的数字，后续判断都基于它们。

| 维度 | 事实 | 来源 |
|---|---|---|
| 代码规模 | 193 个 TS/TSX 文件，约 30,306 行 | 实测（遍历统计） |
| 页面 | 31 个路由（玩家侧 16 / 管理端 14 / 裁判端 1） | 实测（路由清单） |
| 接口 | 36 个 API 路由 | 实测 |
| 真实用户量 | 36 支队、205 名选手，全部「已冻结」 | 实测（线上公开接口） |
| 真实赛程 | 20 场：资格赛 4 场（已完）+ 入围赛 16 场（已完成 6 场） | 实测 |
| 赛制复杂度 | 四阶段：资格赛 8 队 → 入围赛 32 席 → 小组赛 16 → 淘汰赛 8 | 实测（线上赛程结构） |
| AI 状态 | 识图报分已实现；3 场真实截图对照，比分与地图 8/10 一致 | 实测（影子对照） |
| 项目目标 | 章程原文：「掌握游戏＋AI 产品能力……**不以商业化为完成前提**」 | 项目章程 |

**一个值得先说的事实**：这不是原型。它有真实数据、真实比赛、真实故障（记录在案的一次并发超限导致裁判不足），
并且**在比赛进行中被使用**。这一点决定了它的价值评估方式和「玩具项目」完全不同。

**另一个容易被忽略的优点**：报名收集了姓名与学号，而**公开接口只返回游戏 ID，不返回学号**
（实测核对）。这在同类项目里不常见——多数人会图省事把整个报名表原样返回。属于设计上的克制。

## 三、逐维度评估

### 3.1 产品定位

**现状**：一个覆盖「报名 → 队伍管理 → 赛制配置 → 抽签 → 赛程生成 → 改期协同 → 裁判报分 → 结果公示」
全链路的运营中台，同时面向三类用户（赛事负责人、裁判、选手）。

**问题**：**一个系统，三类用户，三套完全不同的使用频率。**

| 用户 | 使用频率 | 场景深度 |
|---|---|---|
| 赛事负责人 | 每天（比赛月内） | 深，是主用户 |
| 裁判 | 每场（约几分钟） | 浅，且**从未被真实裁判使用过** |
| 选手 | 报名时一次 + 偶尔看赛程 | 极浅，可被一张图替代 |

**推断**：真实的产品只有一个用户——负责人本人。裁判端和玩家门户是「为了让流程闭环而建」，
不是「因为有需求而建」。这不一定是错的（闭环本身有价值），但它解释了为什么感觉「没有核心锚点」：
**主用户只有一个，而系统的重心被摊在三条线上**。

### 3.2 用户价值

按用户拆开看，价值密度差得很远：

- **负责人**：价值真实且可量化——把分散在问卷星、腾讯文档、群聊里的信息收进一处，
  并且**在改期时自动检查全局资源**（并发数、裁判容量）。这是它最有说服力的部分。
- **裁判**：理论价值是「报分更快」，但**没有任何真实裁判用过**，所以这条价值目前是假设，不是事实。
- **选手**：能看到赛程、能报名。但这些用一张长图也能解决，**不构成独立价值**。

**判断**：价值集中在一个人身上。这既是它的真实（不是一个想象出来的需求），
也是它的天花板（无法靠用户增长验证产品）。

### 3.3 核心竞争力

我用「别人做不到 / 别人做不好 / 别人不屑做」三档来分：

| 能力 | 档位 | 依据 |
|---|---|---|
| 四阶段赛制收敛引擎（资格赛 → 32 席 → 16 → 8） | **别人做不好** | 商业化平台只支持标准赛制；含轮空配比、预留席位、段位分档对阵等现实约束 |
| **改期时的全局资源检查** | **别人不屑做** | 商业平台假设「赛程定下就不改」；校园赛事的现实是**随时改** |
| 端到端闭环 | 别人做不到（对个人而言） | 报名到公示一条链，无外部依赖 |
| AI 识图报分 | 尚不成立 | 准确率未达门槛，见 3.5 |

**最关键的一条是第二行**。我读代码后确认：这个平台的改期逻辑不是「改个时间」，
而是「改完之后检查是否导致并发超限 / 裁判不足 / 赛程冲突」，并且在冲突时给出解释。
**商业排程工具不做这件事，因为它们的假设是赛程稳定。而校园赛事恰恰相反。**

**这是它唯一的、真实的差异化锚点，目前被埋在功能列表里。**

### 3.4 功能完整度

**宽，但不深。** 每个模块都可用，但没有一个深到「别人做不了」。

具体表现：玩家侧 16 个页面（含新闻、BP 工具、市场、对阵图等）；管理端 14 个页面。
**这些页面里有多少是真实需求、多少是「顺手做的」，从代码上无法分辨**——
但这本身就是问题：**功能面在膨胀，而没有一个功能被明确标记为「这是重点」。**

**推断**：功能面膨胀的成因是「没有取舍标准」。当没有被明确否掉的功能，
每一个看起来合理的需求都会变成一个新页面。

### 3.5 市场差异化

对标对象：Toornament、Challonge、Start.gg（国际），以及各类电竞小程序（国内）。

| 维度 | 它们的做法 | 这个平台 |
|---|---|---|
| 赛制 | 标准单败/双败/GSL | 支持 + 现实约束（轮空、预留席位、段位分档） |
| 改期 | 假设赛程稳定 | **把改期当成一等公民** |
| 门槛 | 需要赛制知识 | 面向「没有专门赛事运营人员」的组织者 |
| 成本 | 免费档功能受限 | 完全免费、数据自持 |

**差异化的真实位置**：不是「更全」，而是**「为不稳定赛程设计」**。
Toornament 这类工具假设「赛程是权威的」，而校园赛事的现实是**赛程必须让位于队伍时间**。

### 3.6 AI 部分的诚实评估

**必须单独说，因为这是最容易被误读的部分。**

我做了 3 场真实截图的对照（AI 读图 vs 负责人手工报分，基准是独立的）：

| 指标 | 结果 |
|---|---|
| 比分 | 3/3 一致 |
| 地图 | 2/3 一致 |
| 分组（谁和谁一队） | 6/6 一致 |
| 合计字段 | 8/10 |

**看似不错，但不能这么读。** 三个必须说清的限制：

1. **样本只有 3 场，且是最清晰完整的正面样本**——证明不了错误率；
2. **门槛里有一半没测到**：系列赛比分、不同截图类型的失败率、响应成本、人工修改率；
3. **协议经过一次大改（v4 → v5）后，真实截图上的成绩没有变化**（8/10 → 8/10）：
   修好了一场，又错了另一场。**说明「换问法」没有解决模型对胜负方向的判断不稳。**

**结论**：**AI 目前是「已实现的功能」，不是「已被验证的价值」。**
按项目自己定的门槛（胜方 ≥98%、零 AI 致错），它现在**不达标**。

## 四、主要短板（按严重度排序）

1. **定位过宽，没有主线**。三类用户、28 个页面，但没有一句话能说清「它最擅长什么」。
   最锋利的能力（改期协同）被摊平在功能列表里。

2. **AI 价值未证实，且叙事风险高**。面试或对外介绍时，「AI 能识图报分」这句话后面
   必然跟着「准吗」。目前答案是「还在验证」——**这会削弱而不是增强说服力**。

3. **裁判端从未被真实使用**。整个裁判流程（认领比赛 → 传图 → 确认）跑通过测试，
   但**没有一名真实裁判用过**。这条价值目前是假设。

4. **单点依赖**。系统只有一个人能维护、能配置。一旦他不在，赛事无法用系统运行。

5. **没有「不做清单」**。功能面持续膨胀，缺少明确被否掉的需求记录。

---

## 五、潜在机会

1. **把「改期协同」提为主线**。这是唯一别人不做、且被真实事故驱动过的能力
   （记录在案：临时调整后 3 场同时进行、裁判不足）。它值得成为产品的名字和第一句话。

2. **把「验证 AI 不可靠」当成产品判断讲**，而不是当成失败藏着。
   这在专业语境下是加分项：说明候选人知道**什么时候不该用 AI**。
   你们门槛里那条「零 AI 致错」本身就是专业判断的体现。

3. **沉淀「校园赛事赛制模板」**。四阶段收敛、轮空配比这些知识有复用价值，
   其他学校组织者能直接受益——这是比功能数量更好的传播点。

4. **开源**。技术栈通用（Next.js + Supabase），其他高校电竞社团可直接部署。
   这会把「一个人的项目」变成「有他人使用的项目」，量级完全不同。

## 六、发展空间判断

**分三种目标给结论，因为答案完全不同：**

| 目标 | 判断 | 理由 |
|---|---|---|
| **商业化** | **否定** | 校园赛事无付费方；平台侧已有免费替代；规模上限低；数据涉及未成年人隐私，合规成本高 |
| **求职作品** | **肯定，但要换讲法** | 真实用户、真实数据、真实故障处理——这三点比功能数量重要得多。但目前叙事重心在「做了多少功能」，而应在「解决了什么别人解决不了的问题」 |
| **开源工具** | **肯定** | 场景通用、技术栈通用、有真实使用记录。是把它从「个人作品」推向「被他人使用」的最低成本路径 |

**一句话**：**它不缺功能，缺的是一句话。** 发展空间取决于能否把「改期协同」这个真实痛点
立成产品主张，而不是继续往上加功能。

## 七、下一步行动建议（按优先级）

### P0 —— 不做会持续失血

1. **写一句话定位，并在所有对外材料里统一使用**。
   建议方向：**「为会改期的赛程而设计的赛事运营系统」**。
   判断标准：这句话能否让听的人立刻问出「为什么改期难？」——能，就是对的。

2. **把 AI 的叙事从「能识图」改成「我们验证了它在什么条件下不可靠」**。
   具体做法：把影子对照的方法和结论整理成一页——3 场样本、8/10 字段、
   协议改版后未改善、因此当前定位是「预填辅助而非自动判定」。
   **这是专业判断力的证据，不是失败的证据。**

### P1 —— 决定项目「是否被验证过」

3. **让至少一名真实裁判用一次**。哪怕只有一场。这件事的价值高于再写两千行代码——
   它把「裁判端」从假设变成事实。

4. **继续积累 AI 对照样本（目标几十场）**，每场报分时留存原图。
   样本不足之前不对 AI 能力下任何结论，也不对外承诺准确率。

### P2 —— 可以后置

5. **收敛功能面**。列出「明确不做」的清单并在文档里固定下来，
   阻止功能继续膨胀。**这一条比新增任何功能都重要。**

6. **评估开源**。若决定做，先写一份「其他社团如何部署」的说明——写不出来，说明还不具备开源条件。

## 八、风险与关键假设

### 关键假设（若不成立，上述判断需重估）

| 假设 | 若不成立会怎样 |
|---|---|
| 负责人会继续办赛 | 项目失去真实场景，退化为作品集项目，价值大幅下降 |
| 比赛期间系统持续被使用 | 「真实运行」这个最强论据消失 |
| 改期协同确实是校园赛事的普遍痛点 | 差异化锚点不成立，需重新寻找 |

**第三条我需要明说**：我确认了「它被做出来了」，但**没有验证「其他学校也有同样的痛点」**——
这需要问其他组织者，我没有这个数据。

### 风险

1. **功能面继续膨胀**。每多一个页面，主线就更模糊一分。这是当前最现实的风险。
2. **AI 叙事翻车**。若在对方面前把 AI 说成核心能力，而对方追问准确率，会非常被动。
3. **单点依赖**。系统只有一人可维护，赛事期间出现故障没有备份方案。
4. **隐私合规**。205 名选手的**姓名与学号**在系统中（实测：报名收集姓名字段，
   公开接口只返回游戏 ID、不返回学号，属于正确设计）。但赛事停办后的数据处置需要明确交代。

---

## 九、一句话总结

**这是一个有真实用户、真实数据、真实事故的完整系统，但它把自己的强项藏在了功能列表里。
它不需要再做更多功能，需要的是承认「改期协同」是它的核心，
并把 AI 从「卖点」降级为「一个经过验证、当前不达标的辅助能力」——这两件事都做完，它的价值才会显出来。**
