- 文档类型：运行手册（SYS-02 交付物）
- 日期：2026-09-11
- 适用对象：赛事负责人、轮值值班人
- 配套工具

## 一、这份手册解决什么

把 Gate 6 做过的一次性验证，变成办赛期间任何值班人都能照着执行的东西。

比赛日出问题时的目标是：**五分钟内知道故障在哪一层，并知道下一步该做什么。**

## 二、健康接口能证明什么、不能证明什么

地址：`https://ecustesports.top/api/health`

它返回两个能力的状态：数据库、对象存储。

| 它能证明 | 它不能证明 |
|---|---|
| 服务端进程还活着 | 业务逻辑是否正确 |
| 服务端能读到数据 | 页面能不能打开（前端） |
| 服务端能访问对象存储 | 域名解析是否正常 |
| — | 网络通不通 |
| — | 报名、约赛、报分这些具体功能是否正常 |

**看到 200 不代表赛事功能正常。** 200 只说明后端依赖可用。要判断功能是否正常，必须另外走一次真实操作。

返回值只包含能力级状态，不含网址、密钥、表名、bucket 名或报错内容。

| 返回内容 | 含义 |
|---|---|
| `{"ok":true,"checks":{"database":"ok","storage":"ok"}}` | 数据库与存储都可用 |
| `{"ok":false,"checks":{"database":"down","storage":"ok"}}` | 数据库不可用 |
| `{"ok":false,"checks":{"database":"ok","storage":"down"}}` | 对象存储不可用 |
| HTTP 503 | 上述任一不可用 |
| 非 JSON，或连不上 | 故障在更外层（平台或网络） |

## 三、最小监控项

| 监控项 | 怎么看 | 正常标准 | 异常说明 |
|---|---|---|---|
| 主页 | 巡检脚本 / 浏览器 | HTTP 200，页面有内容 | 前端或平台问题 |
| 健康接口 | 巡检脚本 | HTTP 200 且 `ok` 为 true | 后端依赖问题 |
| 公开赛程读取 | 巡检脚本（带赛事 ID） | 返回 JSON | 应用或数据问题 |
| 函数响应时间 | 巡检脚本 / Vercel 日志 | 首页与接口 1 秒内 | 明显变慢先看 Supabase 用量 |
| 函数错误率 | Vercel 控制台日志 | 无持续 5xx | 连续 5xx 即处理 |
| 数据库可用性 | 健康接口 `database` | ok | 见第六节 |
| 存储可用性 | 健康接口 `storage` | ok | 海报上传会失败，赛事主体可继续 |

错误率与响应时间在 Vercel 控制台的项目日志里看。免费版日志保留期有限，所以比赛日靠固定频率跑巡检，而不是事后翻日志。

## 四、检查频率与责任

| 场景 | 频率 | 谁 | 做什么 |
|---|---|---|---|
| 平时（无赛事） | 每周一次 | 负责人 | 跑一次巡检，确认四层正常 |
| 报名开放期 | 每天一次 | 负责人 | 巡检 + 打开报名页确认能提交 |
| 比赛日 | 第一场比赛前，之后每两小时 | 值班人 | 巡检 + 抽查一场公开赛程 |
| 赛后 24 小时内 | 一次 | 负责人 | 备份 + 校验（见第七节） |

## 五、出事了找谁

| 角色 | 人 | 负责 |
|---|---|---|
| 主接收人 | 彭杰（赛事负责人） | 接收异常、判断、决定是否降级 |
| 备接收人 | 待负责人填写 | 主接收人联系不上时接手 |
| 降级执行 | 待负责人填写 | 把最新赛程发到群里，人工通知队伍 |

升级路径：

1. 值班人发现异常，先跑巡检脚本，把输出的「判断」一行留档。
2. 立即通知主接收人，附上巡检输出。
3. 主接收人 15 分钟内判断是否需要降级。需要降级时，用最近一次校验通过的备份导出赛程，发到赛事群。
4. 主接收人联系不上，直接找备接收人。
5. 超过 30 分钟仍未恢复，按降级方案执行，不再等待修复。

## 六、五分钟定位故障在哪一层

```bash
npm run ops:probe
```

要测真实赛程读取：

```bash
npm run ops:probe -- --base=https://ecustesports.top --event=<赛事ID>
```

脚本逐层检查并给出一行判断，对照下表执行：

| 脚本判断 | 故障层 | 立刻做什么 |
|---|---|---|
| 网络或 DNS：三个地址全部连不上 | 网络 | 换手机热点重跑同一命令；仍不通则通知主接收人 |
| 平台层可疑：响应里没有 Vercel 标记 | 平台 | 打开 Vercel 控制台看最近一次部署状态 |
| 数据层故障：数据库与存储都不可用 | 数据 | 打开 Supabase 控制台，确认项目是否被暂停，被暂停就点 Restore |
| 数据层故障：数据库不可用 | 数据 | 看 Supabase 用量与项目状态 |
| 数据层故障：对象存储不可用 | 数据 | 看 Storage 是否超免费额度；临时停掉海报上传 |
| 应用层异常：公开赛程接口失败 | 应用 | 确认赛事 ID 是否正确；再看 Vercel 日志 |
| 前端异常：首页内容不像正常页面 | 前端 | 强刷浏览器；确认最近一次部署成功 |
| 正常：四层全部通过 | — | 玩家反馈的问题属于具体功能，按功能排查 |

不带 `--event` 时，赛程接口返回 404 属正常，不代表故障。

## 七、备份、校验与恢复演练

### 7.1 备份（只读，可以对着生产做）

先设环境变量（PowerShell，把尖括号内容换成真实值）：

```powershell
$env:SUPABASE_URL="https://<生产项目>.supabase.co"
$env:SUPABASE_SECRET_KEY="<生产 service key>"
```

执行备份，文件必须放在仓库之外：

```powershell
npm run ops:backup -- --backup-only --event=<赛事ID> --label=生产 D:\ecust-backups\2026-10-01.json
```

跑完清掉环境变量：

```powershell
Remove-Item Env:\SUPABASE_URL
Remove-Item Env:\SUPABASE_SECRET_KEY
```

备份内容为五份文档：站点配置、报名、赛制、赛程、BP。带 `--backup-only` 时只导出，不写入任何库内数据，因此可以对着生产执行。

### 7.2 校验（只读本地文件）

```powershell
npm run ops:verify-backup -- D:\ecust-backups\2026-10-01.json
```

逐份文档重新计算校验和并比对。任何一份内容被改动或截断都会被指出。全部通过时输出 `ok: true`。

### 7.3 恢复演练（只能在隔离库做）

不加 `--backup-only` 就是完整演练：把备份写进一个临时赛事、逐份读回比对校验和、最后删掉临时赛事。

**这一步会往库里写数据，只允许对隔离用的 Supabase 项目执行，永远不要对生产执行。**

```powershell
# 环境变量指向隔离库，而不是生产库
$env:SUPABASE_URL="https://<隔离项目>.supabase.co"
$env:SUPABASE_SECRET_KEY="<隔离库 service key>"
npm run ops:backup -- --event=<隔离赛事ID> D:\ecust-backups\drill.json
```

### 7.4 备份文件的保管规矩

- 备份文件一律放在仓库之外（脚本会拒绝写入仓库内）。
- 不要提交进 Git，不要把备份内容粘进聊天或文档。
- 建议保留最近三次，文件名带日期。
- 备份文件含真实报名数据，转发前先脱敏。

## 八、免费额度快用完时怎么办

当前是 Vercel Hobby + Supabase Free，超出限额会被暂停。

| 服务 | 免费边界 | 接近时的信号 | 处理 |
|---|---|---|---|
| Supabase 数据库 | 每项目 500 MB | 用量页接近 500 MB | 先备份，再清理历史赛事的旧赛程快照 |
| Supabase 存储 | 1 GB | Storage 用量接近 1 GB | 删除已过申诉期的证据附件；暂缓海报上传 |
| Supabase 项目活跃度 | 长期不活跃会被暂停 | 巡检突然报数据层故障 | 控制台点 Restore，恢复后重跑巡检 |
| Vercel 函数与流量 | Hobby 含免费额度 | 控制台出现用量提醒 | 降低轮询频率，避免后台页面长时间自动刷新 |
| Vercel 项目 | 超额度可能暂停 | 巡检报平台层异常 | 通知主接收人，按降级方案把赛程发到群 |

免费版没有自动备份，所以第七节的备份必须由人按频率执行。这是当前方案里最需要人盯的一件事。

## 九、三张清单

### 9.1 发布前（每次部署或改配置后）

- [ ] `npm run gate` 全绿（lint、类型检查、16 组测试、构建）
- [ ] 部署完成后跑 `npm run ops:probe`，四层全部通过
- [ ] 打开首页，确认能看到报名入口
- [ ] 用普通玩家身份提交一次报名，确认能写进去（返回 403 说明来源校验没配对）
- [ ] 确认生产环境变量没有被改动过
- [ ] 确认最近一次备份存在且校验通过

### 9.2 比赛日

- [ ] 当天第一场比赛前跑一次 `npm run ops:probe`
- [ ] 之后每两小时跑一次（或每场比赛开始前）
- [ ] 抽查一场公开赛程，确认队伍与对阵正确
- [ ] 出现异常时按第六节表格处理，并把巡检输出留档
- [ ] 主接收人保持可接通

### 9.3 赛后归档

- [ ] 赛事结束后 24 小时内执行一次备份（7.1）
- [ ] 对备份执行校验（7.2），确认通过
- [ ] 备份移到长期保存位置，保留最近三次
- [ ] 归档赛事，确认公开页面的可见性符合预期
- [ ] 检查 Supabase 数据库与存储用量，接近限额则按第八节清理
- [ ] 记录本次赛事的故障与处理（无则写「无」）
