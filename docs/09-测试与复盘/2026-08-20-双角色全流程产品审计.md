# 双角色全流程产品审计（第一轮）

- 日期：2026-08-20
- 审计对象：玩家侧公开页面、赛事负责人工作台
- 审计方法：真实浏览器操作；桌面端与 390×844 手机视口；创建一场 4 队单败 BO1 验收赛；并发模拟 4 名玩家报名
- 当前结论：**不通过**。当前版本只能视为可运行的功能原型，不能视为已经完成的工作台或可用于真实赛事的 MVP。
- 范围决定：在完成本文件定义的产品验收前，暂停 AI 接入。

## 1. 实际走过的任务链

### 赛事负责人

登录工作台 → 新建“4 队单败 BO1”赛事 → 填写策划案 → 打开新赛事报名管理 → 打开赛程 → 打开抽签。

### 玩家

进入选手报名页 → 填写身份与联系方式 → 提交报名 → 进入人才市场 → 创建队伍；随后以 3 个独立浏览器会话并发提交报名。

本轮没有继续伪造“完成比赛”的结果。因为建赛、报名和赛程三段的数据已经出现阻断性错误，继续点击旧演示赛程不能证明真实闭环成立。

## 2. P0 阻断问题

| 编号 | 问题 | 实际证据 | 风险 |
|---|---|---|---|
| B-01 | 新赛事没有初始化独立赛制和空赛程 | 创建 4 队单败 BO1 后，赛事目录没有 `format.json`，首次打开赛程却出现旧演示数据 | 新赛事无法按自身赛制运行 |
| B-02 | 赛制配置没有驱动赛程 | 4 队单败理论应为 3 场 BO1，页面实际显示 6 场旧队伍 BO3 | 页面可操作但业务结果错误，属于严重误导 |
| B-03 | 抽签能力写死为 16 队 GSL 小组赛 | 单败测试赛事的抽签页仍显示“小组赛抽签面板”；种子逻辑只接受 16 队 | 已承诺的多赛制配置只是表单层，不是真能力 |
| B-04 | 多人并发报名存在丢写/失败 | 3 个独立玩家近同时提交时，一次提交失败；成功页人数显示 2、3 不一致；最终文件只保留部分记录 | 真实 160 人报名时可能丢失数据 |
| B-05 | 玩家侧状态管理向管理员写接口发请求 | 玩家报名页和人才市场每次状态变化都会向 `/api/data/registration` POST，浏览器连续出现 401 | 玩家页面存在错误请求，状态来源不清晰 |
| B-06 | 多赛事上下文短暂串线 | 新建赛事完成后，主体进入新赛事策划案，但左侧栏仍显示旧赛事并链接到旧赛事；直接刷新后才恢复 | 负责人容易修改错赛事 |
| B-07 | 新建赛事自动替换“当前赛事” | 验收赛创建后，公开导航立即指向尚未准备好的测试赛事 | 草稿可能意外覆盖玩家当前入口 |
| B-08 | 测试与真实数据边界缺失 | 新赛事首次访问会用 `initialSchedule()` 的演示队伍落盘 | 演示数据会混入真实赛事记录 |

## 3. 玩家侧产品与 UI/UX 问题

| 编号 | 问题 | 当前表现 |
|---|---|---|
| P-01 | 手机端头部布局破损 | 390px 宽度下品牌名称被裁切成多行，英文副标被截断，菜单层级不稳定 |
| P-02 | 赛事页没有突出玩家下一步 | 筹备、报名、组队、比赛阶段都以同一组大 tab 为主，玩家需要自行判断该做什么 |
| P-03 | 移动端赛事 tab 占据过大面积 | 五个入口组成大块红色网格，挤压当前任务和赛事信息 |
| P-04 | 报名后身份能力不足 | 仅用本机 localStorage 记住选手；换设备无法找回，也没有最小验证方式 |
| P-05 | 报名信息无法自行修改 | 真实赛事中“信息错误、选手修改”是已确认高频问题，但玩家侧没有修改入口 |
| P-06 | 组队机制与文案不一致 | 文案说“互相邀请”，实际是队长可直接从选手池把他人加入队伍；没有邀请、申请或被加入确认 |
| P-07 | 隐私与同意边界不足 | 人才市场直接公开队长联系方式；队长可把未确认的选手加入首发、替补或教练 |
| P-08 | 缺少“我的赛事”主视图 | 玩家不能集中看到我的报名状态、队伍状态、下一场对手与时间、BP 入口和需要处理的事项 |
| P-09 | 空状态与阶段状态混乱 | 草稿赛事也允许按日期报名；赛事详情可能默认显示空名单或无关 tab |

## 5. 文档与实现漂移

1. `PRD_v1.2.md`、P0 冻结表、工作台设计 v0.2 和当前代码的范围互相冲突。
2. 文档多次把“自动化测试通过”写成“完整闭环已跑通”，但测试使用纯函数或演示数据，并不等于双角色真实浏览器任务成功。
3. “多赛制”“多赛事”“报名组队”“抽签发布”等能力在界面上存在入口，但底层仍含单一模板和演示数据假设。
4. 因此版本 3.25 的状态修正为：工程收口完成，产品验收未通过。

## 6. AI 接入前的四个验收 Gate

### Gate A：真实数据闭环

- 创建 4 队单败 BO1 后，自动产生 3 场空对阵骨架，不出现任何演示队伍。
- 建赛选择的阶段、队伍数和 BO 类型与抽签、赛程、公开页完全一致。
- 至少 20 个并发报名请求全部持久化，不能丢记录、覆盖或返回假成功。
- 队伍完成并经负责人确认后才能进入抽签；不完整或未确认队伍被明确拦截。
- 抽签 → 排期 → BP → 报分 → 晋级 → 决赛完成后，负责人端和玩家端读取同一份结果。

### Gate B：玩家移动端体验

- 390×844 视口无裁切、无横向溢出，导航不遮挡核心内容。
- 每个赛事阶段只突出一个当前主任务，同时保留次要信息入口。
- 玩家能查看并更正自己的报名资料；能创建队伍、申请加入、处理邀请或退出。
- “我的赛事”能展示报名/队伍状态、下一场比赛、比赛时间、对手和 BP 入口。
- 联系方式和入队操作满足最小隐私与同意要求。

### Gate C：赛事负责人工作台

- 赛事列表、新建比赛和单赛事工作区上下文明确，不显示错误赛事。
- 工作台不再复用玩家官网的大页脚和无关导航，核心画布优先。
- 当前阶段、阻塞原因、下一步操作和发布状态可在一屏内判断。
- 对阵图能表达轮次和晋级关系，并在常见桌面宽度下有效利用空间。
- 报名修改、审核、退赛/换人、名单锁定、抽签、排期、改期、报分都有可恢复的状态记录。

### Gate D：负责人亲自验收

- 彭杰亲自创建一场小型验收赛并完成负责人全流程。
- 至少使用两个独立玩家身份完成报名、组队、查看赛程和 BP。
- 记录每个任务的耗时、犹豫点、错误和需要回到群聊/文档补做的步骤。
- P0 阻断问题为 0，负责人明确确认玩家侧和工作台达到可接受水平后，才允许进入 AI Gate。

## 7. 修复顺序

1. 数据隔离、空状态、并发写入和赛事发布边界。
2. 赛制配置 → 对阵骨架 → 抽签 → 赛程的真实数据链。
3. 玩家移动端任务架构与报名/组队闭环。
4. 工作台信息架构、对阵图布局与异常操作。
5. 彭杰亲自完成 Gate D，再决定是否进入 AI 接入。
