# 数据结构与状态精简方案

- 日期：2026-10-12
- 范围：赛事配置、报名与队伍、赛程、裁判报分四条数据链
- 方法：先梳理现状（全部标注证据），再给精简方案；**默认保持线上数据兼容**

---

## 一、现状梳理

### 1.1 数据实体：四个文档

每个赛事在存储上是四个独立文档（实测 `data/events/<id>/`：`bp.json`、`format.json`、`registration.json`、`schedule.json`）：

| 文档 | 承载什么 | 主要类型 |
|---|---|---|
| `registration` | 选手、队伍、入队申请、操作日志、三个开关 | `RegistrationState` |
| `schedule` | 比赛、改期申请、版本快照 | `ScheduleState` |
| `format` | 赛制配置、抽签结果、种子池、分组 | `StagedFormatState` |
| `bp` | BP 会话 | `BPSessionState` |

**隔离方式合理**：分开存的好处是并发写入不互相覆盖（改报名不会覆盖赛程）。
**但代价是跨文档读取很常见**——实测 `registration` 接口要读 `schedule`、`stage` 接口要读两边、
`format` 接口也要读 `schedule`。**这是「耦合」的实际来源。**

### 1.2 状态全景：七个状态机

| 实体 | 字段 | 取值 | 个数 | 语言 |
|---|---|---|---|---|
| 比赛 | `MatchStatus` | 待排期 / 已排期 / 已完成 | 3 | 中文 |
| 选手 | `status` | 已报名 / 已入队 / 已退赛 | 3 | 中文 |
| 选手 | `reviewStatus` | 待审核 / 已通过 / 需修改 / 已拒绝 | 4 | 中文 |
| 队伍 | `status` | 报名中 / 已冻结 / 已退赛 | 3 | 中文 |
| 入队申请 | `TeamRequestStatus` | pending / accepted / rejected / cancelled | 4 | **英文** |
| 改期申请 | `status` | 待对手确认 / 待审批 / 已批准 / 已驳回 / 已失效 | 5 | 中文 |
| BP 会话 | `BPSessionStatus` | 进行中 / 已完成 | 2 | 中文 |
| 赛事 | `status` | draft（仅见一处） | — | **英文** |

**合计约 25 个状态取值，分布在 8 个字段上。**

## 二、冗余与可合并的部分

这是本次梳理的核心。以下每一条都有证据。

### 冗余 1：选手的 `status` 把两个维度压在一个字段里

```ts
status: "已报名" | "已入队" | "已退赛";
reviewStatus?: "待审核" | "已通过" | "需修改" | "已拒绝";
teamId?: string;   // 所属队伍
```

**代码注释自己写了**：「负责人审核状态；与是否组队分开，**避免一个 status 承担两种语义**」
——同一段注释里又承认 `status` 同时表达了「有没有队伍」和「还在不在」。

**实际可推导**：
- 「已入队」⇔ `teamId` 有值
- 「已报名」⇔ `teamId` 为空
- 「已退赛」才是真正独立的信息

→ **`status` 的三个取值里，两个可推导，只剩一个真正必要。**

### 冗余 2：队伍成员双向维护

```ts
// RegistrationTeam
memberIds: string[];   // 成员（含队长）
// RegistrationPlayer
teamId?: string;       // 所属队伍
```

**同一个关系存了两遍**：队伍记成员列表、选手记所属队伍。
任何一次进队/退队都必须同时改两处，**漏改一处就会出现「选手说自己在 A 队，A 队名单里没他」**。

### 冗余 3：比赛状态与时间字段重复

```ts
startTime: string;   // "2026-10-06T12:00:00"，**空表示待排期**  ← 注释原文
status: MatchStatus; // 待排期 / 已排期 / 已完成
```

注释明说「空表示待排期」，而 `status` 里又有「待排期」——
**同一个信息有两条来源，就必然有不一致的一天**。

### 冗余 4：三个「是否关闭」的布尔

```ts
playerRegistrationClosed: boolean;  // 停止接收新的个人报名
teamRegistrationClosed: boolean;    // 停止建队、入队与名单调整
frozen: boolean;                    // 旧字段兼容：队伍申报截止后名单冻结
```

第三个字段的注释直接写着「**旧字段兼容**」，而且实测**它是只写不读的**：
写入处只有一行 `frozen: closed`（与 `teamRegistrationClosed` 完全同步），
读取处都是「兼容 3.24 及更早数据」的老路径。**这是已经完成历史使命的字段，可以直接删。**
前两个语义接近（都是「关闭报名窗口」），只是作用范围不同，可以合并成一个「报名阶段」取值。

### 冗余 5：比赛里嵌了队名

```ts
teamAId: string;     // 队伍 ID（匿名，用于约束校验）
teamAName: string;   // 展示名
```

**这个冗余是有意的、我建议保留**——理由是比赛列表是高频读取，每次都回查队伍表代价更大。
但要说清它是「缓存」而不是「事实来源」，**写入时必须以队伍表为准**。

### 冗余 6：状态语言不统一

四个状态用英文（`pending` / `accepted` / `draft`），其余用中文。
这不影响运行，但**新加入的人（包括未来的合作者）要同时记住两套命名**。

## 三、精简方案

### 3.1 核心原则

> **能从已有数据算出来的，就不要单独存。**

现在的做法是「状态是一等公民，写到字段里」，于是**每个状态都要有人负责更新它**——
更新的地方越多，越容易出现「状态与实际不符」。改成「状态是数据的函数」之后，
**不存在更新的机会，也就不存在不同步。**

### 3.2 具体方案

**第一步：删掉可推导的状态**

| 现状 | 改成 | 判断方式 |
|---|---|---|
| 选手 `status` 的三态 | 只保留「是否退赛」 | `teamId` 有值 ⇔ 已入队 |
| 队伍 `status` 的三态 | 改成从名单算 | `memberIds` 有效人数 ≥ 5 ⇔ 满编 |
| 比赛 `status` 的「待排期/已排期」 | 合并为一态 | `startTime` 为空 ⇔ 待排期 |
| `frozen`（旧字段） | 删除 | 已无使用方 |

**保留**：选手的 `reviewStatus`、比赛的「已完成」——这两个是**外部事实**，推导不出来。

**第二步：消除双向维护**

`memberIds` 与 `player.teamId` 二选一。**我建议保留 `player.teamId`**（选手是主体，
队伍名单由它聚合），并把 `memberIds` 改成读取时才计算。

**收益**：进队/退队只改一处，**结构上不可能出现「两边不一致」**。

**第三步：统一状态命名语言**

全部改中文，或者全部改英文 —— **不要混**。建议中文，因为管理端文案是中文，
状态值直接展示时不用翻译。

**第四步：收敛报名开关**

三个布尔合成一个「报名阶段」取值：`报名中 / 停止个人报名 / 全部停止`。
但这属于**配置**而非**状态**，放 `format` 或事件配置里更合适，不该混在选手/队伍数据里。

### 3.3 数据流简化

**现状**：`registration` 接口读 `schedule`、`format` 接口读 `schedule`、`stage` 接口读三个文档。
**问题不是「跨文档读」本身，而是「谁的数据谁负责」没有讲清。**

**方案**：明确**单一所有权**——

| 数据 | 唯一所有者 | 其他文档不得直接改 |
|---|---|---|
| 选手、队伍 | `registration` | ✓ |
| 比赛、改期 | `schedule` | ✓ |
| 赛制、抽签 | `format` | ✓ |

跨文档只允许**读**（用于校验），**不允许写**。这条立下来之后，
「改赛程时顺手改一下报名状态」这类隐性耦合就不可能发生。

## 四、改动与预期效果

### 4.1 状态数量对比

| 项 | 现状 | 简化后 |
|---|---|---|
| 状态字段数 | 8 | **5** |
| 状态取值总数 | 约 25 | **约 13** |
| 双向维护的关系 | 1（成员/队伍） | **0** |
| 语言混用 | 有 | **无** |

### 4.2 具体收益

1. **不可能出现「状态与实际不符」**。删掉可推导的状态之后，那类 bug 在结构上消失了，
   而不是靠「记得同时更新」来避免。
2. **进队/退队只改一处**，消除现有的双向维护风险。
3. **新人接手成本下降**。现在要记 8 个状态机、两种语言；之后是 5 个、一种语言。
4. **跨文档写操作消失**，改一个模块不会连带影响另一个模块。

### 4.3 实施顺序（关键：线上正在比赛）

**现在有 20 场比赛、其中 10 场已完成，数据是活的。改数据结构必须分阶段，且不能影响进行中的赛事。**

| 阶段 | 做什么 | 风险 |
|---|---|---|
| 1 | **删除已无使用方的 `frozen`** | 低，纯清理 |
| 2 | **统一状态命名语言** | 低，改字符串不破坏数据 |
| 3 | **新代码不再依赖可推导的状态**（读时用推导，字段暂时保留） | 低，**读写分离，不动存量数据** |
| 4 | **赛事结束后**再物理删除冗余字段、并做一次数据迁移 | 中，但那时没有进行中的比赛 |

**关键做法是第 3 步**：先让代码「不再依赖」，数据保持原样——
**这样既拿到收益，又不用在比赛期间冒险改数据。**

## 五、我不建议做的事

1. **不建议把四个文档合并成一个。** 表面上「简单了」，但会引入并发覆盖问题
   （改报名时可能覆盖别人刚改的赛程），**这是拿正确性换简洁**。
2. **不建议动 `teamAName` 这类冗余。** 它是有意的缓存，去掉会拖慢高频读取；
   只需在文档里写明「以队伍表为准」。
3. **不建议在赛事进行中做数据迁移。** 收益可以等，数据风险不能等。

---

## 六、可以立刻做的第一件事

`frozen` 已确认是**只写不读**（唯一写入处 `frozen: closed` 与 `teamRegistrationClosed` 完全同步，
读取处只剩兼容老数据的分支）。**这是整个方案里唯一零风险、可以马上清掉的字段**，
适合作为第 1 阶段的起点——用它验证一遍「删字段 → 跑门禁 → 查线上」的流程，
再往后面更复杂的合并推进。

## 九、数据结构的真源与变更登记（2026-10-16 补）

> 补这一节的起因：2026-10-14 加一个阶段类型（`single-elim-groups`）时发现同一个真值散落在**七处**，
> 且漏掉其中一处（玩家手册页的文案表）**不会报错**，只会静默显示空白。
> 结论：**文档挡不住这类漏，断言可以** —— 所以下面「已做成守卫的」那几条是关键。

### 9.1 真源在哪

- **以代码为真源**：字段与取值的最终依据是 `src/lib/**` 与 `supabase/migrations/*.sql`。
  本文与需求类文档都可能滞后；两者冲突时以代码为准。
- 存储的真实结构 = `supabase/migrations/` 的三个 SQL（Gate6 数据存储 / 裁判证据 / 原子文档）
  + `site-config-schema.ts` 的归一化逻辑（它决定"存进去读回来是什么"）。

### 9.2 变更登记：改数据结构时，这些地方要一起改

| 你要改什么 | 必须同步改的地方 | 漏了会怎样 |
|---|---|---|
| **加一个「阶段类型」** | ① format-templates 类型联合 ② types/index.ts 类型联合 ③ site-config-schema 的 validTypes ④ api/admin/events 的 validTypes ⑤ `STAGE_TYPE_LABELS` ⑥ `STAGE_TYPE_DEFAULT_BO` ⑦ EventHandbook 的文案表（**共七处**） | 值被**静默改写**成兜底；或手册显示空白 |
| **加一个「事件字段」** | 类型（`types/index.ts` + schema 类型）→ 归一化（默认值/白名单）→ 构造点（`buildEventFromTemplate`）→ 更新接口（`api/admin/events` 的 `nextEvent`）→ 展示点 | 「存了又变回去」；或界面不显示 |
| **加一个「比赛字段」** | `schedule-data` 的类型 → `normalizeScheduleState` → 使用点 | 读出来是 `undefined` |
| **改赛程写入** | 登记进 `schedule-write-contract` 清单 + 走 `stampScheduleVersion` | 门禁红（**会点名文件**） |
| **加一个「排期模式」这类枚举** | 类型 → 归一化（只认字面量，缺失保留原值）→ 更新接口白名单 → 两端展示文案 | 模式被重置成默认；或界面选不了 |

### 9.3 已经做成守卫的（漏了会变红）

| 守卫 | 覆盖什么 | 变异验证 |
|---|---|---|
| `npm run test:stage-type-registry` | 扫描 §9.2 第①-⑦处中**散落在别处的五处**，要求每种阶段类型都被登记 | 已做：删掉 EventHandbook 那一条 → 报「漏了：single-elim-groups」 |
| `npm run test:schedule-write-contract` | 赛程写入点的文件、条数与递增方式 | 已做（给某文件加第二条写入路径即红） |
| `npm run test:game-data` | 段位/位置/地图只在 `lib/games` 写一份 | 已做 |

### 9.4 还没做成守卫的（诚实列出）

1. **「事件字段」那条链路**（类型 → 归一化 → 构造点 → 更新接口 → 展示）仍靠人工，
   可以照 `stage-type-registry` 的做法写一个源码扫描守卫，但目前没做。
2. **归一化的默认值口径**没有统一约定表：哪些字段"缺失即回落默认"、哪些"缺失保留原值"、
   哪些"缺失即拒绝"，散在各处。`scheduleMode` 的「未提交则保留原值」就是手工判断的结果。
3. **`supabase/migrations` 与代码的同步**没有守卫：改了归一化但没加迁移，本地与线上会不一致。

| 你改什么 | 只改这里 | 为什么 | 守卫 |
|---|---|---|---|
| **排期参数与比赛日窗口的推导** | `src/lib/scheduling/schedule-policy.ts` | 后台界面按钮与命令行脚本都从它取；**不要**在调用点各写一份 | `test:bulk-schedule` 组8 |
