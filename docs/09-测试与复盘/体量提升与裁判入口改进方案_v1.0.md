# 平台体量提升 · 裁判入口排查 · 开源评估

- 日期：2026-10-12
- 起因：负责人指出「平台体量小、可讨论的点过于具体」，并要求排查裁判端无人使用的原因
- 说明：本文所有「实测」均指我实际读过代码或调过接口；「推断」可信度较低，已单独标注

---

## 〇、先修正我上一条的错误

我上一份评审把「会改期的赛程」当成核心差异化去讲，**这个方向是错的**。

错在两点：

1. **它是一个功能点，不是产品主张。** 拿一个具体功能当「核心竞争力」，
   讨论层次就停在「这个功能怎么做」上，撑不起平台级的对话——这正是负责人说的「太小」。
2. **它不可扩展。** 改期协同做得再深，也只是整个赛事流程里的一小段；
   用它当主线，等于自愿把天花板压到那一段的高度。

**正确的问法是：这个平台要成为什么？** 而不是「它比别的工具多会做什么」。

---

## 一、体量与完成度：四个提升方向

「体量」不是功能数量（现在已有 31 个页面、36 个接口，不算少）。
体量是**系统的广度与深度**——能支撑多复杂的运营、能沉淀多少资产、能容纳多少角色。

按这个标准，有四个方向，我按**「收益 / 成本」**排序：

### 方向 1（P0）：把平台从「一届工具」变成「多年赛事平台」

**现状**：一届比赛对应一个赛事实体，赛事结束后数据就静止了。

**目标**：**历史沉淀**——历届成绩、选手档案、队伍战绩可跨届累积。

**为什么这条排第一**：
- 它是**唯一能让「体量」在一夜之间变大的事**——不需要新功能，只需要把已有的数据结构改成跨届；
- 它把散落的数据变成**资产**，于是可以讨论的东西从「这届怎么办」变成
  「三届下来选手水平怎么变」「哪支队在什么赛制下更强」；
- **成本低**，因为底层已经支持多赛事（`events` 是独立实体，实测已有）。

**做法**：选手身份跨届去重（现在学号是唯一标识）、跨届战绩聚合、历届赛事归档页。

### 方向 2（P0）：把裁判端真正启用（详见第二节）

**为什么和方向 1 并列第一**：裁判端已经写完了（862 行，流程完整：认领 → 传图 → AI 预填 → 确认 → 提交），
**只是没人能用**。这是**成本最低、收益最直接**的一块——不用写新东西，把它变得能用即可。

而且它一旦跑起来，**这个系统才第一次出现「第二类真实用户」**。
现在所有功能都只有负责人一个人用，这本身就是「体量小」的根源之一。

### 方向 3（P1）：从「负责人后台」扩展到「多角色协同」

**现状**：负责人 + 裁判（未启用）+ 选手（只读）。

**目标**：补上**队长端**——提交名单、确认可用时间、申请改期。

**为什么值得做**：改期的真实痛苦恰恰在「和队长反复协商」这一环。
现在这一环在系统外（群聊），如果队长能直接在系统里确认时间，
**「改期协同」才从「一个人用工具」变成「多方协作流程」**——这时候它才配当一条主线。

### 方向 4（P2）：加入内容与观赛侧

赛程页现在是「表格 + 对阵图」。可以往上加：赛程看点、战报、选手数据榜。

**为什么放后面**：这是「锦上添花」，不解决「体量感」的根本问题——
**它增加的是内容，不是系统的复杂度**。

#### 优先级一句话

**先让第二类用户真正用起来（裁判、队长），再谈沉淀（历史数据），最后才是内容和观赛。**

判断标准很硬：**如果平台只有一个人用，它的体量就永远是一个人的项目。**

## 二、裁判入口排查：问题清单与改进方案

我在本地把裁判端的代码从头读了一遍。**问题不在「设计不好看」，而在「根本进不来、进来了也留不住」。**

### 2.1 实测发现的问题（按严重度）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **全站没有任何入口指向裁判端** | 全仓库 grep `"/referee"`，**结果为空** | 裁判只能靠别人口头发网址 |
| 2 | **要手输「赛事 ID」** | 登录表单有第二个输入框，占位符写着「例如 event-1」 | 裁判不知道这是什么，也不知道去哪查 |
| 3 | **要粘贴「裁判凭证」** | 占位符「粘贴凭证」；且**凭证需要负责人单独发给每位裁判** | 多一道人工分发，且账号还没建 |
| 4 | **刷新页面凭证就丢** | 界面原文：「凭证只保存在当前页面内存中，刷新或关闭页面后需要重新输入」 | **手机上极易触发**：切到微信再回来、误触刷新，就得重来一遍 |
| 5 | **标签用英文** | `REFEREE GATE` | 裁判看不懂，显得像内部工具 |
| 6 | 裁判账号尚未创建 | 项目文档记录「等开赛了再说」 | 即使以上都好，也没人能登进来 |

**关键判断**：问题 1、2、4 任何一条单独存在，就足以让裁判放弃。
三条叠加——**裁判端不是「体验不佳」，是「事实上无法使用」**。

### 2.2 改进方案

按「先能进得来，再谈好用」的顺序：

**第一步：解决「怎么找到」（必须做，成本最低）**

- **在首页和赛程页加入口**（现在一个都没有）；
- **更彻底的做法：给每场比赛生成一个二维码**。
  负责人打印出来贴在比赛位／发到赛事群，裁判**扫码直达这场比赛的报分页**——
  **不需要输凭证、不需要输赛事 ID、不需要知道网址**。

**这一步是整套方案里性价比最高的**：它把三个输入项（网址、凭证、赛事 ID）一次性消掉。

**第二步：解决「留得住」**

- 凭证改存 `sessionStorage`（现在纯内存，刷新即失）；
- 或者更根本：**把凭证编码进二维码**，每次扫码自动带上。

**第三步：解决「看得懂」**

- `REFEREE GATE` 改中文；
- 删除「赛事 ID」输入框（从二维码或 URL 带参）；
- 空态文案改成动作指引（现在是「还没有你要裁的比赛，从下面挑一场认领」，基本合格）。

**第四步：验证真实可用性**

- **手机上实测整条路径**（触控目标尺寸、横向溢出、弱网）；
- **让 1 名真实裁判走一次完整流程**——这是唯一能把「裁判端」从假设变成事实的动作。

### 2.3 一个需要负责人确认的事实

**「裁判端没人用」有两种可能**：
(a) 入口和体验的问题（我上面列的那些）；
(b) **根本没有裁判拿到凭证**（文档里记着账号还没建）。

**从代码看不出 (a) 和 (b) 哪个是主因。** 我能确认 (a) 确实存在且严重；
但如果是 (b)，那么**先解决 (b) 再谈体验优化**——否则优化了也没人测。
这一条需要负责人确认：**是否曾经有裁判拿到过凭证并尝试登录？**

## 三、开源评估

### 3.1 可行性

| 条件 | 状态 |
|---|---|
| 技术栈通用（Next.js + Supabase） | ✓ 是主流栈，无私有依赖 |
| 有真实使用记录 | ✓ 36 队 / 205 人 / 20 场 |
| 有测试与质量门禁 | ✓ 统一门禁，多套件通过 |
| **代码与数据分离** | **✗ 阻塞项**：`data/` 与 Supabase 里含真实选手姓名、学号 |
| **他人可自行部署** | **✗ 阻塞项**：依赖 Supabase 配置、环境变量、种子数据，目前没有部署文档 |

**结论**：**技术上可行，但现在不具备开源条件。** 两个阻塞项必须先解决。

### 3.2 利弊

**利**：
- **把「个人项目」变成「他人可用的项目」**，这是量级上的变化；
- 其他高校电竞社团可直接复用，**产生真实的外部使用**；
- 有了外部用户，**「为什么这样设计」才有讨论对象**——这恰好回应「讨论内容没价值」的问题。

**弊**：
- **维护成本**：一旦有人提 issue、提 PR，就要回应；
- **隐私风险**：真实选手数据若随代码泄露，是实质问题；
- **没有直接收益**，且占用精力（负责人现在还要办赛）。

### 3.3 方式（如果做）

1. **先剥离数据**：删除所有真实报名数据，换成可公开的种子数据；
2. **补部署文档**：目标标准是「另一台电脑上照着做能跑起来」——**写不出来就说明还不具备条件**；
3. **License 选 MIT**：校园场景、无商业化意图，MIT 最省事；
4. **保留一份「设计决策记录」**：这个项目的价值不只在代码，更在「为什么这样设计」——
   决策记录才是别人真正会看的部分。

### 3.4 是否值得推进

**判断：值得，但不是现在。**

理由：

- **开源的核心价值是「外部使用」**，而目前**自己的裁判端都还没人用**。
  连内部第二个用户都没跑通就去开源，很可能的结果是「开源了但没人用」，反而消耗精力；
- **成本集中在「部署文档」上**，这件事有明确的前置条件（一键可跑），
  而现在系统依赖 Supabase 配置，别人大概率跑不起来；
- **更划算的顺序**：先把裁判端和队长端跑通（有了第二个、第三类用户）→ 再剥离数据、补部署文档 → 开源。
  那时开源是「分享一个被验证过的系统」，而不是「发布一个只有作者能跑的项目」。

**触发条件（满足其一再启动）**：
1. 至少 1 名真实裁判 / 队长完整用过一轮；
2. 或：负责人需要用它作为对外作品、希望有可点击的公共链接。

## 四、三件事的先后

| 顺序 | 做什么 | 为什么排这里 |
|---|---|---|
| 1 | **让裁判端能进得来**（入口 + 二维码 + 云端凭证） | 成本最低、直接产生第二类用户 |
| 2 | **确认是否曾有裁判拿到凭证** | 若是「没发凭证」，前面做得再好也没人用 |
| 3 | **历史数据沉淀**（跨届） | 不需要新功能，却能让体量立刻变大 |
| 4 | **队长端** | 让「改期」从单人操作变成多方协作 |
| 5 | **开源**（剥离数据 + 部署文档） | 等有了外部使用意愿再做 |

## 五、关键假设与风险

**假设**：
- 假设比赛期间还有余量做这些改动（目前 20 场已完成 10 场，赛事进行中，改动需谨慎）；
- 假设裁判愿意用系统（未验证——这正是要先让一人试用一次的原因）。

**风险**：
1. **在比赛进行中改动裁判端**可能影响正在进行的比赛——建议先做「新增入口」这类无侵入改动，
   凭证存储方式的改动放在赛事间隙；
2. **开源若在数据剥离前启动**，会泄露真实选手信息，这是不可逆的；
3. **功能继续增加而不收敛**——方向 3、4 都容易变成「做更多页面」，
   判断标准仍是那句：**平台有几个真实用户，而不是有几个页面。**
