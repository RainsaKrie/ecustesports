## 1. 一句话架构

Next.js（App Router）单体应用 + 两套可切换的数据后端（本地文件 / Supabase），
把「配置」与「事件数据」分开存：配置是一份文档，事件数据按 eventId 分文档存放。

## 2. 目录与职责

| 目录 | 职责 | 说明 |
|---|---|---|
| `src/app` | 路由层 | 页面（`admin/` 管理端、公开页）与 API（`api/admin`、`api/public`、`api/data`） |
| `src/components` | 界面层 | `components/admin/` 管理端组件、`components/events/` 玩家侧组件 |
| `src/lib` | 领域层 | 排期/赛制/报名/裁判/证据等纯逻辑与数据访问 |
| `supabase/migrations` | **数据结构的真实来源** | 三个 SQL：Gate6 数据存储 / 裁判证据 / 原子文档 |
| `tools/gate6` | 运维与端到端脚本 | 备份、巡检、端到端演练（含隔离赛事） |
| `docs` | 文档 | 见 `docs/README.md` 的目录说明 |

## 3. 两种运行形态（最容易踩的坑）

| 环境 | 后端 | 数据来源 |
|---|---|---|
| 本地开发 | `file` | `data/` 下的 JSON 文件 |
| 生产 | `supabase` | Supabase 文档表 |

- **判定点只有一处**：`src/lib/data-backend.ts` 读 `DATA_BACKEND`，`data-store.ts` 据此选后端。
  有守卫断言"全仓库只有这一处读它"。
- **推论**：改 `data/` 下的文件**只在本地生效**；线上配置必须走管理端 API。
- **两套环境的赛事 ID 不同**（本地 `event-mt8f43vq`、生产 `event-1`），写脚本时别混。

## 4. 数据分层

| 层 | 内容 | 读取方式 |
|---|---|---|
| 配置层 | 赛事列表与站点配置（一份文档，含 `events[]` 与 `stageConfigs` 等） | `getSiteConfig` / 公开接口 |
| 事件数据层 | 每个赛事各自一份：`schedule`（赛程）、`registration`（报名）、`format`（抽签与赛制）、`evidence`（证据）、审计与台账 | `readEventData(eventId, kind)` |
| 公开读取层 | 对玩家侧暴露的只读视图 | `src/lib/public-data-cache.ts`，**缓存 5 秒**（三个：站点配置 / 赛程 / 报名） |

**★ 公开层有 5 秒缓存**：刚写完就读公开接口，可能仍是旧值 —— 这**不代表写入失败**。
核实写入结果要用管理端接口（不走缓存）。

## 5. 三条链路与权限边界

| 链路 | 入口 | 能写什么 | 鉴权 |
|---|---|---|---|
| 玩家侧 | 公开页面 / `api/public` | 只能提交约赛申请、报名类操作 | 参赛令牌（`participant-auth`）；**不能直接写赛程** |
| 裁判侧 | 裁判工作台 / `api/referee` | 只能提交自己那场的赛果与证据 | 裁判凭证（`referee-auth`） |
| 管理侧 | 管理端 / `api/admin`、`api/data` | 全量（排期、赛制、报名审核、结束赛事…） | 管理端会话（`isAdminRequest`）；**鉴权只有一份实现**（有守卫断言） |

生产环境写入还带**来源校验**（缺同源头部返回 403）——本地无此校验，所以"本地能写、线上 403"
不是权限问题。

## 6. 写入契约与护栏（本项目最独特的一块）

赛程是**多写入点**共享的文档，所以有一整套约定，违反会静默写坏数据：

1. **统一递增入口**：改动赛程必须走 `stampScheduleVersion(before, next)`，
   版本号一律 `before.version + 1`（不采信调用方传来的版本）。
2. **写入点登记**：所有写 `schedule` 的文件必须登记在
   `src/lib/scheduling/schedule-write-contract.test.ts` 的清单里（文件 + 条数 + 递增方式），
   新增写入点会被门禁拦下，**报错会点名是哪个文件**。
3. **三道数据护栏**：
   - 内容丢失护栏（`detectScheduleLosses`）：整份保存时，若会覆盖别人的成果则拒绝并点名；
   - 赛果丢失护栏（`assertResultsPreserved`）：**已有赛果/已排期的比赛不得因一次写入消失**；
   - 版本冲突：条件写入（`if-match`）不匹配则 409 拒绝，不覆盖别人的改动。
4. **历史与可回溯**：赛程文档自带 `versions`（每条含 version / matches / note / createdAt），
   每次变更都留下"改了什么"。**数据看着不对时，先读它**（见配对文档的排查手册）。

## 7. 质量门禁与验证

- `npm run gate` = lint（0 错 0 警）+ 类型检查 + **34 套测试** + 构建。
- `npm run gate:full` = gate + 需要起 dev server 的三条端到端（裁判链路 / 换赛制演练 / 36 队演练）。
  → **需要起 dev server 的套件不进 `test:all`**：否则"本机没有别的 dev server"会变成门禁前提。
- **变异验证文化**：凡声称"修好了 / 有守卫"，必须附一次"把它去掉是否变红"。
  这是区分"真守卫"和"装饰性断言"的唯一手段。
- 端到端演练必须自带隔离数据与清理（用完按校验和还原），且不碰生产。

## 8. 已知的架构级薄弱处（如实列出）

1. **同一个真值散落在多处**：阶段类型要改 7 处（类型联合两份、白名单两处、文案表两处、构造点）；
   加一个事件字段要同时改类型、schema、归一化、构造点。**没有单一真源**。
2. **文档滞后于代码**：流程类文档停在 9 月初；此后加了四阶段赛制、组内单败、排期模式二分。
3. **对外推送通道为零**：没有邮件/webhook/企业微信，所以任何"无人值守告警"都无处可发
   （这是"不做定时监控"决定的真正原因）。
4. **单人运维**：所有方案都假设只有一名负责人，不引入需要"每天有人看板"的机制。
5. **数据被清空过一次**：2026-10-14 赛程被"归档并重抽"清成 0 场（功能符合设计，但事后才查清）。
   → 护栏已补，但**"危险动作的提示是否足够"仍未评估**。

## 9. 变更须知（动代码前先看这四条）

1. **以代码为真源**：本文与数据模型类文档都可能滞后；判断某个字段/取值时，
   先看 `src/lib/**` 与 `supabase/migrations/`，再看文档。
2. **新增赛程写入点** → 先登记到写入契约清单，否则门禁红。
3. **新增阶段类型 / 事件字段** → 顺着"谁声明它、谁归一化它、谁构造它、谁展示它"全找一遍
   （§8.1 那 7 处就是漏掉某一处的后果）。
4. **动赛程/报名相关流程** → 同时更新配对文档《数据流转与写入点登记表》，否则它立刻过期。
