# 数据流转与写入点登记表 v1.0

> 2026-10-16 起草。与《系统架构总览》配对：那份讲结构，这份讲**数据怎么动、在哪会坏**。
> **用途**：① 改任何写数据的代码前先查这里；② 数据看起来不对时，按 §6 的顺序排查。
> 本文内容来自实际排查（2026-10-12 至 10-16 的多次事故调查），不是设计设想。

## 1. 三个数据域

| 域 | 存放 | 特点 |
|---|---|---|
| 站点配置 | 一份 `site-config` 文档（含 `events[]`） | 赛事的存在与赛制、可见性等"赛事级设置" |
| 事件数据 | 按 `eventId` 分文档：`schedule` / `registration` / `format` / `evidence` / 审计与台账 | 每个赛事一份，互不影响 |
| 运行产物 | 审计（`operation_audit`）、赛果台账、证据 | 用于回答"谁在什么时候改了什么" |

## 2. 一次写入的全链路

```
界面（管理端 / 玩家侧 / 裁判端）
  → 路由（api/admin | api/public | api/referee）
      · 鉴权（isAdminRequest / 参赛令牌 / 裁判凭证）
      · 生产环境额外有来源校验（缺同源头部 403，本地无此校验）
  → 领域层纯函数（校验 + 生成新状态，如 submitResultOp / setMatchTimeOp）
  → data-store（读改写：readEventData → 变换 → updateEventData）
      · 后端 = resolveDataBackend()：本地 file / 生产 supabase
  → 写后：审计一行 + 版本号递增 + 必要时生成通知草稿
  → 读取侧：公开接口走 public-data-cache（**缓存 5 秒**）；管理端接口不走缓存
```

**关键推论**：写完立刻读**公开**接口可能仍是旧值（5 秒缓存），这不代表写入失败 ——
核实写入要用管理端接口。

## 3. 赛程写入点登记表（六处）

赛程是**多写入点共享文档**，所有写入点必须登记在
`src/lib/scheduling/schedule-write-contract.test.ts`，门禁会核对"文件 + 条数 + 递增方式"。

| # | 写入点 | 触发时机 | 版本递增 | 备注 |
|---|---|---|---|---|
| 1 | `app/api/data/schedule/route.ts` | 整份保存（管理端赛程页） | 走 `applyScheduleSave` | 自带**内容丢失护栏**与版本冲突裁决 |
| 2 | `app/api/data/bp/route.ts` | BP 完成 | `stampScheduleVersion` | 顺带写通知草稿 |
| 3 | `app/api/public/schedule/request/route.ts` | 队长约赛申请 / 对手确认与审批（**2 处**） | `stampScheduleVersion` | **固定比赛时间模式下直接拒绝**（队伍侧无协商入口） |
| 4 | `lib/referee/reporting-data.ts` | 裁判提交赛果 | `stampScheduleVersion` | 曾是可豁免的例外，2026-10-12 取消 |
| 5 | `app/api/admin/events/format/route.ts` | 换赛制时清掉"未开打骨架" | `stampScheduleVersion` | 只清"待排期且无开赛时间"的场次 |
| 6 | `app/api/admin/events/route.ts` | 新建赛事等 | 豁免 | 尚未登记递增理由，属已知遗留 |

## 4. 版本号口径

- **唯一递增入口**：`stampScheduleVersion(before, next)` → `{ ...next, version: before.version + 1 }`；
  **不采信调用方传来的版本值**（否则版本护栏形同虚设）。
- 内容没变时原样返回、不递增（避免无意义地让别人的编辑器失效）。
- **为什么重要**：版本号是"别人改过没有"的唯一信号。若某条路径写赛程却不递增，
  别人的旧快照就能在它之后覆盖回去 —— 2026-10-12 的事故正是这么发生的。

## 5. 三道数据护栏

| 护栏 | 位置 | 拦住什么 | 绕过它的方式（都实测过） |
|---|---|---|---|
| 内容丢失护栏 | `applyScheduleSave`（写入点 1） | 整份保存会覆盖别人的成果时拒绝并点名 | **只在那一条路径上**；其余直写路径不走它 |
| 赛果丢失护栏 | `stampScheduleVersion`（所有走统一入口的路径） | 有赛果/有开赛时间的比赛因一次写入消失 | 归档类操作（见下）**刻意不走它**，因为清空是它的正常语义 |
| 版本冲突 | `if-match` 条件写入 | 别人改过之后覆盖回去 | 需要调用方传对版本；不传就绕过了 |

**★ 2026-10-14 的真实案例**：赛程 40 场（含 20 场已录赛果）被写成 0 场。
事后查清是**「归档并重抽」这个功能被触发**（`archiveAndClearScheduleOp`，
赛程页有确认弹窗，语义就是"清空当前对阵、保留历史版本"）—— 不是异常写入。
它的清空**刻意不经过赛果丢失护栏**；数据没有丢，在 `versions` 历史里。
→ **教训**：看到数据"消失"，先确认是不是某个既有功能的正常语义（见 §6）。

## 6. 排查手册（数据看着不对时按这个顺序）

1. **先读变更历史**：赛程文档自带 `versions`（version / 场次数 / 时间 / **说明**）。
   多数"数据没了"在这就能查到是谁、什么时候、干了什么（说明文字往往直接点名功能）。
2. **再读审计**：`operation_audit` 记录管理端操作；判分链路另有台账。
3. **再排除缓存**：公开接口 5 秒缓存 → 用管理端接口复核，别把旧值当失败。
4. **最后才查代码**：翻写入点登记表，看哪条路径能产生这个结果。
   （2026-10-14 我跳过前三步直接查代码，连查三轮才回到第 1 步找到答案。）
