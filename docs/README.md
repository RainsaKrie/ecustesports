## 项目目标

以即将举办的新一届校内《无畏契约》赛事为真实场景，按照正式产品流程完成问题研究、需求定义、PRD、人机协作设计、原型、真实赛事使用和效果复盘。项目不以商业化为前提，但必须产生可运行结果、真实使用记录和可解释的产品决策。

项目代码、产品资料和验证材料统一位于 `D:\桌面\esports-operations-assistant`，本文档位于其 `docs` 目录。当前先搭建赛事策划、报名与队伍、赛制与抽签、赛程中心、比赛执行、通知中心、赛事报告和赛事设置八个模块的完整框架；赛程中心仍是首个重点验证模块，但不再以孤立单功能页面作为整个产品的起点。

## 当前核心场景

赛事负责人导入确认后的队伍名单、队伍可用时间、裁判可用时间和赛制规则；系统检查数据与时间冲突，生成可审核的赛程草案。当队伍提出变更时，系统给出影响范围和调整方案，由负责人确认后形成新赛程与通知。

“方向和范围已确认”不等于产品价值已经得到验证。当前仍需证明：该流程是否能减少排程与临时调整耗时，避免队伍、比赛时段和裁判资源之间的冲突。

问卷星、WPS/腾讯文档、QQ 群和微信群是必须纳入评估的既有工具，但项目不预设“全部替代”或“仅做轻量补充”。当前领先候选是由产品真正承接赛程约束、生成、审批、变更和版本管理核心闭环，再根据迁移成本决定报名收集、共享文档和群通知采用迁移、集成还是保留；该产品形态仍需验证。

## 已有真实依据

- 赛事规模约 160 人、32 支队伍，裁判约 3—4 人。
- 原计划在每周六、日 12:00—18:00 举行，每场预留 1.5 小时，同时进行 2 场。
- 固定赛程发布后，许多队伍不满或无法参赛，后来改为两支队伍自行协商时间，裁判临时顶上。
- 曾发生双方临时调整时间后同时进行 3 场比赛，造成裁判不足。
- 阶段规模为入围赛 32 支、小组赛 16 支、淘汰赛 8 支，即 `32 → 16 → 8`。
- BO1、BO3、BO5 分别预留 45、90、150 分钟；不能继续用统一 1.5 小时时隙处理所有比赛。
- 已确认采用 VCT Champions 2025 的结构：16 队分为 4 组进行 GSL 式双败晋级，8 队进行完整双败淘汰；败者组决赛和总决赛 BO5，总决赛不重置。种子按首发5人当前段位平均水平划分，不设置同学院或同社团避让。

## 系统职责边界

| 责任方 | 职责 |
|---|---|
| 数据规则 | 必填、去重、格式、版本和明确冲突检查 |
| 规则/排程系统 | 赛制、对阵、时间容量、队伍与裁判硬约束、BO3/BO5 时长和冲突检查 |
| AI | 识别模糊、缺失和矛盾信息，解释不可满足原因，比较调整方案并生成通知 |
| 赛事负责人 | 处理例外，批准名单、赛程和临时调整，决定是否对外发布 |

## 配置与数据维护原则

- 负责人可编辑：站点品牌、导航文字、首页文案与主视觉、赛事名称与状态、规模、对外日期、赛制摘要、参赛步骤、赛事规则、奖项说明和往届赛事说明。统一从后台“公开内容与赛事设置”维护，保存后同步前台。
- 业务数据自动生成：实际报名队伍数、选手数、已完成场次、比分、晋级关系、赛程状态和裁判占用，应由报名、赛程和比赛执行模块产生，不在内容设置中重复手填。
- 页面结构固定：布局、字体层级、按钮样式和响应式规则属于产品设计，不作为日常赛事配置，避免后台退化为任意装修器。
- 当前本地版本将配置持久化在项目数据文件，并支持后台上传主视觉图片。上线多人使用前需要迁移到数据库或对象存储，并补充账号权限、修改记录和发布版本。
- AI 不参与必需的内容修改流程；未来可以提供文案建议、冲突检查或批量整理，但是否采用和发布始终由赛事负责人确认。
