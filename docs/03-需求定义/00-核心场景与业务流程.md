# 核心场景与业务流程

- 项目：《无畏契约》校园赛事 AI 排程协同助手
- 当前版本：1.1
- 文档状态：负责人已确认；按最小输入原则修订
- 日期：2026-08-16
- 本阶段目标：只确认一个高价值流程，确认后进入需求定义，不继续扩大研究

## 1. 核心场景

| 项目 | 当前定义 |
|---|---|
| 场景 | 已发布赛程后，一支队伍提出临时改期 |
| 主要用户 | 赛事总负责人或赛程负责人 |
| 协作角色 | 提出改期的队长、对手队长、裁判 |
| 触发 | 队伍因成员时间等原因无法按原时间参赛，两队先协商并提交一个双方认可的候选新时间 |
| 用户目标 | 在不破坏队伍、裁判、并发容量、赛制依赖和赛事进度的前提下完成调整 |
| 成功结果 | 负责人看到可解释的候选方案，批准其中一个；赛程形成新版本，受影响对象收到一致通知 |
| 不包含 | 自动判罚、自动同意改期、未经批准发布、完整报名平台、比赛实时管理 |

## 2. 主流程草案

| 步骤 | 责任角色 | 行为与结果 |
|---:|---|---|
| 1 | 队长/负责人 | 提交比赛 ID、改期原因、双方约定的新时间和两队确认状态；信息不完整时进入补充流程 |
| 2 | 系统 | 校验提交信息完整性，标记缺失或矛盾字段；改期申请为结构化提交，不解析自然语言 |
| 3 | 规则系统 | 读取当前有效赛程、比赛时长、该时段裁判容量、并发上限和前后置比赛；首版不维护完整队伍或个人裁判日历 |
| 4 | 规则系统 | 检查候选时间；若不可行，返回明确违反的约束和受影响对象 |
| 5 | 规则系统＋AI | 对双方已约定时间给出“可批准/存在冲突”；冲突时解释原因，并可展示赛程层面的空闲时段供双方重新协商，但不声称该时段双方一定可用 |
| 6 | 负责人 | 批准、修改或拒绝；系统不得代替负责人作出正式决定 |
| 7 | 系统 | 生成新的赛程版本、变更记录和受影响对象清单，保留上一版本以便回退 |
| 8 | 系统＋负责人 | 生成队伍与裁判通知；负责人确认后，通过最终选定的渠道发布 |

## 3. 每次改期必须检查的硬条件

1. 两支参赛队伍的队长已经确认同一个新时间。
2. 同一队伍不能同时参加其他比赛。
3. 新时间内的总并发不得超过该时段配置的裁判容量；首版不要求记录具体裁判姓名或个人日历。
4. 新时间不能早于决定参赛双方的前置比赛结束时间。
5. 比赛必须预留对应 BO1、BO3 或 BO5 时长。
6. 调整不能超过当前阶段截止时间，除非负责人明确批准例外。
7. 已冻结或明确不可移动的比赛不能被系统静默修改。

## 4. 最小异常流程

| 异常 | 系统处理 |
|---|---|
| 信息缺失或表达模糊 | 列出需要补充的问题，不进入排程 |
| 队伍给出的候选时间不可行 | 说明冲突原因，可展示赛程空档供双方重新协商，但不直接判定空档是双方可用时间 |
| 没有任何可满足方案 | 明确返回“不可满足”，列出必须放宽的条件，由负责人决定是否例外 |
| 临时事件来不及完整协商 | 仍执行最低冲突检查；负责人可使用人工紧急处理，但必须留下原因和版本记录 |
| 负责人拒绝所有方案 | 保留原赛程，记录拒绝原因，不发送变更通知 |

## 5. 产品承接深度的当前边界

试用期由排程工作台保存唯一、可追溯的有效赛程，并向腾讯文档或群通知导出。具体同步或连接方式尚未冻结。只要仍需负责人手工维护多份互相独立的赛程并从头检查冲突，就不算完成核心闭环。
