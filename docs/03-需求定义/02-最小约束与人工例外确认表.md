# 最小约束与人工例外确认表

- 项目：《无畏契约》校园赛事 AI 排程协同助手
- 当前版本：1.0
- 文档状态：已确认并冻结
- 日期：2026-08-16
- 当前范围：先验证两队已约定时间的改期校验；完整首版排程不在本轮约束确认中

## 1. 约束分类

- 硬约束：不满足时系统不能给出“可批准”。
- 软约束：尽量满足，但不满足时仍可由负责人批准。
- 人工例外：必须由负责人明确操作并记录原因；系统不能静默放宽。

## 2. P0 硬约束

| 编号 | 约束 | 不满足时 |
|---|---|---|
| HC-01 | 比赛存在，且申请基于当前有效赛程版本 | 要求刷新后重新提交 |
| HC-02 | 两队队长确认同一个约赛开始时间 | 保持待确认，不进入审批 |
| HC-03 | 系统能从 BO1/BO3/BO5 得到完整占用时长 | 拒绝校验并提示赛制数据缺失 |
| HC-04 | 参赛队伍在该时段没有其他比赛 | 判定冲突 |
| HC-05 | 后续比赛不能早于决定参赛方的前置比赛结束 | 判定冲突 |
| HC-06 | 整个比赛时段的并发场次数不超过裁判容量 | 判定冲突 |
| HC-07 | 约赛时间没有超出赛事阶段的起止范围 | 判定冲突；需先修改阶段配置才能重新校验 |
| HC-08 | 比赛未被冻结；冻结比赛必须先由负责人重新开放 | 拒绝直接改期 |

## 3. P0 软约束

| 编号 | 软约束 | 系统表现 |
|---|---|---|
| SC-01 | 尽量不移动其他已确认比赛 | P0 默认只检查当前约赛时间，不自动重排其他比赛 |
| SC-02 | 尽量在主办方推荐时段内比赛 | 超出推荐时段时警告，但可由负责人批准 |
| SC-03 | 尽量减少新版本影响的通知对象 | 展示受影响对象，不以此否决可行时间 |

## 4. 人工例外边界

| 情况 | 是否允许负责人例外 | 处理方式 |
|---|---|---|
| 超出推荐比赛时段，但仍在赛事阶段内 | 允许 | 记录理由后批准 |
| 超出赛事阶段结束时间 | 原则上不允许 | 必须先修改赛事阶段配置，再重新校验 |
| 并发超过裁判容量 | 不允许直接覆盖 | 先增加该时段容量，再重新校验 |
| 同一队伍比赛重叠 | 不允许直接覆盖 | 两队重新协商时间 |
| 前置比赛尚未结束 | 不允许直接覆盖 | 调整时间或先修改前置比赛 |
| 冻结比赛需要改期 | 允许重新开放 | 负责人填写原因，解除冻结后重新提交 |
| 旧版本上的改期申请 | 不允许直接覆盖 | 刷新到最新版本并重新计算 |

## 5. 负责人确认项

| 编号 | 决策 | 当前建议 | 负责人结论 |
|---|---|---|---|
| R1 | 默认最大并发场次 | 2 场，可由负责人按赛事实际资源修改 | 确认采用（2026-08-16） |
| R2 | 约赛时间与其他比赛冲突时 | 返回冲突，不自动移动其他比赛 | 确认采用（2026-08-16） |
| R3 | 超出推荐日常时段但仍在赛事期限内 | 允许负责人记录理由后批准 | 确认采用（2026-08-16） |
| R4 | 裁判容量不足时 | 不允许直接批准；先增加容量或重新约时间 | 确认采用（2026-08-16） |
| R5 | 冻结比赛需要改期时 | 负责人先填写原因并解除冻结，再走正常校验 | 确认采用（2026-08-16） |
