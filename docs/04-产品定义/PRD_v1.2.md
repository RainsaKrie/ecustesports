## 一、产品背景

### 1.1 现状

校园电竞赛事的组织工作高度依赖人工和碎片化工具。以某高校电竞社为例，一场 32 支队伍参加的无畏契约赛事，周期长达一个月，组织者需要使用 QQ群（沟通）、Excel（数据管理）、腾讯文档（文档协作）三套工具来回切换，流程割裂、效率低下。

### 1.2 痛点分析

| 环节 | 当前做法 | 痛点描述 | 痛点级别 |
|------|---------|---------|---------|
| 写策划案 | 翻旧文档手动改 | 每次办赛重复劳动，规则需要逐条修改 | 中 |
| 招人报名 | QQ群 + Excel | 选手抱怨报名不方便，信息容易遗漏 | 高 |
| 组队 + 赛事手册 | 手动编写 | 组队信息混乱，赛事手册每次重写 | 中 |
| 比赛进行中 | 裁判全手动操作 | 叫选手上场、记录比分、更新对阵图、处理争议、控制时间，一人多角 | 极高 |
| 赛后收尾 | 手动发社媒 | 奖品公示、写文案、收集反馈和返图，工作琐碎 | 中 |

### 1.3 市场机会

现有校园赛事管理工具要么功能过于通用（腾讯文档），要么面向专业赛事（成本高、上手难）。缺少一个专为校园赛事组织者设计的、AI 驱动的一站式赛事管理工具。本产品用 AI 解决策划、赛程、战报等重复性工作，用自动化工具解决报名、对阵图管理等流程性工作。

---

## 二、产品目标

### 2.1 核心目标

用 AI + 自动化工具将校园赛事从策划到收尾的全流程数字化，减少组织者的重复劳动，让一个人也能轻松办一场赛事。

### 2.2 衡量指标

| 维度 | 指标 | 目标值 |
|------|------|--------|
| 实际使用 | 电竞社使用本产品完整办一场赛事 | ≥ 1 场 |
| 效率提升 | 赛事策划到发布的时间 | 从 3 天降至 1 天 |
| 裁判减负 | 比赛进行中手动操作次数 | 减少 60% |
| 选手满意 | 报名流程满意度 | 4/5 以上 |
| AI 价值 | AI 生成内容（策划案/战报）被实际采用 | ≥ 80% |

## 三、目标用户

### 3.1 用户画像

**主要用户：赛事组织者（社长/干事）**

- 身份：高校电竞社负责人
- 特征：有赛事组织经验但缺乏专业工具，一个人干多个角色的活（策划、裁判、运营）
- 核心诉求：减少重复劳动，提高办赛效率，让赛事更专业

**次要用户：参赛选手**

- 身份：在校学生，游戏玩家
- 特征：通过手机/电脑查看赛程、报名参赛
- 核心诉求：报名方便、赛程清晰、及时收到比赛通知

### 3.2 用户角色与权限

| 角色 | 权限 | 典型操作 |
|------|------|---------|
| 组织者 | 赛事管理全部权限 | 创建赛事、审核报名、管理赛程、录入比分、生成战报 |
| 选手 | 参赛相关权限 | 报名参赛、组队、查看赛程、提交反馈 |
| 游客 | 只读 | 浏览赛事信息、查看赛程和结果 |

## 四、核心场景

### 场景一：从零策划一场赛事

组织者决定办一场无畏契约比赛，打开 AI 赛事运营助手，输入基本信息（游戏名称、预计队伍数 32、赛制偏好、比赛周期 1 个月），AI 生成赛制建议（单败淘汰/双败淘汰）、规则文档和奖品方案。组织者在 AI 初稿基础上修改确认，系统基于瓦理杯参赛手册模板结构自动生成选手赛事手册（赛制介绍→时间安排→单场流程→BP规则→文明参赛→应急处理→处罚规定→奖项设置）。

### 场景二：报名与组队

组织者发布赛事，在腾讯文档中创建报名问卷并关联到平台。选手通过分享链接填写报名信息，数据自动同步到平台。选手在平台内组队（队长创建队伍，邀请队员加入）。组织者在后台审核报名，查看队伍列表。报名截止后，系统自动锁定名单。

### 场景三：比赛进行中的赛程管理（核心场景）

> 解决"做裁判最痛苦"——叫人、记分、更新对阵图、处理争议、控制时间全手动

系统根据报名结果自动生成对阵图（支持单败和双败赛制）。对于固定时间槽的比赛，组织者在后台直接安排时间；对于自行约赛的比赛，两队队长在系统内协商时间，确认后自动更新赛程。比赛当天，双方先使用 BP 工具选图，BP 完成后系统自动通知裁判。组织者在后台录入比分，系统自动推进对阵图、更新下一轮对阵（双败赛中胜者组败者进入败者组），并通知下一轮参赛选手。选手在公开赛程页实时查看自己的比赛时间和对手。

### 场景四：赛后收尾

赛事结束后，组织者输入决赛比分和比赛亮点，AI 自动生成战报文章、朋友圈文案和社媒推文。系统展示最终排名和奖品公示。组织者向选手发送反馈表单和返图收集链接。海报由组织者自行制作。

## 五、功能清单（MVP）

### 5.1 痛点 → 功能映射

| 痛点 | 功能模块 | AI 角色 | 优先级 |
|------|---------|--------|--------|
| 写策划案翻旧文档 | F1. AI 赛事策划 | 生成赛制建议 + 规则文档 + 赛事手册 | P0 |
| 报名靠 QQ群 + Excel | F2. 在线报名 + 组队 | 无（功能型，接入腾讯文档问卷） | P0 |
| 裁判工作全手动 | F3. 赛程管理 + 对阵图自动化 | 自动生成对阵图 + 赛程推进 | P0 |
| 赛后写文案发社媒 | F4. AI 战报 + 社媒文案 | 生成战报 + 朋友圈文案 + 社媒推文 | P1 |
| 赛事管理全靠手动 | F5. 后台管理 | 无（功能型） | P0 |
| BP 靠线下口头/纸笔 | F6. 在线 BP 工具（地图 Ban/Pick） | 无（功能型） | P1 |

### 5.2 F1. AI 赛事策划

**功能描述**

组织者输入赛事基本信息，AI 生成完整的赛事策划方案，包括赛制建议、规则文档和选手手册。

**输入**

- 游戏名称（如：无畏契约）
- 预计参赛队伍数（如：32）
- 赛制偏好（单败/双败/循环）
- 比赛周期（如：1 个月）

**AI 输出**

- 赛制建议（推荐赛制 + 理由，含阶段划分如入围赛→小组赛→淘汰赛）
- 规则文档（比赛规则、违规处理、申诉流程、处罚规定）
- 奖品方案建议
- 选手赛事手册（基于瓦理杯参赛手册模板结构自动生成）

**参赛手册模板结构**（基于上一届瓦理杯参赛手册提炼）

1. 赛事介绍与赛制说明
2. 时间安排（报名期、比赛期、各阶段截止时间）
3. 单场比赛流程（签到→BP→比赛→报分）
4. BP 规则（地图 Ban/Pick 顺序、决胜图规则）
5. 文明参赛规范
6. 应急处理流程（弃权、迟到、掉线、争议处理）
7. 处罚规定（违规分级与对应处罚）
8. 奖项设置（冠军/亚军/四强/FMVP 等）

**需求描述（EARS）**

- 当组织者提交赛事基本信息时，系统应当调用 AI 生成赛制建议、规则文档和选手手册，并在 30 秒内返回结果。
- 组织者应当能够对 AI 生成的所有内容进行在线编辑和修改。
- 如果 AI 生成失败，则系统应当提示重试，并保留组织者已输入的信息。
- 系统应当支持保存历史赛事策划案，供后续赛事参考。
- 系统应当以瓦理杯参赛手册为模板基础，根据赛事参数（队伍数、赛制、时间范围、奖品）自动生成手册初稿。
- 在赛事状态为"策划中"时，系统应当允许组织者多次重新生成或修改策划案。

### 5.3 F2. 在线报名 + 组队

**功能描述**

替代 QQ群 + Excel 的报名方式，接入腾讯文档问卷收集报名信息，提供组队管理功能。组织者在腾讯文档中创建报名问卷，系统通过腾讯文档接口读取报名数据，在平台内完成组队和审核。

**报名流程**

1. 组织者在腾讯文档创建报名问卷 → 系统通过接口关联问卷数据
2. 选手通过分享链接填写报名信息（昵称、游戏 ID、联系方式）→ 数据自动进入腾讯文档表格
3. 系统读取表格数据 → 选手在平台内创建/加入队伍（队长创建队伍，生成邀请码）
4. 组织者在后台审核报名
5. 报名截止 → 系统自动锁定名单

**需求描述（EARS）**

- 当组织者发布赛事时，系统应当支持关联腾讯文档问卷链接，读取报名数据。
- 当选手通过腾讯文档问卷提交报名信息后，系统应当自动同步报名记录到平台。
- 选手在平台内创建队伍后，系统应当生成队伍邀请码，其他选手可通过邀请码加入。
- 当报名截止时间到达时，系统应当自动锁定报名名单，不再接受新报名。
- 如果队伍人数不足（无畏契约需 5 人），则系统应当标记该队伍为"人数不足"并提醒队长。
- 组织者应当能够在后台查看所有报名记录和队伍信息，并支持通过或拒绝报名。

### 5.4 F3. 赛程管理 + 对阵图自动化

**功能描述**

核心功能，解决裁判工作中的痛点。自动生成对阵图，比分录入后自动推进赛程并通知选手。

**功能点**

- 自动生成对阵图（MVP 支持单败淘汰 + 双败淘汰）
- 双败赛制自动维护胜者组/败者组对阵
- 比分录入后自动推进对阵图
- 自动通知下一轮参赛选手
- 公开赛程页实时更新
- 赛程时间表展示
- **约赛功能**（自行约赛场景）

**需求描述（EARS）**

- 当报名截止且名单确认后，系统应当根据参赛队伍数和赛制（单败/双败）自动生成对阵图。
- 当赛制为双败淘汰时，系统应当自动生成胜者组和败者组对阵图，并在败者组比赛中正确安排从胜者组淘汰的队伍。
- 当组织者录入某场比赛比分后，系统应当自动更新对阵图，将胜者推进到下一轮（双败赛中，胜者组败者进入败者组对应位置）。
- 当某场比赛的对阵确定后，系统应当自动通知相关参赛选手（站内通知）。
- 系统应当始终公开赛程页，供选手和游客查看实时赛程和结果。
- 如果比赛比分录入有误，则系统应当支持组织者修改比分，并自动重新计算后续对阵。
- 在比赛进行中，系统应当展示当前赛程进度（已完成/进行中/待开始）。
- 当赛事所有比赛完成后，系统应当自动标记赛事为"已结束"并展示最终排名。

**自动排程（赛程时间表自动生成）**

负责人不逐场排期，而是配置节奏参数，系统自动推算完整赛程时间表。

- 负责人配置节奏参数：每周比赛日（可多选）、每天开赛时段（可增删）、每场时长（BO1/BO3/BO5 分开）、开赛日期。
- 系统根据参赛队伍数 + 赛制结构 + 节奏参数，自动推算：每阶段场次数、每阶段所需周数、各阶段里程碑日期（入围赛/小组赛/淘汰赛结束日、决赛日）。
- 节奏参数在比赛中可随时调整，改动后系统自动重算赛程。
- 自动生成的赛程允许负责人人工微调（拖拽/改单场时间），微调走改期规则引擎校验。

**约赛功能（自行约赛场景）**

在部分比赛中，组织者不指定固定比赛时间，而是由两队自行协商。约赛功能将这一线下协调过程线上化。

- 当某场比赛的对阵确定且未指定固定时间时，系统应当允许两队队长在系统内发起约赛请求。
- 一方队长提出建议时间后，系统应当通知对方队长确认或提出反建议。
- 当双方就时间达成一致后，系统应当自动将该时间更新到赛程表，并通知组织者/裁判。
- 如果比赛截止时间前双方仍未达成一致，则系统应当提醒组织者介入协调。
- 系统应当为每场约赛设置截止时间，超时未完成的比赛应当标记为"待裁定"并通知组织者。

### 5.5 F4. AI 战报 + 社媒文案

**功能描述**

赛事结束后，AI 根据比分和亮点生成战报和社媒文案。海报由组织者自行制作，不在产品范围内。

**AI 输出**

- 赛事战报（比赛回顾文章）
- 朋友圈文案（短文本）
- 社媒推文（适合发布的格式）

**需求描述（EARS）**

- 当赛事结束后，系统应当根据比赛数据（比分、赛程）自动生成战报初稿。
- 组织者应当能够补充比赛亮点（如：关键操作、逆转场面），AI 将其融入战报。
- 系统应当同时生成朋友圈文案和社媒推文，供组织者直接复制使用。
- 如果组织者对生成内容不满意，则系统应当支持重新生成或手动编辑。

### 5.6 F5. 后台管理

**功能描述**

赛事管理后台，支持赛事增删改查、报名审核、权限管理。

**功能点**

- 赛事列表（按状态分类：策划中/报名中/进行中/已结束）
- 赛事创建/编辑/删除
- 报名审核
- 权限管理（组织者 vs 选手）

**需求描述（EARS）**

- 组织者应当能够在后台创建、编辑和删除赛事。
- 系统应当将赛事按状态分类展示（策划中/报名中/进行中/已结束）。
- 只有组织者角色才能访问后台管理功能，选手和游客无权限。
- 当赛事状态变更为"进行中"时，系统应当锁定赛事基本信息，不允许修改赛制和规则。
- 当赛事状态变更为"已结束"时，系统应当将赛事归档，不再接受任何修改。

### 5.7 F6. 在线 BP 工具（地图 Ban/Pick）

**功能描述**

为无畏契约等游戏提供在线地图 Ban/Pick 工具，替代线下口头/纸笔操作。不依赖游戏 API，仅提供在线交互界面，双方轮流选图。

**功能点**

- 展示当前游戏地图池（无畏契约默认 7 张地图）
- 双方轮流 Ban/Pick 地图
- 自动记录 Ban/Pick 顺序和结果
- 支持自定义 Ban/Pick 规则顺序
- 投屏友好，适合比赛现场展示
- **赛程关联**：BP 结果自动关联到对阵图上的对应比赛记录
- **BP 完成通知**：BP 完成后自动通知裁判"双方已 BP 完毕，比赛地图为 XX"
- **BP 历史记录**：赛后可回溯每场比赛的 BP 过程

**差异化说明**

与"掌上无畏契约"等独立 BP 工具相比，本产品 BP 工具的核心差异在于与赛程管理打通：
- BP 结果直接写入对阵图上的比赛数据，不再需要手动记录
- 裁判收到 BP 完成通知，知道何时可以开始比赛
- 赛后回溯：查看某场比赛的 BP 过程和最终选图，用于复盘和战报撰写

**需求描述（EARS）**

- 当比赛开始前，系统应当展示当前游戏的地图池（无畏契约默认 7 张地图）。
- 双方队伍应当轮流进行 Ban/Pick 操作，系统应当按预设顺序提示当前操作方。
- 当一方选择 Ban 或 Pick 某张地图时，系统应当实时更新地图状态（已Ban/已Pick/可选）。
- 系统应当支持组织者自定义 Ban/Pick 顺序（如：A ban → B ban → A pick → B pick → A ban → B ban → 决胜图）。
- 当 Ban/Pick 流程完成后，系统应当展示最终选图结果并记录到赛事数据中。
- 当 BP 流程完成后，系统应当自动通知裁判/组织者"双方已 BP 完毕，比赛地图为 XX"。
- 系统应当将 BP 结果关联到对阵图上对应的比赛记录，供赛后回溯查看。
- 如果操作方选错地图，则系统应当支持组织者回退上一步操作。

## 六、流程说明

### 6.1 办赛全流程

```
创建赛事 → AI 生成策划案（含参赛手册模板）→ 编辑确认 → 发布赛事
→ 选手报名组队（腾讯文档问卷）→ 审核报名 → 锁定名单
→ 自动生成对阵图（单败/双败）→ 约赛/固定时间 → BP 选图（关联赛程+通知裁判）
→ 比赛进行（录入比分 → 自动推进 → 通知选手）
→ 赛事结束 → AI 生成战报 → 发布结果 → 收集反馈
```

### 6.2 赛事状态流转

```
策划中 → 报名中 → 进行中 → 已结束
```

| 状态 | 进入条件 | 可执行操作 |
|------|---------|-----------|
| 策划中 | 创建赛事 | AI 生成策划案、编辑赛事信息 |
| 报名中 | 发布赛事 | 审核报名、管理队伍 |
| 进行中 | 锁定名单 | 录入比分、管理赛程 |
| 已结束 | 所有比赛完成 | 生成战报、收集反馈、查看结果 |

### 6.3 页面结构

| 页面 | 路径 | 访问权限 | 说明 |

## 八、已确认决策

| # | 问题 | 决策 | 理由 |
|---|------|------|------|
| 1 | BP 工具是否纳入 MVP？ | 纳入 MVP（F6） | 不依赖游戏数据，仅需在线 Ban/Pick 交互界面，无畏契约固定地图池即可 |
| 2 | 通知方式 | MVP 做站内通知 | 后续考虑接入微信/QQ 推送 |
| 3 | 选手注册登录 | 不做账号体系 | 报名内置到网站（直接存选手与队伍信息），降低使用门槛；「我的」参赛者个人中心留后续 |
| 4 | 双败赛制 | MVP 支持单败+双败 | 实际比赛使用双败赛制，仅做单败不够用。数据架构预留多阶段扩展 |
| 5 | 海报生成 | 不做 | 海报由组织者自行制作，F4 只保留文字内容（战报 + 文案） |
| 6 | 管理员鉴权 | 密码登录 + 会话 cookie | 后台与写接口统一保护，公开页面不受影响；默认密码上线前改为环境变量配置 |
| 7 | 导航信息架构 | 首页 / 赛事 / 工具 + 工作台靠右 | 赛事（对象）与详情（切片）非同级不并列；海报+历届只放首页，「赛事」直指详情页 |
| 8 | 阶段驱动 UI | 5 阶段自动判定 + 手动覆盖 | 筹备/报名/分组/比赛/赛后，主 CTA 与默认 tab 随阶段切换，不写死 |
