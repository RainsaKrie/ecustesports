# PRD v0.1：临时改期闭环

- 项目：《无畏契约》校园赛事 AI 排程协同助手
- 版本：v0.1
- 文档状态：已确认
- 日期：2026-08-17

## 1. 产品概述

### 1.1 背景

上一届瓦理杯真实事故：固定赛程发布后多支队伍不满，改为两队自行协商时间，临时改期时出现 3 场并发、裁判不足。核心痛点是：改期时负责人要人工反复核对赛程、容易漏查并发冲突、多处信息不一致。

### 1.2 定位

面向校园电竞赛事负责人的赛事运营工作区。P0（首个版本）聚焦「赛程发布后的临时改期闭环」，其余模块停留在框架层。

### 1.3 目标

两队协商出新的比赛时间后，负责人能快速判断能否批准；批准后形成唯一的新赛程版本并生成一致通知，避免人工反复核对、漏查冲突、信息不一致。

## 2. 目标用户与场景

| 角色 | 职责 |
|---|---|
| 赛事负责人（主要用户） | 审批、决策、处理例外 |
| 队长 | 提交改期、确认时间共识 |
| 裁判 | 接收通知 |

核心场景：已发布赛程后，一支队伍提出临时改期，两队先协商一个候选时间，负责人审批，赛程更新，通知到位。

## 3. 核心业务流程

```
队长提交改期申请 → 系统校验信息完整性 → 规则系统校验约束
   → 冲突时解释原因 → 负责人批准/驳回 → 批准生成新赛程版本 → 生成一致通知
```

### 异常处理

| 异常 | 系统处理 |
|---|---|
| 信息缺失或字段矛盾 | 列出需补充的问题，不进入排程 |
| 候选时间不可行 | 说明冲突原因，可展示赛程空档供双方重新协商，但不判定空档双方一定可用 |
| 无任何可满足方案 | 返回"不可满足"，列出需放宽的条件，由负责人决定是否例外 |
| 临时事件来不及完整协商 | 仍执行最低冲突检查；负责人可人工紧急处理，但须留原因和版本记录 |
| 负责人拒绝所有方案 | 保留原赛程，记录拒绝原因，不发送变更通知 |

## 4. 功能需求（7 个）

| 编号 | 功能 | 需求 |
|---|---|---|
| F01 | 当前赛程与版本管理 | 保存当前唯一有效版本，识别基于旧版本提交的申请 |
| F02 | 改期申请 | 录入比赛编号、双方约定时间、原因、双方确认状态 |
| F04 | 确定性约束校验 | 检查比赛状态、队伍时间重叠、前后置依赖、阶段范围、时段并发容量 |
| F05 | 冲突解释 | 指出违反的约束及受影响比赛；不静默放宽、不自动移动其他比赛 |
| F06 | 负责人审批与例外 | 批准/驳回；冻结比赛先解冻再校验 |
| F07 | 新版本与变更记录 | 每次批准生成新版本，保留旧版本、操作人、时间、理由，可恢复 |
| F08 | 一致通知 | 按同一版本生成给双方队伍、裁判、受影响对象的通知草稿 |

注：F03「AI 自然语言解析」已按 A2 决策移除；AI 价值体现在 F05 冲突解释与 F08 通知生成。

## 5. 数据模型

引用 `docs/03-需求定义/04-跨模块数据模型.md`（10 个对象：赛事、选手、队伍、比赛、赛制、规则、赛程版本、改期申请、审批决策、通知）。报名与队伍细节见 `docs/03-需求定义/05-报名与队伍.md`。

## 6. 验收标准（6 条）

| 编号 | 验收标准 | 通过条件 |
|---|---|---|
| AC-01 | 单次处理效率 | 提交双方已确认的改期到生成可审批结果 ≤ 1 分钟（不计协商时间） |
| AC-02 | 硬约束可靠性 | 10 可行 + 10 冲突案例不误判；冲突案例指出正确首要阻塞原因 |
| AC-03 | 审批前置完整性 | 旧版本申请、冻结比赛、缺双方确认的申请均不能直接进入批准 |
| AC-05 | 版本可追溯 | 每次批准生成新版本，旧版本和变更原因可查看、可恢复 |
| AC-06 | 通知一致性 | 同版本所有通知信息一致，覆盖全部受影响对象 |
| AC-07 | 完整闭环可用 | 负责人连续完成 3 个改期且无需另表手工复查硬约束 |

注：AC-04「AI 解析质量」已随 F03 移除。

## 7. 非功能需求

- **隐私**：选手姓名/学号/联系方式仅负责人可见，前台对阵页只显示游戏 ID。
- **权限**：审批、发布仅赛事负责人。
- **人工兜底**：任何自动建议不得直接对外发布，须经负责人确认。

## 8. 范围与暂缓

本轮暂缓：完整初始赛程自动生成、收集全部队伍可用日历、个人裁判日历与自动指派、报名/奖品/赛后验收等大而全功能。

外部工具连接：网站内置完成后，暂不考虑直连腾讯文档 / QQ / 微信；通知先以复制 / 导出方式人工触达。
