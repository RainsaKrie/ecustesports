# 赛果识别评测 · 首轮实测结论 v1

> 数据集：`result-vision-2026-10`（资格赛 4 + 入围赛 16，共 20 例，一张一场）
> 图片：18 张**手机拍屏**照片 + 2 张清晰截图；原图按隐私规矩不入库（`.gitignore` 排除 `images/`）
> 模型：deepseek-flash；提示词版本 v5 / v6 / v7

## 一、结论（先说结果）

**No-Go。** 但失败点非常集中，而且**不在提示词**：

| 指标 | 门槛 | 实测 | 判定 |
|---|---:|---:|---|
| 地图精确匹配 | ≥95% | **100%（20/20）** | ✅ |
| 单局比分精确匹配 | ≥95% | **100%（20/20）** | ✅ |
| 关键信息不足时不得猜测 | 0 次 | 0 次 | ✅ |
| 严重虚构事实 | 0 次 | 0 次 | ✅ |
| 可用预填比例 | ≥80% | 100% | ✅ |
| 可减少的手工字段 | ≥50% | 60% | ✅ |
| **胜方精确匹配** | ≥98% | **55%（11/20）** | ❌ |
| 昵称分组（逐名，诊断项） | ≥98% | 86%（172/200） | ❌ |

## 二、分层发现：问题只在「拍屏照片」上

| 图片类型 | 胜方正确 |
|---|---:|
| 清晰截图（png，n=2） | **2 / 2** |
| 手机拍屏（jpg，n=18） | **9 / 18（≈ 抛硬币）** |

**读图本身没问题**（地图、两个比分都 100%），问题在「顶部那两个比分数字分别属于哪一排颜色」——
提示词给的方法就是靠**数字的绿/红色与行底色对应**，而拍照的反光、斜拍、压缩恰恰最先毁掉这个色差。

## 三、三次调提示词，结果一模一样

| 版本 | 改动 | 结果 |
|---|---|---|
| v5 | 基线 | 55% / 86% / png 2/2、jpg 9/18 |
| v6 | 补「色差不可辨时改用『截图者自己那一行的高亮色』」 | **完全一致** |
| v7 | 补「两条线索都拿不到时**禁止猜**，必须声明不可确定」 | **完全一致**；20 例中**0 次**声明不可确定 |

→ **提示词不是瓶颈。** 模型在照片上拿不到线索时**不会交白卷，而是继续猜**（这是它的行为特性，
不是提示词能约束的）。这比"错"更值得警惕：系统若直接采信，就会给出**看起来正常但错的胜负**。

## 四、一项被数据推翻的指标设想（记录在此，避免重犯）

曾设想把 Gate 的必过项改成「队伍识别 + 比分 + 不猜测」，把逐名分组降为诊断项，
理由是"判队伍不需要每个昵称都对"。

**数据否掉了它**：两侧整体对调 **0/20**（说明模型认队伍确实没错），但**胜方仍错 45%**
—— 队伍对 ≠ 胜负对。按那个口径改，会把一个"会给裁判错胜负"的系统判成通过。
**所以 Gate 保持原样（胜方必须 ≥98%）。**

「判队伍不需要每个昵称都对」这个判断本身是对的，已体现在：逐名分组降为**诊断项**
（它不在必过项里），而两侧整体对调计数单独统计。

## 五、可执行结论

1. **AI 预填只对清晰截图成立**（直接截屏），**拍屏照片不能用于判定胜负**。
2. **系统侧必须自己设限**：不能指望模型声明"我不确定"（实测 0 次）。
   建议按图片类型分流 —— 照片类输入不给胜负预填，或强制人工确认。
3. **样本量仍不足**（门槛 ≥50：清晰 15 / 压缩 10 / 模糊 8 / 多局 8 / 昵称干扰 5 / 无效 4），
   本批 20 例只够跑通流程与校准标注规范。

## 六、局限（未验证的部分）

- 清晰截图只有 **2 例**，"2/2"只是信号，**不能当结论**。
- `truth` 的阵容按「首发」取，而**首发名单 ≠ 上场名单**（替补上场时会有 1–2 个昵称对不上）；
  这会影响逐名指标，但不影响"认队伍"（名册 7 人，对上任意 1–2 个即可定队）。
- 全部为 BO1（单局），多局（BO3/BO5）与「多局拼图」类样本尚未覆盖。
