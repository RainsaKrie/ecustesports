## 零、这份文档要你决定什么

现在后台的问题不是"某个按钮太丑"，是三件事同时发生：**颜色有 24 个来源、按钮没有统一的件、同一件事能从好几个地方点**。前两件让界面看起来乱，第三件让操作的人不知道该点哪个、点完不知道有没有生效。

本文给出三档处理办法，请你选一档：

| 档 | 做什么 | 得到什么 | 代价 |
|---|---|---|---|
| 只做收口 | 把颜色和按钮都换成统一的一套（视觉层），不动结构和流程 | 界面立刻变整齐，改动集中在 CSS + 少量组件 | 按钮数量不变、重复入口不变 |
| 收口 + 精简 | 在收口基础上，删掉重复入口、把次要按钮收进折叠区 | 界面上"可点的东西"明显变少，层级出来 | 需要逐页调整，且要你确认哪些入口可以砍 |
| 全套 | 再加一轮布局重排（页头工具条、面板结构、空态统一） | 达到"专业管理端"的观感与操作效率 | 改动面最大，需要分批验收 |

**建议从第二档开始**，理由在第七节。

## 一、外部规范收集：查了什么，哪些能直接用

收集了四份来源，都是能查到原文的公开规范，不是二手转述。

### 1. Ant Design — 按钮规范

原文里可直接落地的规则：

- 一个按钮区**最多一个主按钮**。次要操作收进右侧下拉。
- 按钮按主次排序，**折叠起来的内容永远排在最右**。
- 屏幕按钮过多时，**把相关动作编成组，并让同组按钮用相似的视觉**。
- 优先用**间距**分组，也可以用分割线。
- 按钮文案必须是**动词**，且描述结果（写"确认名单"，不写"确定"）。
- 底部固定工具栏不推荐滥用：只在"对象详情页推进状态"或"超复杂表单"两种场景用。

### 2. Carbon Design System — 数据表格

- 表格工具栏**最多放 5 个动作**，多的进 overflow 菜单。
- 行内动作**少于 3 项时保持内联图标按钮**（少一次点击）；超过再折叠。
- 批量操作栏在**选中之后**出现在表格顶部。
- 搜索默认收起，放在表格标题下方；排序放在列头。
- `overflowMenuOnHover` 这个选项**在移动端/触屏会被自动忽略**（强制常显）——也就是说，想靠 hover 藏按钮，手机上做不到。

### 3. NN/g — 渐进披露（Progressive Disclosure）

- 两种模式要分清：
  - **渐进披露**：初始只放核心功能，**多数用户不会进入下一层**。收益是**可学习性**。
  - **分步披露**：初始放"任务顺序上先用的那一步"，**用户必然会走完**。典型是向导。收益是**简单性**。
- 必须做对两件事：**初始层/次级层的切分要对**；**必须让用户明显看得出怎么进入下一层**（机制要简单，标签要给出明确预期）。
- 超过 **2 层**披露，可用性通常很差。
- 确定"初始层放什么"要靠**任务分析 + 实地观察 + 使用频次统计**；页面访问量高可能是误入，必须用观察式测试补充。

### 4. SaaS 管理后台综述（opendoordigital / redpiapps / designstudiouiux / createbytes）

- 顶部放**状态速览**：3–5 个关键指标，让人 2 秒内判断"是不是正常"。中部放趋势与上下文，底部放待办（在折叠之下可以接受）。
- **一个按钮区最多一个主按钮**（与 Ant Design 同一条原则）。
- 侧边栏顶层分区主流是 **5–15 个**；超过 15 要分组，超过 8 就该考虑侧边栏搜索——而"需要搜索框"本身就是信息架构该重做的信号。
- 列表行高建议 48–56px。
- 细节优先用**右侧抽屉**滑出，不要整页跳走。
- 每条列表都要设计"还没有内容"的空态，并给出**下一步动作**；空态要展示"填满后会是什么样" + 1–3 个具体动作 + 预计耗时。
- **用 toast 代替 alert**（"浏览器 alert 是 bug，不是功能"）。
- 危险/不可逆动作要**显式确认**。
- 快捷键：Esc 关弹窗，Cmd/Ctrl+K 聚焦搜索。

### 引用这些规范时必须带上的限制

上面四条里有三条的前提与本项目不同，不能照搬：

1. **"侧边栏 5–15 个分区"不适用**。本项目只有 3 个模块，这是对的——`工作台系统设计 v0.2` 已经把"赛事列表 / 三个模块"定死。不要为了凑数量往侧边栏塞东西。
2. **"一个按钮区最多一个主按钮"里的"一个按钮区"要自己定义**。本项目一个页面里有三个区域（页头工具条、面板标题栏、行内），这三个是三个区，各自一个主按钮，是可以的。真正的病是同一个区里有两三个红色按钮。
3. **"渐进披露"的收益是"可学习性"，不是"减少点击"**。所以把按钮藏起来会让老手变慢。本项目的负责人是固定的一两个人、要反复用，**折叠只适用于低频操作，高频操作必须留在外面**。这是本文与通用建议最大的一处分歧，第五节会逐条落到具体按钮上。

## 二、现有问题：分成三类

以下数字都是本轮在代码里实测的（28 个管理端文件），不是估计。

### A 类 · 视觉层：乱从哪来

**A1 颜色有 24 个来源，而设计令牌只定义了 9 个。**

`globals.css` 里定义了 9 个令牌（`--paper` `--paper-deep` `--ink` `--ink-soft` `--muted` `--line` `--red` `--red-dark` `--white`）。但管理端代码里硬编码了 24 个色值，含义互相重叠：

| 语义 | 令牌值 | 实际在用的值 | 个数 |
|---|---|---|---|
| 品牌红 | `#ff4655` `#d83b48` | `#ff4655` `#c83242` `#d83b48` `#d93746` `#9f2431` `#ff6572` `#d9a6aa` | 7 |
| 深色 | `#0f1923` `#25313b` | `#171a1f` `#34383f` `#34383e` `#0f1923` `#25313b` `#101820` `#575c62` | 7 |
| 浅底 | `--paper` `--white` | `#fff1f2` `#fffdf8` `#fff7f7` `#f2eee6` `#f8f6f1` `#fff7f6` `#f3f0e9` `#d8d1c6` `#a39d94` | 9 |

同一个"品牌红"有 7 种深浅，本身不一定错（hover 态、浅底强调确实需要不同深浅）——错在**它们是散落的一次性色值，不是一套有名字的阶**。所以换一次主题要改 24 处，且没人知道 `#d93746` 和 `#d83b48` 差在哪。

**A2 按钮没有统一的"件"。**

- 含 `#ff4655` 的 `className` 有 **123 种不同写法**，共出现 158 次。也就是几乎每个按钮都是手写的。
- `src/components/ui/Button.tsx`（有切角、5 种 variant、4 种 size）在管理端**引用 0 次**——它只服务首页和玩家侧 4 个页面。
- 次按钮（`border border-slate-300...` 那一类）有 **42 种不同写法**。
- `ui/Card` 管理端引用 0 次。

**A3 危险操作有三种长相。** 同一件事"删除"：报名页删选手是**红色纯文字按钮**；赛事设置删规则是**红边描边按钮**；赛事设置删整届赛事是**红色区块 + 要求输入全名**。而同一页上语义更重的"重置凭证"反而是中性灰按钮。

**A4 原生弹窗和自定义弹窗并存。** `window.confirm` 10 处、`window.alert` 2 处，分布在侧边栏、赛事设置、裁判管理、赛程页、BP 房间。其余确认走的是自定义 `Modal`。结果是：有的确认框长得跟站点一样，有的是浏览器原生灰框。

明细：侧边栏 1、赛事设置 2、裁判管理 3、赛程页 3、BP 房间 1（confirm）；赛程页另有 2 处 alert。

**A5 小字号密集。** 桌面端根字号 24px，`0.45rem` = 10.8px、`0.5rem` = 12px、`0.5625rem` = 13.5px，这些值被大量用于标签、编号、meta 文字。10.8px 在 1080p 屏上看是吃力的。移动端根字号降到 16px，同一个 `0.5rem` 只剩 8px——**手机上基本读不了**。

### B 类 · 结构层：按钮为什么这么多

**B1 单页按钮数量。** 计入 `<button>` 元素：

| 页面 / 组件 | 按钮数 | 输入控件 | 行数 |
|---|---|---|---|
| 报名与队伍 | 47 | 40 | 932 |
| 赛事设置 | 27 | 22 | 577 |
| 赛程页 | 20 | 10 | 611 |
| 报名与队伍子页（format draw） | 14 | 1 | 834 |
| 评审批次 | 9 | 5 | 430 |
| 裁判管理 | 7 | 4 | 316 |
| 官网内容 | 2 | 2 | 137 |

工作台内合计约 **127 个按钮**。对照 Carbon 的"工具栏最多 5 个动作"，单页 47 个按钮是数量级上的过量。

**B2 同一件事有多个入口。** 逐条核对过，确实存在的是这几组：

| 这件事 | 入口 1 | 入口 2 | 是否同一件事 |
|---|---|---|---|
| 刷新数据 | 页头工具条 | 约赛审批标题栏 | 是，同一个 `refresh()` |
| 给比赛排期 | 对阵图面板「排期」 | 约赛审批「按此时间排期」 | 是，同一个目标 |
| 改比赛时间 | 面板「负责人调整」 | 约赛审批批准 | 是 |
| 确认满编名单 | 报名页「一键确认满编队伍」 | 侧边栏 CTA「结束报名并进入分组」 | 是 |
| 抽签 | 侧边栏 CTA | 赛程页「开始抽签」 | 是，同一目标 |
| 归档/重置 | 赛事级 `archiveEvent` | 赛程级 `reset()` | 否，语义不同，**不要合并** |

**B3 弹窗种类多。** 报名页有 13 种弹窗（编辑选手 / 删除选手 / 建队 / 分配选手 / 移出选手 / 重开队伍 / 换人 / 退赛 / 解散 / 改名 / 改角色 / 建选手 / 确认），赛程页有 4 种模式（总览 / 排期 / 改期 / 报分）。

**B4 三个区域都能触发同一动作。** 页头工具条、面板标题栏、行内图标——三者视觉权重接近（都是小按钮），但职责应该是"全局 / 区块 / 单条"。

### C 类 · 交互层：点下去会怎样

**C1 同一个字段的两个入口，提示不一致。** 赛事简介（`description`）在后端**已经统一**——`/api/admin/events` 和 `/api/admin/site-content` 都调用 `site-content-limits.ts` 的 `eventDescriptionIssue()`，规则是 10–280 字，不合规返回 400 并在界面上显示"首页赛事简介应为 10—280 字（当前 N 字）"。

问题只在**界面提示**：官网内容页的输入框有 `maxLength={280}`，赛事设置页的输入框**既没有 `maxLength` 也没有字数提示**。用户在两处遇到的不是同一件事——一处写不进去，一处写进去再被弹回来。规则一致、反馈不一致。

**C2 缺批量。** 按场次逐个操作（如裁判分配）在大规模下是 N 次点击。是否值得加批量，取决于第七节的判断，见第八节。

**C3 反馈形式不统一。** 有 toast、有 alert、有内联红字、有按钮 disabled，没有统一约定。

## 三、设计目标与原则

### 沿用（`工作台系统设计 v0.2` 已确认的四条，不动）

删解释性文案、删重复、保持边界、操作直觉化。

### 本次新增三条（针对"乱"）

1. **一个字段一个来源，一种表达。** 颜色、间距、按钮样式、确认框，全部只用一套定义。规则可以有多条，表达只能有一种。
2. **一个动作一个入口。** 同一件事只留一个可点的位置；其他位置只显示状态，不重复给按钮。例外：全局刷新可以多处存在，因为它是无副作用的读操作。
3. **层级靠位置，不靠颜色。** 主次区分用"放在哪、排第几、前面有没有分割线"，而不是"用多红的红"。红色只表示"这是本区的主要动作"或"危险"，不当装饰用。

### 明确不做

- 不引入新配色、新装饰、圆角、阴影（守 `UI设计规格` 第一节与第七节）。
- 不改信息架构（3 模块 + 侧边栏生命周期条不动）。
- 不为"减少按钮"把低频但救命的操作删掉（见第四节"必须留"清单）。

## 四、布局与信息层级优化方案

### 4.1 页面骨架固定成三段

每个工作区页面统一为：

```
[ 页头 ]  标题 + 状态徽标 + 一句话说明        右：本页唯一主按钮 + 更多(⋯)
[ 上下文条 ]  当前阶段 / 关键数字（3–5 个）    不做成卡片，做成一行文字
[ 主体 ]  一个主视图（对阵图 / 队伍列表 / 设置分组）
```

对照现状：页头已存在（`AdminPageHeader`，含 eyebrow / title / description / status / actions），但 `actions` 里有时放两三个平级按钮，且"更多"区不存在。要补的是**"溢出区"**：把不常点的动作统一收进页头右侧一个 `⋯`，而不是散在页头、面板、行内三处。

### 4.2 上下文条改为一行数字，不做卡片

现在关键数字散在各面板标题里。改为页头下方一行：报名页显示"已报名 N 队 / 满编 M 队 / 待确认 K 队"，赛程页显示"未排期 N 场 / 待报分 M 场"。

规则：**最多 5 个数字**，超出的不显示（Carbon 的工具栏上限同源）。数字只读，不可点——**要点的话说明它在这页不是"速览"而是"入口"，应该做成按钮而不是数字。**

### 4.3 主体区"一个视图 + 一个工具栏"

- 对阵图页：主视图就是对阵画布；工具栏固定在画布上方，**最多 5 个动作**，其余进 `⋯`。
- 报名页：主视图是队伍列表（选手/队伍 tab 切换，已在 v0.2 定义）；工具栏同理。
- 设置页：主视图是左"分组导航 + 右表单"两栏，分组导航现在已有（04/PUBLIC PAGE 那种卡片按钮），改为**左侧竖列**，右侧只显示选中分组，避免五个分组卡片同时占据视觉。

### 4.4 移动端策略写死

根字号 `760px` 以下降到 16px，`0.5rem` = 8px 已经不可读。约定：

- 移动端**不缩小字号**，改为**减少一屏信息**：上下文条隐藏、工具栏只留主按钮 + `⋯`。
- 侧边栏已有 `<details>` 折叠，保留。
- 明细表格在移动端改为纵向卡片（Carbon 的响应式表格做法），不做横向滚动。

## 五、按钮与选项的精简及归类策略

### 5.1 建立按钮唯一来源

新增一个管理端按钮组件，**从 `ui/Button` 抽出来但视觉不同**（管理端不是切角海报语言，是工具语言）。定义五个层级，其余一律不许手写：

| 层级 | 用途 | 视觉 | 每区数量上限 |
|---|---|---|---|
| primary | 本区主要动作 | 实心品牌红 | 1 |
| secondary | 常规动作 | 白底 + 墨色细边 | 不限，但同区 ≤ 2 个 |
| ghost | 行内动作 | 无底色，hover 出底 | 不限 |
| danger | 破坏性动作 | 红字/红边，**必须带确认** | 1 |
| link | 跳转 | 下划线文字 | 不限 |

原 `ui/Button` 的切角只用于首页与玩家侧，管理端不继承——这与 `UI设计规格` 第七节"后台保持工具感"一致。

> **实现注记（2026-10-08）**
>
> 「唯一来源」最终落在 **CSS 组件类**上，而不是 React 组件：`.adm-btn` 加五个层级修饰类，
> 定义在 `globals.css` 的 `@layer components` 里；调用点直接写
> `className="adm-btn adm-btn--primary adm-btn--md"`。两个原因：一是 Tailwind v4 里
> 未分层 CSS 的优先级高于所有 `@layer`，样式集中一处更好控；二是后台大量调用点需要附加
> 位置类（`w-full` / `mt-4` / `shrink-0` / `border-dashed`），直写类名比传 props 更短。
>
> 三个尺寸档是 **px 定值**，不是 rem：`sm` / `md` / `lg` = 32 / 44 / 52px。原因是桌面根字号
> 被设为 150%（24px），而 Tailwind 的高度类走 rem —— 同一个控件在桌面比移动端高一倍，
> 字号却已经是 px 定值，两边对不上。**表单控件（输入框、下拉）的高度也对齐到 `md` 档的
> 44px**，与同排按钮齐平。
>
> React 包装组件只保留**有真实调用点**的 `AdminButton`（确认弹窗在用）。
> `StatusPill` / `StatusNote` / `Toolbar` 建好后全仓库零引用，已删除 —— 留着会形成
> 「CSS 类 + React 组件」两套并行实现，后续每次改动都要先判断哪一套是唯一来源。

### 5.2 同一动作只留一个入口

按第二节 B2 的表逐条处理：

| 现状 | 处理 |
|---|---|
| 刷新 ×2 | 保留页头一个；约赛审批标题栏的删掉（面板内不再放刷新） |
| 排期 ×2 | 保留对阵图面板「排期」；约赛审批里的改为纯状态显示 + 一个「去排期」跳转（跳回面板） |
| 改期 ×2 | 保留一处，另一处改为"查看改动"，不重复给按钮 |
| 确认名单 ×2 | 保留报名页「一键确认满编队伍」；侧边栏 CTA 文案改为指向它（或直接触发同一个动作，只保留一个可点面） |
| 抽签 ×2 | 保留赛程页「开始抽签」；侧边栏 CTA 改为跳转 |
| 归档 / 重置 | **不合并**，两个是不同的事，但要在文案上写清区别（"归档本届（保留数据）" vs "重置赛程（清空赛程）"） |

原则：**状态可以多处显示，动作只留一处。

### 5.3 按频率决定"留外面还是收起来"

这一条与通用建议不同：本项目用户固定，所以按**每届用几次**来分：

**每届必用（留在外面）**：抽签、排期、报分、确认名单、发布/撤回、导出名单。

**每届数次（进 `⋯` 溢出区）**：重置赛程、归档、清空 BP、批量改期。

**极低频但必须留（进设置深层，且保留确认框）**：解散队伍、退赛、删除选手、永久删除赛事、重置凭证。理由见下。

### 5.4 极低频 ≠ 该删：这些不能动

| 操作 | 为什么必须留 |
|---|---|
| 退赛 / 解散 / 删除选手 | 出事的唯一退路，删了就把"可恢复"变"不可恢复" |
| 永久删除赛事 | 误建赛事的唯一清理手段，且已有"输入全名"双确认 |
| 重置凭证 | 队长丢码时唯一补救 |
| 赛程 `reset()` | 赛程整体作废重来 |

这些可以**藏得更深**，但不能删。

## 六、组件与交互规范建议

### 6.1 颜色：把 24 个收到一套阶

不改令牌本身（`UI设计规格` 已定 9 个），而是**为管理端补一组有名字的派生阶**，写在 `globals.css` 里：

```
--red       品牌红（主按钮、强调）
--red-dark  hover / 深一档
--red-soft  浅底红（#fff1f2 这一档，用于提醒条）
--red-deep  深红文字（#9f2431 这一档，用于浅底上的字）
--ink / --ink-soft / --muted / --line / --paper / --white  沿用
--ink-90 / --ink-70 / --ink-50  文字层级（替代 #171a1f/#34383f/#575c62）
--surface   #fffdf8（白卡）
--surface-2 #f8f6f1（次一级底）
```

然后**逐个替换**——这是一次机械替换，风险低、收益直接。替换完，`#c83242` `#d93746` `#9f2431` 这类一次性色值应清零。

### 6.2 按钮：见 5.1

### 6.3 确认框：全部改用同一套

- 删掉 10 处 `window.confirm` 与 2 处 `window.alert`，统一走自定义 `Modal`。
- 分级：
  - 普通确认（撤销、清空某区域）→ 单按钮弹窗。
  - 破坏性确认（删除、解散、退赛、永久删除）→ 必须"说出后果 + 按钮是红的 + 文案写动作结果"。
  - 永久删除赛事 → 保留现有的"输入全名"。
- 需要填原因的操作（现有的审计约定）→ 确认框里带原因输入，**不要为了统一而把这个要求删掉**。

### 6.4 反馈：统一成三件

- **成功** → 右上角 toast，3 秒消失。
- **失败** → toast（红色）+ 保留内联红字（用在表单字段旁）。
- **进行中** → 按钮内转圈 + disabled，不用 alert。

### 6.5 空态：每条列表都要有

现在不少列表"没数据就是一片空白"。补三样：一句说明（"还没有队伍报名"）+ 一个动作（"复制报名链接"）+ 预期（"报名开放后会自动出现"）。

### 6.6 表格与列表

- 行高 ≥ 48px。
- 排序放列头，不单独做排序按钮。
- 行内动作 ≤ 2 个图标，多出来的收进行尾 `⋯`（Carbon 的 "少于 3 项保持内联"）。
- 选中后顶部出现批量操作条。

### 6.7 快捷键

Esc 关弹窗、Cmd/Ctrl+K 聚焦搜索。属于加分项，放最后做。

## 七、优先级与推进步骤

### 判断哪个先做

按"改一处、影响多大"排，不按"哪个显眼"排。

**先做的是"颜色收敛 + 按钮组件"**，因为后面所有页面调整都要用这两个件。如果先调布局、后做组件，布局改完还得再改一遍按钮。

**真正会先咬人的是"同一动作多入口"**——不是它最难改，是它最容易出事：负责人在 A 处操作后，B 处显示的还是旧状态，他会以为没生效，于是重复点一遍。

### 分四批

**第一批 · 打基础（不动页面结构）**
1. 补管理端颜色派生阶，替换 24 个散落色值。
2. 建管理端按钮组件（五个层级）。
3. 统一确认框（消掉 12 处原生弹窗）。
4. 统一反馈（toast）。

做完这批，界面会明显整齐，但按钮数量和入口没变。

**第二批 · 精简入口（逐页）**
5. 处理第二节 B2 的重复入口表。
6. 每页新增 `⋯` 溢出区，低频动作收入。
7. 页头上下文条（每页最多 5 个数字）。

**第三批 · 布局与结构**
8. 设置页改左右两栏。
9. 移动端策略落地（不减字号、减信息）。
10. 空态补齐。

**第四批 · 打磨**
11. 快捷键、表格行高/排序/批量、抽屉替代整页跳转。

### 每批的验收

- 不改任何后端接口与数据。
- 每批做完跑一次 `npm run gate`（lint + 类型检查 + 全部测试 + 构建）。
- 界面改完需要你在浏览器里看（我没有管理员口令，进不了 `/admin`，**改完我只能静态校验，不能替你点**）。
