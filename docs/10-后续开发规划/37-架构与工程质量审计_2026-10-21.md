# 架构与工程质量审计（2026-10-21）

> 范围：`src/` 全部代码（233 文件 / 约 1.9 万行 TS+TSX）。
> 方法：**先测量再判断** —— 所有结论都附可复现的检查命令，不是凭印象。

## 一、结论

**分层与安全没有硬伤，问题集中在"异常边界"和"超大文件"。**

| 维度 | 实测结果 | 判定 |
|---|---|---|
| 分层违规（lib→components/app） | **0 处** | ✅ 干净 |
| 分层违规（domains→上层） | **0 处** | ✅ 干净 |
| 客户端组件直连 Supabase | **0 处** | ✅ 干净（全走 API Route） |
| 硬编码密钥 / token | **0 处** | ✅ 干净 |
| API 路由统一错误出口 | **0 / 35** | ❌ **缺失** |
| 路由缺 try/catch | **12 / 35** | ⚠️ **其中含核心写操作** |
| >800 行的文件 | **4 个** | ⚠️ 维护成本高 |

---

## 二、问题清单（按严重程度）

### P1 · 裁判端核心写操作没有异常边界（严重）

**实测**：35 个 `route.ts` 中 23 个有 `try/catch`，**12 个没有**，且**没有任何统一的错误响应出口**。

**缺的这 12 个里，包含最关键的写操作**：

| 路由 | 方法 | 说明 |
|---|---|---|
| `referee/submit` | POST | **提交赛果** —— 裁判报分的核心 |
| `referee/upload` | POST | 上传赛果截图 |
| `referee/claim` | GET/POST | 抢单 / 释放 |
| `referee/recognize` | POST | 识别 |
| `referee/login` | POST | 登入 |

**风险**：领域函数 `refereeSubmit` 遇到数据库不可达、网络错误等**非业务异常**时会抛出。
路由没有 `catch`，异常冒到 Next 运行时 → 返回 **HTML 格式的 500**，而不是 JSON。

前端（`useSchedule` 等）拿到响应第一件事是 `.json()`，**对 HTML 解析会再次抛错**，
于是界面上看到的是"未知错误"甚至白屏，**而不是"服务暂时不可用，请重试"**。

在比赛现场、裁判正要点提交的那一刻，这个差别很实际。

**另一层风险**：12 个路由的错误响应形状各不相同（有的 `{message}`、有的裸文本、有的 Next 默认），
客户端无法统一处理。

### P2 · 4 个文件超过 800 行（中）

| 文件 | 行数 |
|---|---|
| `components/admin/FormatDrawWorkspace.tsx` | 980 |
| `app/admin/events/[id]/schedule/page.tsx` | 895 |
| `app/referee/RefereeWorkbench.tsx` | 875 |
| `lib/domains/schedule/schedule-ops.ts` | 825 |

**风险**：这几处是"改一处要想半天"的地方。本阶段已有多个文件被架构守卫锁行（只许变短），
说明问题已经被机制承认，但**没有拆**。

**注意**：`schedule-ops.ts` 是**纯领域逻辑**（825 行），拆它的收益最大、风险最小 ——
它没有 JSX、没有 `"use client"`，可以按"赛程读取 / 写入 / 校验"切开。

### P3 · 纯规则与展示混在一起（中，已治理一部分）

本阶段已把分组逻辑从客户端组件抽到 `lib/domains/schedule/group-standings.ts` 并加了测试。
**同类未治理的还有**：赛程页的阶段/统计计算（在 `PublicSchedule.tsx` 里）。

### P4 · 测试覆盖偏科（中）

47 套测试覆盖了规则、守卫、构建、CSS、文档一致性，**但没有一层覆盖 API 路由的路由层行为**
（鉴权、参数校验、错误状态码）。`test:route-guards` 是静态检查，不是行为测试。

## 三、优化方案与优先级

| 优先级 | 改动 | 收益 | 风险 | 验证 |
|---|---|---|---|---|
| **P1-a** | 新增 `lib/api-error.ts`：`withApiError()` 包装器 + 统一 `{ok:false,message}` 形状 | 异常一律转成 JSON 4xx/5xx，客户端不再解析到 HTML | 低（新增文件 + 逐路由套壳） | 构造抛异常的假 handler，断言返回 JSON 且状态码正确 |
| **P1-b** | 给 12 个路由套上包装器 | 同上，覆盖全部 | 中（逐个改，需核对签名差异） | 全部路由跑一遍 200/400/500 路径 |
| **P2** | 拆 `schedule-ops.ts`（825 行纯逻辑） | 单文件职责清晰、可测性提升 | 中（拆分要保证导出一致） | 拆后 `test:scheduling` 等既有套件必须全绿 |
| **P3** | 把 `PublicSchedule` 的统计计算抽到 lib + 加测试 | 与分组逻辑同样收益 | 低 | 新增断言 + 变异验证 |
| **P4** | 给 3 条核心路由加行为测试（submit / claim / upload） | 路由层首次被覆盖 | 低 | 直接起 dev server 打接口 |

**实施顺序**：P1-a → P1-b → P3 → P2 → P4。
**理由**：P1 是"出问题时会掩盖真相"的那种缺陷；P3 成本最低；P2 风险最高放后面。

## 五、明确不动的地方

| 项 | 为什么不动 |
|---|---|
| `max-w-2xl` 等 10 处命名尺寸 | 是段落文字宽度上限，宽一点无害；只有弹窗那种**固定容器**才需要改 |
| `pub-theme.css` 的选择器分层 | 已合并 18 条重复规则；再拆要逐条比对生效值，风险高于收益 |
| 4 个大文件里带 `"use client"` 的 3 个 | 拆分要动 JSX 结构，当前没有回归手段（无无头浏览器），**改坏了发现不了** |
