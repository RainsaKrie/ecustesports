# 裁判报分基础设施工作包 v1.0

- 轨道：B
- 目标：建立不依赖 AI 也能完整使用的裁判报分、凭证、异常处理和恢复闭环
- 产品原则：裁判提交，规则校验，异常由管理员处理，AI 永不自动提交
- 上线原则：默认关闭，完整验收后再由发布负责人开启

## 1. 最小产品边界

首期只支持以下闭环：

1. 管理员建立裁判身份并分配比赛；
2. 裁判查看自己的待执裁比赛；
3. 裁判手工填写地图和逐局比分，并上传凭证；
4. 系统进行确定性规则校验；
5. 普通合法结果由裁判确认后生效；
6. 异常、修改、关键场次进入管理员队列；
7. 正式赛果、原始提交和操作历史可以追溯；
8. 出错时能够安全恢复或明确阻止自动恢复。

首期不包含 AI、聊天、作弊判断、选手身份识别、自动处罚和通用裁判排班系统。

## 2. RPT-00：领域设计与 ADR

### 目标

在任何实现前冻结角色、状态、对象关系、权限和恢复边界，避免不同 AI 各自发明一套流程。

### 必须做出的产品决策

1. 裁判身份采用什么形式；
2. 一场比赛允许一名还是多名裁判；
3. 普通比赛是否由裁判提交后直接生效；
4. 哪些比赛必须管理员复核；
5. 已生效赛果在什么条件下可以自动撤销；
6. 下游比赛已经 BP、排期或完赛时如何处理上游赛果修改；
7. 队长申诉入口是否纳入首期；
8. 截图保存期限和访问人；
9. 裁判凭证的有效期、撤销和遗失处理；
10. 功能开关的默认值和启用范围。

### 建议对象

#### RefereeIdentity

- `id`
- `eventId`
- `displayName`
- `status`: active / disabled
- `credentialHash`
- `credentialExpiresAt`
- `createdAt`
- `disabledAt`

#### MatchAssignment

- `id`
- `eventId`
- `matchId`
- `refereeId`
- `status`: assigned / revoked / completed
- `assignedBy`
- `assignedAt`
- `revokedAt`

#### ResultSubmission

- `id`
- `eventId`
- `matchId`
- `submittedByRefereeId`
- `basedOnScheduleVersion`
- `games`
- `declaredWinnerTeamId`
- `evidenceIds`
- `source`: manual / ai-assisted
- `status`: draft / submitted / needs-review / accepted / rejected / superseded
- `submittedAt`
- `resolvedAt`
- `resolutionReason`

#### MatchEvidence

- `id`
- `eventId`
- `matchId`
- `submissionId`
- `objectPath`
- `mimeType`
- `sizeBytes`
- `sha256`
- `uploadedByRefereeId`
- `createdAt`
- `expiresAt`

#### ResultDecision

- `id`
- `submissionId`
- `decision`: accept / reject / supersede / revert
- `actorType`
- `actorId`
- `reason`
- `beforeResultVersion`
- `afterResultVersion`
- `createdAt`

### 建议状态机

```text
draft
  └─ 裁判提交 ─→ submitted
                    ├─ 规则一致、非强制复核 ─→ accepted
                    ├─ 异常/关键场次 ───────→ needs-review
                    └─ 状态已过期 ─────────→ rejected

needs-review
  ├─ 管理员确认 ─→ accepted
  └─ 管理员驳回 ─→ rejected

accepted
  ├─ 新提交替代 ─→ superseded
  └─ 安全撤销 ───→ superseded / reverted decision
```

`accepted` 之后禁止原地修改。更正必须形成新提交和新决策。

### 交付物

- 一份 ADR；
- 对象与字段定义；
- 状态机；
- 权限矩阵；
- 下游恢复决策表；
- API 草案；
- 功能开关方案。

### 完成定义

- 产品负责人逐项确认上述十个决策；
- 后续 AI 只能实现冻结合同，不得自行修改流程。

## 3. RPT-01：赛果状态机、确认与恢复纯函数

### 目标

先在无 UI、无数据库、无模型的情况下证明赛果状态和晋级更新正确。

### 工作内容

1. 新建独立赛果领域类型和纯函数，不把全部逻辑继续堆入页面。
2. 复用现有 `validateGames`，但补充队伍、地图、重复提交和版本校验。
3. 区分候选提交与正式赛果。
4. 只有接受决策能够调用正式赛果更新。
5. 为幂等提交设计稳定的 request/submission ID。
6. 定义上游赛果更正对下游比赛的安全矩阵。
7. 在无下游进度时支持可测试的重新计算；存在下游进度时必须阻止自动覆盖并返回明确风险。
8. 正式结果变更必须产生新版本或决策记录。

### 下游恢复最小矩阵

| 下游状态 | 上游结果更正处理 |
|---|---|
| 后续对阵仅有占位队伍，未排期 | 允许重新填充队伍 |
| 后续已排期但未 BP | 阻止自动生效或要求管理员明确确认并重新校验排期 |
| 后续 BP 已开始/完成 | 禁止自动覆盖，进入人工恢复 |
| 后续已报分或继续晋级 | 禁止自动覆盖，生成受影响比赛清单 |
| 赛事已结束/归档 | 只允许受控更正流程，不自动重放整届赛事 |

### 建议修改范围

- 新建 `src/lib/scheduling/result-*` 领域文件；
- 最小修改 `schedule-data.ts` 和 `schedule-ops.ts`；
- 新建专用纯函数测试。

### 禁止

- 不修改 UI；
- 不接入 Supabase；
- 不引入 AI SDK；
- 不用 `any` 绕过状态类型；
- 不为了通过测试删除现有比赛校验。

### 必测案例

- [ ] BO1/BO3/BO5 合法结果；
- [ ] 平局、局数不足、局数超限；
- [ ] 比赛不存在或版本过期；
- [ ] 裁判未分配；
- [ ] 同一提交重复发送保持幂等；
- [ ] 同一比赛两条结果相同；
- [ ] 同一比赛两条结果冲突；
- [ ] 普通合法结果接受；
- [ ] 强制复核场次进入审核；
- [ ] 无下游进度时安全更正；
- [ ] 下游已 BP 或完赛时阻止自动更正；
- [ ] 接受后晋级双方和去向正确；
- [ ] 撤销失败不会留下半更新状态。

## 4. RPT-02：裁判身份、凭证与比赛分配

### 目标

提供轻量、独立、可撤销和可追责的裁判身份，不复用管理员密码或选手参赛码。

### 推荐方案

采用“赛事级裁判身份 + 独立随机凭证 + 比赛分配”：

- 管理员创建裁判并一次性展示初始访问凭证；
- 服务端只保存凭证哈希；
- 裁判凭证有有效期，可以单独撤销和重置；
- 裁判登录后只看到当前赛事和被分配比赛；
- 每次写操作重新在服务端验证裁判和比赛关系。

### 工作内容

1. 实现裁判凭证生成、哈希、读取和轮换。
2. 实现管理员创建、停用、重置裁判。
3. 实现比赛分配和撤销。
4. 实现裁判会话或安全 cookie。
5. 服务端权限不得依赖前端传入的 `refereeId`。
6. 为登录、重置、分配和裁判写操作增加限流与审计。
7. 不将裁判加入选手公开名单。

### 安全要求

- 凭证使用加密安全随机数；
- 哈希比较避免直接明文存储；
- cookie 使用 HttpOnly、Secure、SameSite；
- 会话包含赛事范围和过期时间；
- 停用后立即拒绝后续写操作；
- 错误信息不区分“裁判不存在”和“密码错误”；
- 管理员重置后旧凭证失效；
- 不允许一个赛事凭证访问另一赛事。

### 文件边界

- 可以新建 referee auth/domain/API 文件；
- `src/proxy.ts` 由本工作包独占修改；
- 不把裁判路径加入管理员白名单后放弃路由内鉴权；
- 不修改赛果状态机。

### 验收清单

- [ ] 未登录访问被拒；
- [ ] 已登录但未分配比赛被拒；
- [ ] 已停用裁判被拒；
- [ ] 旧凭证在重置后失效；
- [ ] 跨赛事访问被拒；
- [ ] 管理员可以追溯分配和重置操作；
- [ ] 公开接口不泄露裁判凭证和内部 ID；
- [ ] 速率限制故障在生产环境按安全策略处理。

## 5. RPT-03：私有比赛凭证存储

### 目标

安全保存赛果截图，不复用公开海报空间。

### 工作内容

1. 新增独立私有 bucket，例如 `match-evidence`。
2. 使用新 migration 或明确的基础设施说明创建，不修改已执行 migration。
3. 只允许服务端持有的密钥访问对象。
4. 上传时校验 MIME、文件签名、大小、数量和散列。
5. 对象路径只使用不透明 ID，不包含姓名、学号、手机号或昵称。
6. 下载使用短时签名地址或鉴权代理。
7. 定义删除期限、申诉保留和归档策略。
8. 上传失败不得生成悬空提交；提交失败后的孤儿文件有清理策略。

### 推荐限制

- JPG、PNG、WebP；
- 单张不超过 5MB；
- 单场初始最多 5 张；
- 读取地址短时有效；
- 生产日志不打印对象签名 URL。

### 验收清单

- [ ] 匿名用户无法列举或读取对象；
- [ ] 其他裁判无法读取未分配比赛凭证；
- [ ] 假扩展名和错误文件签名被拒；
- [ ] 超限文件和频繁上传被拒；
- [ ] 相同文件散列可用于识别重复上传；
- [ ] 签名地址过期后失效；
- [ ] 删除和保留策略有可验证说明；
- [ ] 测试仅使用隔离 bucket 或 mock，不写生产。

## 6. RPT-04：裁判报分与管理员处理 API

### 目标

将 RPT-01～03 组合成原子、鉴权、可审计的服务端能力。

### 建议接口能力

- 裁判登录和退出；
- 裁判读取我的比赛；
- 裁判创建草稿或上传凭证；
- 裁判提交赛果；
- 管理员读取异常队列；
- 管理员接受、驳回或要求重提；
- 管理员受控更正或撤销赛果；
- 管理员管理裁判和比赛分配。

具体 URL 在 RPT-00 冻结，不由实现 AI 临时决定。

### 关键要求

1. 每次提交包含所基于的赛程版本。
2. 服务端从身份和分配关系推导权限，不相信客户端角色字段。
3. 接受赛果、更新比赛和产生决策必须在同一受控更新中完成。
4. 重复请求返回同一结果，不产生双重晋级。
5. 版本冲突返回明确的 409，不静默覆盖。
6. 图片先上传后提交时，需要草稿和过期清理机制。
7. 所有高风险操作写审计，但审计故障策略要明确区分业务提交是否已成功。
8. 返回裁判和公开端的数据必须最小化。

### 验收清单

- [ ] API 正常路径、越权、版本冲突和重复提交测试通过；
- [ ] 接受结果不会双重推进；
- [ ] 异常不会修改正式赛果；
- [ ] 下游有进度时更正被安全阻止；
- [ ] 服务端功能开关关闭时裁判写操作不可用；
- [ ] 现有管理员手工报分仍可按迁移策略使用或被明确替代；
- [ ] 公共赛程只显示已接受的正式赛果。

## 7. RPT-05：手机端裁判工作台

### 目标

让裁判在手机上以最少步骤完成被分配比赛的手工报分。

### 页面结构建议

1. 登录或恢复访问；
2. 我的比赛：待开始、待报分、已提交、异常；
3. 比赛详情：双方、BO、时间、BP 地图、当前状态；
4. 报分表单：逐局地图、双方比分、自动计算大比分；
5. 凭证上传；
6. 提交前汇总确认；
7. 提交结果和异常说明。

### 体验原则

- 默认显示当前或最近一场，不让裁判在完整对阵中查找；
- BP 已确定地图时自动带入但允许按规则处理变化；
- 大比分由逐局结果计算，不重复要求输入；
- 错误直接定位到具体局和字段；
- 提交按钮明确说明操作后果；
- 网络失败保留本地草稿，但不把本地草稿伪装成已提交；
- AI 未接入或不可用时页面保持完整可用。

### 验收清单

- [ ] 390×844 可只用触屏完成报分；
- [ ] 软键盘不遮挡核心输入和提交按钮；
- [ ] 裁判看不到未分配比赛；
- [ ] 提交前能看到完整汇总；
- [ ] 重复点击不会创建重复赛果；
- [ ] 网络失败后状态清晰；
- [ ] 已提交结果不可在原表单静默修改；
- [ ] 不存在 AI 入口也能完成全部任务。

## 8. RPT-06：管理员异常赛果工作台

### 目标

让管理员只处理需要判断的异常，而不是重新录入所有比赛。

### 页面内容

- 待审核数量和风险原因；
- 比赛、裁判、提交时间和赛程版本；
- 原始截图和结构化赛果；
- 规则校验结果；
- 重复或冲突提交对比；
- 下游受影响比赛；
- 接受、驳回、要求重提和受控更正；
- 操作原因必填；
- 决策和历史版本记录。

### 关键原则

- 风险原因优先展示；
- 不以大面积统计卡挤压处理区；
- 危险操作需要二次确认并说明影响；
- 下游已发生进度时不提供误导性的“一键覆盖”；
- 图片访问按需签名，不把永久公开链接写入页面数据。

### 验收清单

- [ ] 管理员能在一屏判断为什么进入异常队列；
- [ ] 可以对比原提交和拟生效结果；
- [ ] 接受、驳回和更正均有原因与审计；
- [ ] 决策后队列状态与公开结果一致；
- [ ] 越权或会话失效时不能继续提交；
- [ ] 长队名、长裁判名和多图证据布局可用。

## 9. RPT-07：综合验收

### 功能回放

至少使用一场隔离的小型赛事完成：

1. 创建两名裁判；
2. 分配不同比赛；
3. 验证跨比赛越权被拒；
4. 完成 BO1、BO3 和 BO5 报分；
5. 上传合法和非法图片；
6. 完成普通结果直接生效；
7. 完成异常结果管理员复核；
8. 重复提交验证幂等；
9. 两人并发提交冲突结果；
10. 更正无下游进度的赛果；
11. 尝试更正已有下游 BP/赛果的比赛并确认被阻止；
12. 停用裁判并确认权限立即失效；
13. 检查公开赛程只展示正式赛果；
14. 执行备份与隔离恢复；
15. 关闭功能开关并确认现有平台不受影响。

### 非功能验收

- 手机端关键路径；
- 并发与版本冲突；
- 限流；
- 私有存储访问；
- 审计脱敏；
- 功能开关；
- 完整门禁和生产构建。

### 上线条件

- 所有验收在隔离环境通过；
- 产品负责人确认裁判流程可接受；
- 至少一名真实裁判完成试用；
- 手工报分回退可用；
- 发布负责人单独制定上线和回滚步骤；
- 本轨道不包含 AI，因此不能以 AI 演示代替验收。
