## 通用原则（三部分共用）

1. **不依赖专人盯盘。** 你是单人运营，任何方案如果要"每天有人看板"就是失败的；告警只发"需要你动手"的事。
2. **结论必须可被反驳。** 每条"已完成"都要附证据（命令输出、演练结果、变异验证），没验过的必须显式写"没验过"。
3. **新增即登记。** 新增写入点、新增指标、新增埋点事件都要进对应的登记表并加断言，否则半年后没人知道它存在（本次会话已经踩过两次：赛程写入点、阶段类型清单）。

# 第一部分 赛事数据化与数据监控体系

## 1.1 目标

从「有真实数据但说不清状态」变成能一句话回答三个问题：

| 问题 | 现在怎么答 | 目标怎么答 |
|---|---|---|
| 赛事现在健康吗？ | 靠翻页面 | 一个数字：**有效完成场次 / 计划场次**，以及是否有护栏告警 |
| 卡在哪了？ | 靠感觉 | 一张按"报名 / 赛程 / 公开站"分层的面板，每层最多 5 个数字 |
| 和上一届比变好还是变差？ | 没有基线 | 每周一张趋势对照（同一口径的周同比） |

**北极星指标（建议）**：`有效完成场次 / 计划场次`，配合 `单位场次运营工时`（你的投入时间 ÷ 完成场次）。前者看赛事推进，后者看这个系统有没有真的省你的事。

## 1.2 指标分层与口径

**【现状】** 以下指标的数据**已经全部存在**（赛程文档 / 报名文档 / 审计台账 / 公开接口），第一部分不需要新埋点就能算出八成。

### A 层：报名与名单（赛事前 / 中）

| 指标 | 口径 | 来源 | 健康信号 |
|---|---|---|---|
| 报名队伍数 | `teams` 中状态 ≠ 已退赛 | 报名文档 | 与预期规模对比 |
| 满编率 | 首发 ≥5 且状态=已冻结 ÷ 报名队伍数 | 报名文档 | 冻结期应趋近 100% |
| 资料待处理数 | `reviewStatus` ∈ {需修改,已拒绝} 的选手数 | 报名文档 | 应逐日下降 |
| 名单冻结进度 | 已冻结队数 ÷ 目标队数 | 报名文档 | 抽签前必须 100% |

### B 层：赛程与执行（赛事中，最重要）

| 指标 | 口径 | 来源 | 健康信号 |
|---|---|---|---|
| 赛程完成率 | 已完成场次 ÷ 总场次 | 赛程文档 | 与赛期剩余天数对照 |
| 未排期场次 | 状态=待排期 | 赛程文档 | 次日要打的场次应已排期 |
| **报分时延** | 比赛开始时间 → 赛果录入时间 | 赛程 + 审计 | 中位数与 P95：这是"卡不卡"的核心 |
| 改期率 | 改期申请数 ÷ 已完成场次 | 赛程文档 | 突增说明排期本身有问题 |
| 改期闭环时长 | 申请 → 审批 → 重排完成 | 赛程 + 审计 | 待审批堆积要告警 |
| 阶段推进 | 当前阶段 + 预计剩余天数 | 赛程 + 赛制 | 预计完成日 > 赛事截止日即为红 |
| **护栏触发次数** | 内容丢失被拦截 / 版本冲突 / 空赛程 | 运行时 | 任何一次都值得看 |

> 最后一项直接来自今天的真实事故：赛程被清成 0 场时，**没有任何一个数字在变红**——因为没人统计"场次数环比骤降"。它应该是 B 层的第一条告警。

### C 层：公开站点（玩家侧）

| 指标 | 口径 | 来源 | 健康信号 |
|---|---|---|---|
| 健康检查成功率 | `/api/health` 200 占比 | 定时探测 | < 99% 告警 |
| 首页 / 赛程页访问 | 去重访客数（不记个人身份） | **新增轻量埋点** | 只看量级与趋势 |
| 公开数据缓存新鲜度 | 缓存版本 vs 最新版本的时间差 | 定时探测 | 超过 revalidate 周期 2 倍要查 |
| 5xx 比例 | 服务端错误 ÷ 请求数 | 运行时 | > 0.5% 告警 |

## 1.3 数据采集与埋点方案

三层采集，**越靠前越优先，能不埋就不埋**：

**第一层：事实层（零成本，已存在）**
赛程 / 报名 / 裁判台账 / 操作审计直接聚合。**这是主力**——L1 指标全部由此得出。

**第二层：服务端事件（新增，落在写路径上）**
在写路径（保存赛程、提交赛果、审批改期、调整赛制）成功与失败各落一行事件：

```
事件名：域.动作.结果          例：schedule.save.ok / schedule.save.rejected
必填属性：event_id, actor_type(admin|referee|captain), result_reason, version_before, version_after
禁止采集：姓名 / 手机号 / 学号 / 截图 / 任何个人标识
```

- 本地 `file` 后端 → `data/metrics/events.jsonl`（按日分文件）
- 生产 → Supabase 一张事件表（与现有两套后端约定一致）
- **写入点必须进登记表并加断言**（同赛程写入契约的做法）

**第三层：客户端埋点（最后做，且克制）**
只采公开站的少量事件（首页到达、赛程页到达、报名页到达），**不引第三方 SDK**（避免 Cookie 与合规问题），字段只有 `事件名 + 页面 + 匿名会话号`。

**保留策略**：明细 30 天，之后只留日聚合（避免免费额度被明细撑爆）。

## 1.4 监控与告警

> **【2026-10-16 负责人已决定：本节暂不做】** 原话「太麻烦了就不弄了，感觉实用性不强」。
> 理由：赛事 11-8 结束只剩三周；且已有更便宜的兜底 ——
> 赛果丢失护栏（写入异常会当场报错）+ 后台赛程页自带「数据时间」标识（异常肉眼可见）。
> 本节保留为**方案存档**，不代表待办；若赛事常态化再重新评估。
> 另：项目当前**没有任何对外推送通道**（无邮件/webhook/企业微信，vercel.json 无 cron），
> 现有的"通知"只是后台里的列表 —— 任何无人值守机制在做之前必须先解决"怎么找到人"。

三层节奏，全部自动化：

| 层 | 频率 | 内容 | 出口 |
|---|---|---|---|
| 实时 | 页面内 | 比赛工作台显示三个数字：未排期 / 待报分 / 待审批改期 | 他打开就看到 |
| 定时巡检 | 每小时 | 健康检查、**赛程场次数环比**、未排期数、待审批数、缓存新鲜度 | 只在越阈值时发一条 |
| 每周复盘 | 每周一次 | 周同比趋势 + 上周护栏触发清单 | 一张对照表 |

**告警分级（避免疲劳）**

- **P0 立即发**：赛程场次数骤降 / 健康检查连续失败 / 体检发现数据不一致
- **P1 当日汇总**：报分时延 P95 超标、待审批改期堆积、阶段推进落后于赛期
- **P2 只进周报**：访问量趋势、满编率变化

**同一条告警 1 小时内只发一次**；静默期内不重复。

**【需你拍板】免费层保活**：Supabase 免费层 7 天不活跃会暂停数据库。每小时巡检天然也是心跳，能把暂停风险压掉——**但这与我此前"不做定时监控"的记档冲突**，需要你确认是否放开。

## 1.5 落地步骤

| 步 | 内容 | 可独立验收 |
|---|---|---|
| 1 | 只读指标计算：不新增任何采集，用现有数据算出 A/B/C 三层全部指标，命令行输出（`ops:metrics`） | 与页面数字逐项对得上 |
| 2 | 服务端事件：写路径落事件 + 登记表 + 断言 | 演练里能看到事件行 |
| 3 | 定时巡检 + P0/P1 告警（先只发给你） | 手动制造一次异常，能收到且只收到一条 |
| 4 | 面板与周报：把指标渲染成一屏；每周自动生成对照表 | 周报能回答"变好还是变差" |
| 5 | 客户端埋点（可选，放最后） | 访问量与第三方统计量级一致 |

## 1.6 验收标准

- `ops:metrics` 能一次输出三层全部指标，且**每个指标都标注口径与数据来源**（不接受"看起来对"）
- 断网/空数据/赛事不存在三种情况下不报错、给出明确提示
- 手动制造"赛程被清空"：**60 秒内收到一条 P0 告警**（这是对本次事故的直接回应）
- 连续运行 7 天无误报（误报率 0）与漏报（人为制造 3 次异常，3 次都报）

# 第二部分 赛事 AI 功能的打磨与实现

## 2.1 目标与现状

**【现状】** AI 集成度 **0%（冻结）**；仅 F05 冲突解释、F08 通知文案保留为 AI 职责。已有基础：裁判报分链路、赛果截图上传、离线评测框架的雏形、以及"以传图取代填表"的方案文档。

**目标**：在**不引入不可控风险**的前提下，让 AI 从"玩具"变成"你每天都在用的一步"。判断标准只有一条：**它有没有减少你的人工作业量**。

## 2.2 场景分层与优先级

| 层 | 场景 | 为什么排这个位置 |
|---|---|---|
| **L1 记录辅助** | 赛果截图 → 结构化字段（比分、地图、胜者）；报分转录 | 收益最大（你现在亲手转录）、错了立刻能看出来、可离线评测 |
| **L2 判断辅助** | 改期冲突解释（F05）、通知文案（F08） | 已有设计、价值明确、有明确的人工兜底 |
| **L3 玩家体验** | 赛程解读、常见问题问答 | 面向外部，错了影响面大，放最后 |

## 2.3 能力边界（三条硬线，不可越过）

1. **不产出赛果事实** —— 识别结果一律进"待人工确认"，人点了才落库。
2. **不改赛程** —— 只能给建议文本，改期与排期由人确认。
3. **不判定资格** —— 不参与报名审核、名次判定。

配套：**任何 AI 输出都必须可一键人工兜底**，且兜底路径与无 AI 时完全一致（AI 挂掉不影响赛事运行）。

## 2.4 从「可用」到「好用」的四条路径

| 维度 | 玩具态 | 好用态 | 做法 |
|---|---|---|---|
| 口径 | 每次输出略不同 | 同输入同输出、可复现 | 固定参数与提示版本，评测用固定种子 |
| 可解释 | 只给结论 | 给依据与置信度 | 输出字段级依据（"来自第 3 张图的比分栏"） |
| 可回退 | 出错只能重来 | 一键人工修改 | 识别结果进草稿态，人工确认才生效 |
| 成本延迟 | 没有预算 | 有单场预算与超时降级 | 单场成本上限 + 超时自动转人工 |

## 2.5 效果评估方式

**① 离线评测集（先建这个，否则一切改进都不可比）**

- 50 例真实赛果截图 + 50 例真实改期案例，人工标注为金标准
- 指标：字段级准确率、需人工修改率、拒答率（宁拒不错）、P95 延迟、单场成本
- **每次改动必须跑同一套集**，否则不许说"变好了"

**② 影子运行**：AI 跑但不生效，与人工结果对照，至少 2 周，记录一致率与差异类型

**③ 上线后**：采纳率（AI 结果被直接确认的比例）、人工修改率、失败类型分布

## 2.6 迭代机制

```
预注册（先写清"什么算变好"）→ 离线 Gate（达标才继续）→ 影子（对照 2 周）
→ 灰度（仅你一个人用）→ 复盘（写一页结论：涨了什么、掉了什么）
```

**禁止"感觉变好了就上线"**——每次改动都要留一份评测报告，否则三个月后无法回答"这套东西到底行不行"。

## 2.7 落地步骤

| 步 | 内容 | 可独立验收 |
|---|---|---|
| 1 | 建离线评测集（100 例 + 金标准），跑通评测脚本 | 脚本能输出五项指标 |
| 2 | L1 截图识别做到"可用"（进草稿态 + 人工确认） | 离线指标达标 + 真跑一场 |
| 3 | L2 冲突解释与通知文案接入（沿用现有设计） | 影子对照一致率达标 |
| 4 | 影子 → 灰度 → 常态化 | 采纳率与人工修改率有基线 |
| 5 | L3 玩家体验（可选） | 单独立项评估 |

## 2.8 验收标准（建议阈值，**【需你拍板】**）

- 字段级准确率 **≥ 95%**、需人工修改率 **≤ 10%**、拒答率 **≤ 5%**
- P95 延迟 **≤ 8 秒**、单场成本 **≤ 0.05 元**
- 影子期人机一致率 **≥ 90%**，且**没有一次错判流入正式数据**
- AI 服务不可用时，赛事全流程仍可完成（断网演练验证）

# 第三部分 把验收升级为评测体系

## 3.1 目标

把"你验收时发现问题 → 我改"这个回路，前移成"系统先发现"。具体三件事：

1. 每次交付自带证据，不需要你替我找问题；
2. 每个已修的问题都变成一条**可复现**的评测条目（下次自动拦住）；
3. 评测结果可量化、可追踪，能回答"这周比上周稳了吗"。

## 3.2 三层评测与证据分级

| 层 | 谁执行 | 内容 | 现在有没有 |
|---|---|---|---|
| **E0 事实层** | 自动 | lint / 类型检查 / 33 个测试套件 / 构建 | ✅ 已有（`npm run gate`） |
| **E1 行为层** | 自动 | 端到端演练：裁判链路 63 项、36 队演练、换赛制演练 13 项 | ✅ 已有（`gate:full`） |
| **E2 判断层** | 你 | 产品验收：是否符合预期、是否好用 | ❌ **本次要补的就是这一层** |

**证据分级（交付时必须逐条标注）**

| 级别 | 含义 |
|---|---|
| 验过 | 实跑并有输出可查 |
| 只读代码 | 读过逻辑但没跑 |
| 没验过 | 明确没覆盖（必须写出来，不许含糊） |

## 3.3 可复用资产（本次会话已经在积累，只是没成体系）

**① 评测清单模板（每条一个场景）**

```
编号：EV-012
场景：入围赛全部完成后打开赛事阶段面板
前置数据：20 场已完成（含 16 场入围赛），小组赛尚未抽签
操作：打开 /admin/events/event-1
期望：显示"赛制还有 2 个阶段未开始：小组赛、淘汰赛"，按钮为"开始小组赛抽签"
证据：页面文本断言 + 截图（可选）
状态：通过 / 失败 / 未覆盖
```

**② 回归集**：每次修 bug，**必须**把复现步骤变成上表一条，并加进自动套件或演练。本次已积累的条目（示例）：
赛程契约盲区、鉴权唯一实现、结束赛事判据、换赛制三版判据、组内单败 43 项、赛程写入点登记。

**③ 变异验证**：凡声称"修好了 / 有守卫"，必须附一次"把它去掉是否变红"。**这是本项目区分"真守卫"和"装饰性断言"的唯一手段**，本次已多次依赖它抓到假绿。

**④ 两套夹具原则**：端到端评测必须自带隔离数据与清理（用完按校验和还原），此前已形成惯例。

## 3.4 协作机制

```
预注册：动代码前先写清"什么算成功"（避免事后解释）
一次交付一次评测：一批改动 = 一条结论，不夹带无关变更
结论表：做了什么 / 证据 / 没覆盖什么 / 需你拍板什么
你的 [xxx] 标注：回流成清单条目，下次自动跑
```

**结论表模板**

```
本批：<做了什么>
证据：<命令与输出摘要、演练项数、变异次数>
没覆盖：<显式列出>
需你决定：<选项与我的建议>
```

## 3.5 指标（评测体系本身也要被度量）

| 指标 | 口径 | 目标方向 |
|---|---|---|
| 门禁通过率 | 一次通过 ÷ 总提交 | 上升 |
| 变异通过率 | 做了变异验证的守卫 ÷ 新增守卫 | 趋近 100% |
| **缺陷逃逸率** | 发布后才发现的问题 ÷ 总问题 | **下降**（当前这次事故就是一次逃逸） |
| 首次验收通过率 | 你一次点头 ÷ 交付次数 | 上升 |
| 返工次数 | 同一需求返工轮数 | 下降 |
| 修复时长 | 发现 → 修复 → 回归通过 | 下降 |

## 3.6 落地步骤

| 步 | 内容 | 可独立验收 |
|---|---|---|
| 1 | 建清单库（把已有回归项写成条目，目标 ≥ 30 条） | 每条都有编号与复现步骤 |
| 2 | 交付一律附结论表（含"没覆盖"） | 连续 5 次交付都有 |
| 3 | 逃逸缺陷 24 小时内补成条目 | 条目库只增不减 |
| 4 | 月度复盘看 3.5 的指标 | 能画出一条趋势 |

## 3.7 验收标准

- 清单库 ≥ 30 条，且每条可被独立执行（不依赖"当时的环境"）
- 最近 10 次交付均附结论表，且"没覆盖"栏**从未为空**（为空说明没认真写）
- 缺陷逃逸率从当前水平降到 **≤ 1 项/周**
- 评测指标能按月出趋势，且趋势与你的主观感受不矛盾（矛盾就以数据为准，回头查口径）

# 附三：排期规则定义（固定比赛时间模式的自动化规则）

> 2026-10-16。负责人的要求：「固定模式下排期的自动化规则是什么也要定义，不同比赛他每天的场次和
> 比赛时间都可能不一样」——即**规则必须是可配的，不能写死**。
> 本附件是规则定义（先定规则、再写代码），实现进度见文末。

## 一、模式的定位

排期模式是**赛事级配置项**（与赛制同级，抽签发布后不再改）：

| 模式 | 时间由谁定 | 选手侧协商入口 | 「待排期」的含义 |
|---|---|---|---|
| `open` 自由约赛 | 选手在窗口内自行协商 | 有 | 正常状态 |
| `fixed` 固定比赛时间 | 主办方统一排定 | 不提供 | **异常状态（应长期为 0）** |

本附件只定义 `fixed` 模式下的自动化排期规则。

## 二、规则的可配参数（事件级，逐项可覆盖）

**★ 关键设计：比赛日不是"一个统一时段"，而是"每一天各自一行"** ——
因为不同赛事的每日场次数与时段都可能不同，甚至同一届里周六与周日也不同。

| 参数 | 含义 | 默认（取赛制约束） | 粒度 |
|---|---|---|---|
| `days` | 可比赛的日期 | 赛期内的周六、周日 | **逐日一行**，可显式指定 |
| `sessionStart` / `sessionEnd` | 当天时段起止 | 12:00 / 18:00 | **逐日可不同**（如周六 10:00–20:00、周日 10:00–16:00） |
| `dailyLimit` | 当天最多打几场 | 不限（只受时段与并发约束） | **逐日可不同** |
| `maxConcurrent` | 同时进行上限 | 2 | 赛事级 |
| `perTeamDailyLimit` | 同一队一天最多打几场 | 2 | 赛事级（防背靠背） |
| `durations` | 单场时长（按 BO） | BO1 45 / BO3 90 / BO5 150 分钟 | 赛事级 |
| `gapMinutes` | 两场之间的最小间隔 | 0（可设 15，用于换场） | 赛事级 |
| `stepMinutes` | 时间推进粒度 | 15 分钟 | 赛事级（排期以整点/半点为佳） |
| `teamUnavailable` | 某队某天不可用 | 空 | 可选，来自协商或改期申请 |

## 三、算法（确定性，可复现）

1. **场次排序**：按「阶段顺序 → 轮次先后 → 比赛 id」。只排**参赛队已确定**的场次；
   参赛队未定的（组内决赛、淘汰赛后续轮次）留给前序出结果后再排。
2. **逐场安置**：按比赛日升序，遍历该日时段内的候选开始时间（步长 `stepMinutes`），
   取**最早**满足全部约束的那个：
   ① 结束不超出当天时段；② 当天场次数 < `dailyLimit`；③ 该时刻并发 < `maxConcurrent`；
   ④ 该队当天场次数 < `perTeamDailyLimit`；⑤ 与同场地前一场满足 `gapMinutes`。
3. **顺延**：当天排不下 → 顺延到下一个比赛日；全部比赛日都排不下 → 记为「排不下」。
4. **不静默丢弃**：排不下的场次要**写明卡在哪个约束**，并给出建议动作
   （增加比赛日 / 提高并发 / 提高当天上限），而不是只报失败。
5. **输出是草案**：列出每场的日期、时间、对阵，以及排不下的场次与原因；
   **负责人确认后才写入**（写入走赛程写入契约 + 条件写入防覆盖），不是静默写库。
6. **规则留痕**：写入时把本次生效的参数摘要记进版本记录的说明里 ——
   以后能回答「当时的赛程是按什么规则排的」。

## 四、边界与不做的事

- 不自动**改**已排期的场次（重排是另一个动作，需要显式确认）；
- 不跨天：一场比赛必须落在同一个比赛日内；
- 不猜测队伍偏好 —— 「队伍不可用时间」只能来自显式输入（协商或申请）；
- 不替代抽签：只负责"什么时候打"，不决定"谁打谁"。

| `open` 自由约赛 | 选手在窗口内自行协商 | 有 | 正常状态 |
| `fixed` 固定比赛时间 | 主办方统一排定 | 不提供 | **异常状态（应长期为 0）** |

本附件只定义 `fixed` 模式下的自动化排期规则。

## 二、规则的可配参数（事件级，逐项可覆盖）

**★ 关键设计：比赛日不是"一个统一时段"，而是"每一天各自一行"** ——
因为不同赛事的每日场次数与时段都可能不同，甚至同一届里周六与周日也不同。

| 参数 | 含义 | 默认（取赛制约束） | 粒度 |
|---|---|---|---|
| `days` | 可比赛的日期 | 赛期内的周六、周日 | **逐日一行**，可显式指定 |
| `sessionStart` / `sessionEnd` | 当天时段起止 | 12:00 / 18:00 | **逐日可不同**（如周六 10:00–20:00、周日 10:00–16:00） |
| `dailyLimit` | 当天最多打几场 | 不限（只受时段与并发约束） | **逐日可不同** |
| `maxConcurrent` | 同时进行上限 | 2 | 赛事级 |
| `perTeamDailyLimit` | 同一队一天最多打几场 | 2 | 赛事级（防背靠背） |
| `durations` | 单场时长（按 BO） | BO1 45 / BO3 90 / BO5 150 分钟 | 赛事级 |
| `gapMinutes` | 两场之间的最小间隔 | 0（可设 15，用于换场） | 赛事级 |
| `stepMinutes` | 时间推进粒度 | 15 分钟 | 赛事级（排期以整点/半点为佳） |
| `teamUnavailable` | 某队某天不可用 | 空 | 可选，来自协商或改期申请 |

## 三、算法（确定性，可复现）

1. **场次排序**：按「阶段顺序 → 轮次先后 → 比赛 id」。只排**参赛队已确定**的场次；
   参赛队未定的（组内决赛、淘汰赛后续轮次）留给前序出结果后再排。
2. **逐场安置**：按比赛日升序，遍历该日时段内的候选开始时间（步长 `stepMinutes`），
   取**最早**满足全部约束的那个：
   ① 结束不超出当天时段；② 当天场次数 < `dailyLimit`；③ 该时刻并发 < `maxConcurrent`；
   ④ 该队当天场次数 < `perTeamDailyLimit`；⑤ 与同场地前一场满足 `gapMinutes`。
3. **顺延**：当天排不下 → 顺延到下一个比赛日；全部比赛日都排不下 → 记为「排不下」。
4. **不静默丢弃**：排不下的场次要**写明卡在哪个约束**，并给出建议动作
   （增加比赛日 / 提高并发 / 提高当天上限），而不是只报失败。
5. **输出是草案**：列出每场的日期、时间、对阵，以及排不下的场次与原因；
   **负责人确认后才写入**（写入走赛程写入契约 + 条件写入防覆盖），不是静默写库。
6. **规则留痕**：写入时把本次生效的参数摘要记进版本记录的说明里 ——
   以后能回答「当时的赛程是按什么规则排的」。

## 四、边界与不做的事

- 不自动**改**已排期的场次（重排是另一个动作，需要显式确认）；
- 不跨天：一场比赛必须落在同一个比赛日内；
- 不猜测队伍偏好 —— 「队伍不可用时间」只能来自显式输入（协商或申请）；
- 不替代抽签：只负责"什么时候打"，不决定"谁打谁"。
