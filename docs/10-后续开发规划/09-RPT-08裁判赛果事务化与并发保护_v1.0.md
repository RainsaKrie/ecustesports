# RPT-08 裁判赛果事务化与并发保护 v1.0

## 1. 结论

裁判报分写链路已从“依次覆盖多份 JSON 文档”改为“基于同一版本快照的多文档原子比较交换（CAS）”。一次业务操作要么完整提交，要么整体失败并重试，避免赛程、正式赛果和证据记录只写入一部分。

同一快照覆盖以下文档：

- `schedule`：比赛状态、比分、胜负方与完成时间。
- `result-ledger`：裁判提交、复核、驳回与管理员更正记录。
- `evidence-ledger`：赛果证据引用。
- `referee-ledger`：裁判身份、分配与凭证状态；即使本次不修改，也作为授权前置条件参与版本校验。

## 2. 实现范围

### 2.1 数据层合同

`DataStoreDriver` 新增 `updateMany`，业务层通过一个更新函数读取一致快照，并只返回需要改动的文档。驱动层负责冲突检测、重读与整组重试。

- 本地文件驱动：同一赛事内串行化读写；写入中途失败时恢复已写文档。
- Supabase 驱动：调用数据库函数 `update_app_documents_atomic`，由数据库事务完成版本校验和原子提交。

### 2.2 数据库迁移

迁移文件：`supabase/migrations/202609100001_rpt08_atomic_documents.sql`

数据库函数使用赛事级事务锁、逐文档版本校验和条件更新。并发冲突以 PostgreSQL `40001` 返回，应用层重新读取整组文档后再计算；函数使用受限搜索路径，并在同一事务内撤销默认公开权限、仅授予 `service_role` 执行权限。

### 2.3 业务接入

以下写操作统一进入事务入口：

- 裁判提交赛果。
- 管理员复核赛果。
- 管理员更正正式赛果。
- 裁判账号创建、禁用、凭证重置。
- 裁判分配与撤销。

## 3. 验证范围

新增 `npm run test:data-transaction`，验证：

- 多文档一次提交并返回合并后的快照。
- 只读授权文档参与版本校验但不被无意义写回。
- 20 个并发更新不丢失，关联文档最终一致。
- 本地第二份文档写入失败时，第一份文档恢复原值。
- Supabase 返回 `40001` 后整组重读、重新计算并重试。

仍需在 Preview 环境补充真实 Supabase 并发、超时与重复请求验证，不能用本地模拟结果替代。

2026-09-10 本地最终回归证据：ESLint 通过、TypeScript 通过、12 组测试合计 `371/371` 通过、Next.js 生产构建通过。该证据证明代码基线可构建，不代表数据库迁移和 Preview 实测已经完成。

## 4. 发布门禁

按以下顺序执行，任何一步失败均停止：

1. 保持 `REFEREE_REPORTING_ENABLED=0`，不开放生产裁判写入。
2. 在目标 Supabase 项目执行本次迁移。
3. 确认数据库函数存在，且匿名与普通登录角色无执行权限。
4. 推送代码并生成新部署。
5. 只在 Preview 环境设置 `REFEREE_REPORTING_ENABLED=1`。
6. 用裁判和管理员两种身份完成一次提交、复核、驳回、更正与并发冲突演练。
7. 由负责人明确批准后，才可讨论生产环境开放。

## 5. 回滚

- 功能回滚：将 `REFEREE_REPORTING_ENABLED` 设为 `0` 并重新部署，裁判写入口立即关闭。
- 代码回滚：回退应用提交不会破坏已有数据；新增数据库函数可以暂时保留。
- 数据回滚：不直接删除生产记录。依据操作审计和赛果台账人工确认后再更正。

## 6. 边界与剩余风险

- 本地文件驱动只能处理运行期失败回滚，无法提供数据库级断电原子性；生产必须使用 Supabase。
- 网络在“数据库已提交、客户端未收到响应”时存在结果不确定性，Preview 必须验证重复请求的幂等表现。
- 正式开放前仍需完成裁判权限实测、真实移动端操作和赛事期值守方案。
- AI 接入继续冻结；本工作只完善确定性的赛果基础设施。
