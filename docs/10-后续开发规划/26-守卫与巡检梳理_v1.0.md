# 守卫与巡检 · 现状梳理与简化方案 v1.0

> 2026-10-18。**这是一份建议稿，不执行。**
> 背景：这些守卫是今天**边写边修**出来的 —— 一天里改坏过 6 次（判据写宽、基线冲突、插入位置错）。
> 这份文档把重复与复杂点摆出来，给出合并/删除/抽象的具体位置。

## 二、重复与复杂点（每条都有实测证据）

| # | 问题 | 证据 |
|---|---|---|
| 1 | **遍历文件的 `walk()` 写了三遍** | `arch / ui / color` 各 1 份，逻辑完全一致（跳过 node_modules、只收 .ts/.tsx） |
| 2 | **`check()` 输出函数写了三遍** | 三份 `const check = (name, ok, detail) => …`，连缩进都一样 |
| 3 | **基线的"读-比-写"写了三遍** | 每份都有 `JSON.parse(readFileSync(BASELINE…` + `--write-baseline` 分支（出现 4/3/3 次）+ added/removed/worse 三段 diff |
| 4 | **色板有两个真源** | 一份从 `globals.css` 的 `--xxx: #hex` 现算；另一份是 `color-guard` 里**手写的 `PUBLIC_EXTRA` 数组** —— 同一种事实两处维护 |
| 5 | **`--write-baseline` 有多个写入点** | 今天正是这个让我把 `ui-guards` 改坏（两处都写、其中一个还 `process.exit` 抢跑） |
| 6 | **继承的 `.next` / 临时目录污染** | 删路由后 typecheck 被旧生成物绊住（已踩过一次） |
| 7 | **mutation 用例与守卫分家** | `guard-mutation-check.ts` 里**手写 9 条用例**、硬编码三份文件路径 → 新增守卫时**必须记得**同步改这里，否则新守卫永远没被验证过 |
| 8 | **四个 npm 脚本指向同一件事** | `test:arch-guards` / `test:ui-guards` / `test:color-guard` / `test:guard-mutation` |

## 三、方案：一个骨架 + 三个插座 + 一条真源

### 3.1 抽 `tools/guards/kit.ts`（唯一骨架，约 80 行）

```ts
export function walkSources(root: string, dirs: string[]): string[]      // 现三份 walk 合一
export function createReport(): { check; section; done }                 // 现三份 check 合一
export function createBaseline<T>(file: string, scan: () => T)           // 读/写/比 三段合一
export function readPalette(cssPath: string): Set<string>                // 色板唯一来源
```

每个守卫文件只保留**自己的判据**，从 ~120 行降到 ~50 行：

```ts
const baseline = createBaseline("tools/arch/baseline.json", scan);
const { check, done } = createReport();
check("① 没有新增的「文件 >400 行」", diff.added.length === 0, detail);
done();
```

**关键约束（写进 kit 的注释）**：`createBaseline` 是**唯一**能写基线的入口；
任何守卫文件里**不允许**再出现 `writeFileSync(BASELINE…)`。

### 3.2 色板只留一个真源

- **删掉** `color-guard` 里手写的 `PUBLIC_EXTRA`（14 个值）；
- 把它们**全部搬进 `globals.css`** 的 `:root`（今天已经搬了 3 个：`--pub-ink-*`）；
- 色板 = **只**从 globals 算出来。**新值要进色板，唯一方式是在 globals 里定义** ——
  这条纪律比任何检查都有效。

### 3.3 mutation 跟着守卫走（消除 #7）

每个守卫文件**导出一个 `mutations` 数组**（自己的违规样本）：

```ts
export const mutations = [
  { name: "行数 >400", apply: () => …, expect: "① 没有新增的「文件 >400 行" },
];
```

`guard-mutation-check.ts` 改成**收集各守卫导出的 mutations 并逐条跑**（不再手写清单、不再硬编码路径）。
→ **新增守卫 = 新增文件，它的变异用例自动被跑到**，不会漏。

### 3.4 脚本收敛（消除 #8）

- **合并为一个** `test:guards`（跑三条）→ 接进 `test:all`；
- 保留 `test:guard-mutation`（改源码，不进 gate）；
- **删掉** `test:arch-guards` / `test:ui-guards` / `test:color-guard` 三个独立脚本
  （需要单独跑时用 `tsx tools/.../xxx.test.ts` 即可，不值一个 npm 别名）。

### 3.5 明确**不合并**的两处

| 保留 | 理由 |
|---|---|
| `tools/gate6/production-audit.ts` | 它查的是**生产数据**（打线上公开接口），不是源码 —— 触发时机、失败含义、修复方式都不同。硬合并只会让两边都变复杂。 |
| `src/lib/api-route-guards.test.ts` | 它锁的是**鉴权归属**（谁该有鉴权、留痕登记），属既有的 38 套之一，与这三条源码守卫无重叠。 |

## 四、预期收益

| 维度 | 现状 | 方案后 |
|---|---|---|
| 三条守卫总行数 | 358 | **≈ 190**（骨架 80 + 三个判据各 ~35） |
| `walk()` / `check()` / 基线逻辑 | 各 3 份 | **各 1 份** |
| 色板真源 | 2（globals + 手写数组） | **1（globals）** |
| 新增一条守卫的成本 | 抄 60 行骨架 + 改 mutation 清单 + 加脚本 | **只写判据 + 导出 mutations** |
| 「新守卫没被验证过」的风险 | 高（靠人记得改清单） | **归零**（自动收集） |
| 今天那种「改坏守卫」的概率 | 高（3 份骨架、2 处写基线） | 低（1 处入口、1 份骨架） |

## 五、潜在风险与对策

| 风险 | 对策 |
|---|---|
| 重构时**改坏守卫的判据本身**（比改坏代码更危险，因为它会静默放行） | 先把 `test:guard-mutation` 跑通并记录 9/9；重构后再跑，必须仍是 9/9 |
| kit 抽得太"聪明"（过度设计） | 只抽**已经重复三遍**的四样东西（walk / check / baseline / palette）；**不**做插件系统、不做配置 DSL |
| 合并脚本后无法单独跑某一条 | 单条仍可直接 `tsx <文件>`；npm 别名只留两个 |
| 基线格式变化导致历史基线失效 | 一次迁移：kit 读取旧格式并自动转换，转换后删旧字段 |

## 六、落地顺序（建议）

1. **抽 kit**（不改任何判据，只搬家）→ 跑 `test:guard-mutation`，必须 9/9；
2. **色板搬家**（`PUBLIC_EXTRA` → globals）→ 跑 color-guard，色板外计数应**下降**；
3. **mutation 改为自动收集** → 跑，仍须 9/9；
4. **脚本收敛**（一个 `test:guards`）+ 文档更新；
5. 每一步单独提交、单独回滚。

## 七、一句话总结

**今天最大的教训是"判据写宽 = 守卫失效"，而这份梳理要解决的是它的孪生问题：
"实现写重 = 改坏的概率上升"。** 358 行里真正属于"判据"的只有约 90 行，其余都是重复的脚手架。
