# 架构重构 · 开发计划 v1.0（待确认）

> 2026-10-17。本计划**不改任何业务规则**，只做结构与界面层。
> 依据：`19-平台架构重构方案_v1.0.md`（诊断与目标结构）。
> **状态：等待负责人确认后执行。**

## 一、目标与范围

### 目标（三条，按优先级）

1. **结构可读**：任何人在不读代码的情况下，能靠目录名找到「报名/赛制/赛程/赛果」；
2. **观感统一**：页面之间不出现「同一件事两种写法」，为"接近官方级"打底；
3. **改动可控**：每条规则只有一处实现，改一处不再需要全仓库 grep。

### 范围

| 做 | 不做 |
|---|---|
| 目录与分层重组（搬家） | 不重写业务逻辑、不改规则口径 |
| 领域层与 React 解耦 | 不换技术栈（Next.js + Tailwind 保留） |
| 页面骨架与组件库 | 不加新功能（AI、直播、开放 API 都不做） |
| 公开页改版 | 不做多游戏抽象 |

### 排期约束（已按负责人 2026-10-17 的答复修订）

**赛事期间也可以改动**（负责人明确「不需要绕开，在赛事期改动也没关系」）。
但每批仍保持四条纪律：**单批单提交、可单独回滚、门禁与 CI 全绿、合并后跑一次生产冒烟**
（`npm run ops:audit-production`）。阶段仍按**依赖顺序**推进，不再按日期卡点。

## 二、功能模块拆解

### 领域层（L1，七个）

| 领域 | 包含什么 | 现在的落点 | 目标规模 |
|---|---|---|---|
| 身份 identity | 参赛者令牌、管理员会话、裁判凭证 | `participant-auth` `referee-auth` `lib/referee` 部分 | 5–8 文件 |
| 赛事 event | 赛事配置、阶段、赛制模板、规则库 | `site-config*` `format-templates` `stage` `rule-library` | 8–10 |
| 报名 registration | 报名、名单、冻结、队伍状态 | `registration-*` `public-roster` `participant-recovery` | 8–10 |
| 赛制 format | 抽签、对阵、晋级 | `bracket-*` `staged-format` `team-swap` `format-data/support` | 8–10 |
| 赛程 schedule | 排期、改期、版本 | `schedule-*` `bulk-schedule` `schedule-policy` `schedule-mode` | 10–12 |
| 赛果 result | 报分、校验、证据、BP | `result-*` `reporting-*` `evidence-*` `bp-*` `lib/referee/*` | 10–12 |
| 内容 content | 公告、站点内容、发布检查 | `site-content-*` `publication-check` | 4–5 |

**每个领域固定 `types / policy / ops / service` 四件套**（超过就再按子域拆，不混职责）。

### 其余层

| 层 | 模块 | 目标 |
|---|---|---|
| L2 应用 | 抽签发布 / 晋级推进 / 批量排期 / 改期 / 报分 | 5 个用例文件，唯一允许跨领域 |
| L3 接口 | 35 个路由 + 4 个 hooks | 路由只解析与返回；hooks 移到 `src/hooks/` |
| L4 界面 | 14 个页面 / 25 个组件 | 页面 = 骨架 + 功能组件；单页面 ≤300 行 |
| L0 内核 | 数据访问 / 鉴权 / 审计 / 缓存 / 限流 / 配置 | 收拢，只有它碰存储 |

## 三、阶段与优先级

> 阶段按**依赖**排，不按日期排；每阶段有明确的"建议窗口"（以赛事节点为界）。

### 阶段 0 · 护栏先行 ✅ 已完成（2026-10-17）

**为什么先做这个**：搬家之前必须先有"搬错了会红"的守卫，否则改 import 只靠人眼。

- 三条新守卫：
  1. **依赖方向守卫**：解析 import，L4 不许直接 import L0；L1 不许 import React；
  2. **行数守卫**：单文件 >400 行、单页面 >300 行即报告（先只报告不拦，见阶段 2 再转拦截）；
  3. **命名守卫**：`lib/` 下出现 `use[A-Z]` 即红（hooks 不许住领域层）。
- 交付物：`tools/arch/arch-guards.test.ts` + `tools/arch/arch-baseline.json` + 接入 `test:all`（第 37 套）。
- **实测基线（2026-10-17）**：超限文件 **24** 个、`src/lib` 里的 hooks **4** 个、跨层 import **24** 处。
- 三条守卫都已做**变异验证**（各造一个违规 → 对应项变红；还原 → 3/3）。

### 阶段 1 · 领域归位（赛事期间可做，纯搬家）

按**风险从低到高**分五批，每批一个提交、可单独回滚：

| 批次 | 搬什么 | 风险 | 说明 |
|---|---|---|---|
| 1-1 | `content`（公告/站点内容） | 最低 | 无人依赖，最先做 |
| 1-2 | `identity`（令牌/凭证） | 低 | 只被路由与领域用 |
| 1-3 | `registration` | 中 | 玩家侧在用 |
| 1-4 | `schedule` + `format` | 中 | 核心，测试最多，靠测试兜 |
| 1-5 | `result`（含 `lib/referee` 合一） | 最高 | 三处合一，放最后 |

每批的固定动作：建新目录 → 移动文件 → 改 import（只改路径不改逻辑）→ 门禁全绿 → 提交。

### 阶段 1.5 · 领域层内部细化（建议稿已存档，**不在当前执行范围**）

## 七、验证与验收标准

### 每批必过的通用门槛

1. `CODEBUDDY_SAFE_DELETE_ENABLED=0 npm run gate` → **EXIT=0**（36 套 + 构建）；

4. 生产冒烟：`npm run ops:audit-production` 通过（只在合并到 main 后跑）。
