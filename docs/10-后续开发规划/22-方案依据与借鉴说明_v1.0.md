# 方案依据与借鉴说明 v1.0

> 2026-10-17。**用途**：说明 `19 架构重构`、`20 开发计划`、`21 领域层细化` 三份方案
> **各自的方法论来源**，以及**取用了什么、如何适配、哪里没有照搬**。
> 原则：**借鉴方法论，不搬运代码与目录结构**。本仓库没有引入任何第三方源码。

## 一、本机 skill（我实际读过并在用的）

| 来源 | 取用的方法 | 在本仓库的落点 | 适配调整 |
|---|---|---|---|
| **`impeccable`**（本机 skill） | ① 动手前先定四件事：受众、用例、品牌调性、**差异化那一个点**；② **The AI Slop Test**（先排除"一眼像 AI 拼的"观感）；③ Tone 要选一个极端，不选"安全中间值" | 阶段 3 设计系统、阶段 4 公开页 | 它的工作流面向"从零做一个前端"；我们已有 `--adm-*` 令牌与既定视觉语言（暖白 + 墨线 + 品牌红、禁圆角），所以**只取"先定调性再动手"和"slop test"两条**，不重做视觉体系 |
| **`quality-gate-setup`** | ① **先审计再写 YAML**；② **测试文件数 vs npm 脚本数** 对不齐是最常见的缺口；③ **一条命令、本地与 CI 共用**；④ ★「**门禁绿了部署仍可能红**：CI 环境与运行时环境的盲区」 | 现有 `npm run gate`（37 套）、阶段 0 的守卫 | 我们早已在跑 ①③；④ 这一条**被本仓库真实验证过**（CI 无平台环境变量）—— 所以本次新增守卫全部是**纯静态扫描**，不依赖运行时环境，避免引入同一类盲区 |
| **`production-runbook-setup`** | ① **第 0 步先判断该不该做**（拒绝过度建设）；② 健康接口 200 ≠ 业务正常；③ 输出里禁止出现地址/密钥/表名 | 运维三件只读命令、生产冒烟 | 直接采用了它的第 0 步判断法 —— **据此否掉了"生产监控"**（赛事三周、单人运维、当时无推送通道），只留备份校验与线上巡检 |

> 这三份 skill 是**方法来源**，不是代码来源。它们没有一行代码进入本仓库。

## 二、开源项目（取方法论，不取实现）

| 来源（开源项目 / 公开方法） | 取用的思路 | 在本仓库的落点 | 明确**没有**照搬的部分 |
|---|---|---|---|
| **ArchUnit**（Java，开源） | **架构规则写成测试**：依赖方向不允许的 import 直接让构建失败 | `tools/arch/arch-guards.test.ts` 的三条守卫 | 它分析字节码与包依赖图；我们做**源码正则扫描**（TypeScript + 无新增依赖），规则也从"包级"降为"目录级 + 三条具体规则" |
| **Rubocop 的 `.rubocop_todo.yml`**（开源工具的做法） | **债务基线**：把存量违规记进 todo 文件，规则只允许减少、不允许新增 | `tools/arch/arch-baseline.json` 的基线棘轮 | 只借了"基线只减不增"这一个模式；没有引入 Rubocop，也没有照抄它的文件分层 |
| **Spring Modulith**（Java，开源） | **模块边界可校验**：模块之间只允许声明过的依赖，越界即报错 | L1 七个领域「横向不互相依赖」的规则 | 它是运行时框架（要引依赖、改启动方式）；**我们只把规则写进静态守卫**，不引入任何运行时 |
| **Clean Architecture**（Robert C. Martin，公开著作） | **依赖方向规则**：依赖只能指向内层；跨越层要经过接口 | 五层（L0–L4）、"L4 不许直接碰 L0" | 没有照搬它的四层命名与用例交互器结构；我们的层按本项目实际裁剪成五层 |
| **Domain-Driven Design / Implementing DDD**（Evans / Vernon，公开著作） | **聚合边界**：一次事务只改一个聚合；聚合根是不变量的唯一守卫点 | `21 领域层细化`：`Match` 作聚合根、`ScheduleState` 拆细 | **明确不取** CQRS 与事件溯源（见该文档第五节）；也不做"每个领域都完整 DDD" |
| **shadcn/ui**（开源组件集合） | **组件代码归你所有、可改**（不是装一个黑盒组件库） | 阶段 3 的 `ui/shell`、`ui/data` | 我们没有引入它（项目已有 Tailwind 与自己的令牌），只借"**组件可改造、不做黑盒**"这个取向 |
| **start.gg / Toornament / Challonge**（赛事平台，公开产品） | 公开页的**信息架构**：赛事 / 赛程 / 战队 / 赛果四条主线 | 阶段 4 公开面 | ⚠️ **我没有逐页比对过它们的界面**，只把它作为"四主线结构"的体感参照；具体版式是本项目自定，不是仿制 |

## 三、哪些判断**不是**外部依据，而是本项目的判断

为避免"拿外部名词给自定决策背书"，单独列出：

| 决策 | 依据 |
|---|---|
| 五层分成 L0–L4、七个领域的切法 | **本仓库现状**（`lib/scheduling` 里实际住着什么）反推 |
| 阈值 **400 行 / 300 行** | 我按现有五个最大组件的体量（609–947 行）拍的经验值，**没有外部标准** |
| 基线选三项（行数 / hooks 位置 / 跨层 import） | 对应本仓库已有的三类问题，不是"DDD 必须有"N 项 |
| 赛事期间是否可以改代码 | **你的决定**（2026-10-17：「不需要绕开」），不是任何方法论 |
| 不做 CQRS / 事件溯源 / 实时直播 / 开放 API | 校园赛规模 + 单人运维，属**范围裁剪**，与外部最佳实践无关 |

## 四、怎么保证"有据可依"而不是"拼凑"

1. **每条建议都要能指回一个本仓库事实**：`19` 的诊断全部带代码位置与行数；`21` 的每条问题都附"代码事实"列。
   方法论只用来**解释为什么这样切**，不用来替代事实。
2. **每个外部来源都要写"没有照搬什么"**：见上面两张表的最后一列 —— 这一列比"借鉴了什么"更能防照抄。
3. **能落成守卫的才写进计划**：无法验证的建议（例如"更优雅"）不进阶段，只留在讨论里。
4. **不允许出现"某项目这么做所以我们这么做"**：如果一条规则没有本仓库的事实支撑，就不写进方案。

- 新的方案文档若引用外部方法，**必须在开头登记**：来源 / 取用 / 适配 / 不照搬；
