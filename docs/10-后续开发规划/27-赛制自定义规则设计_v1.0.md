# 赛制自定义规则设计 v1.0（方案稿，待确认）

> 2026-10-19。负责人要求：「赛段数量和类型自定义、参赛队伍/人数适配赛制高度自定义，
> 做成一个高度自定义的赛制规则，而非现在这样捆绑某一套。」
> **本稿只定规则模型与约束，不写实现。**

## 一、先收束一件事：只做无畏契约

现状**已经是单游戏**：地图 / 段位 / 位置 / 首发人数等游戏数据单源在 `lib/games/valorant.ts`，
赛事级 `game` 字段目前**并不驱动取值**（全部取默认款）。
→ 收束的实际动作是：**不再为"多游戏"预留抽象**（不建 `GameConfig` 注册表、不做按游戏切换）。

## 二、现状：捆绑在哪

| 层 | 现在是什么 | 问题 |
|---|---|---|
| 段类型 | 5 种：`single-elim` / `double-elim` / `gsl-groups` / `single-elim-groups` / `round-robin` | **`round-robin` 只有类型、没有构建器**（写了会掉进空分支） |
| 轮次引擎 | 4 个：单败 / 双败 / GSL / 小组单败 | **瑞士轮完全不存在** |
| 复合赛制 | 4 个**写死的预设**：`staged-playin`(32) / `staged-direct`(16) / `single-elim-groups`(8) / `group-single-elim`(16) | 办赛者只能四选一，不能组合 |
| 队伍数 | 各预设内部写死（28 队直进 + 4 队资格赛 = 32） | 换数量就要改代码 |

**结论**：现在不是"可配置"，是"四套模板"。要做高度自定义，缺的是**两件事**：
① 一个把段串起来的**模型**；② 两个缺的轮次引擎（瑞士轮、循环）。

## 三、目标模型：赛段链（stage chain）

办赛者定义一串**赛段**，每段声明"进来几支、打什么、出去几支"：

```
Stage {
  name      赛段名（如「入围赛」）
  type      轮次引擎：single-elim | double-elim | round-robin | swiss | gsl-groups | single-elim-groups
  entrants  进入本段的队伍数（首段由报名决定，后续 = 上一段的晋级数）
  bo        bo1 | bo3 | bo5（单败/双败的每轮可再细分）
  advance   晋级几支 + 去向（下一段 / 淘汰）
  groups    仅分组类段需要：小组数、每组队数
}
```

**三条守恒（校验的核心）**：
1. **入口守恒**：首段 `entrants` = 报名确认队伍数；后续段 `entrants` = 上一段 `advance`；
2. **出口守恒**：最后一段 `advance` = 1（冠军）；
3. **容量守恒**：每段的 `entrants` 必须被该段类型**整除或可轮空**（见第五节）。

**这条模型能表达现在全部四套预设**（见第六节）—— 这是设计成立的前提：
新模型不是推翻现状，是**把现状变成预设**。

## 四、段类型的适用条件

| 类型 | 入口数要求 | 特点 | 备注 |
|---|---|---|---|
| **单败** | 任意（非 2 的幂自动轮空） | 场次最少 | 现有构建器可用 |
| **双败** | 建议 8 / 16 / 32（2 的幂） | 更公平、场次约 2 倍 | 现有构建器可用 |
| **GSL 小组** | 4 × 组数 | 每组 2 出线、场次固定 | 现有构建器可用 |
| **小组 + 单败** | 4 × 组数 | 小组循环后交叉淘汰 | 现有构建器可用 |
| **循环** | 任意（组内 ≥3 才有意义） | 场次 = n(n−1)/2，队多会爆 | **构建器缺失** |
| **瑞士轮** | ≥8，建议 8/16/32 | 场次 = 轮数 × n/2，强弱自动相遇 | **引擎缺失** |

## 五、队伍数量 → 可选赛制（这是他问的"16-24 可选哪些"）

按"能不能整除 / 要不要轮空 / 总场次是否可控"分档：

| 队伍数 | 推荐首选 | 可行的组合 | 不建议 |
|---|---|---|---|
| **8–15** | 双败（8）或单败 | 单败 / 双败 / 瑞士(8) / 2 组×4 | 三赛段（人太少，撑不起） |
| **16–24** | 小组赛 4×4→8 + 淘汰(8) | 单败16 / 双败16 / 瑞士(16) / 4组×4 + 淘汰 / 2组×6~8 + 淘汰 | 瑞士轮 24 队需 5 轮（场次 60，1 天打不完） |
| **25–32** | **两段**：入围(32→16) + 淘汰(16) | 单败32（轮空） / 双败16（需先筛） / 8组×4 + 淘汰16 / 瑞士(32→16) | 单段双败 32（场次 62，赛程过长） |
| **33–48** | **两段**：资格赛(多出的队) + 32 正赛 | 资格赛 BO1 单败 + 32 队正赛 | 直接 48 队单败（轮空过多、强弱悬殊） |
| **48+** | 断言不支持 | — | 校园赛规模下不现实 |

**每一档的"可行组合"都要被校验器放行、档外组合被**明确拒绝并给出理由**（不是静默失败）。

## 六、现状四套预设如何映射到新模型（迁移可行性证明）

| 预设 | 新模型下的表达 |
|---|---|
| `staged-playin`(32) | 段1 资格赛 单败 BO1（28+4 → 4）；段2 入围 单败 BO3（32 → 16）；段3 小组 GSL（16 → 8）；段4 淘汰 单败 BO5（8 → 1） |
| `staged-direct`(16) | 段1 入围 单败 BO3（16 → 8）；段2 小组（8 → 4）；段3 淘汰（4 → 1） |
| `single-elim-groups`(8) | 段1 小组（8 → 4）；段2 淘汰（4 → 1） |
| `group-single-elim`(16) | 段1 小组 4×4（16 → 8）；段2 淘汰（8 → 1） |

**四套全部可表达** → 新模型是**超集**，老赛事的数据不需要迁移（`stageConfigs` 已经是数组）。

## 七、需要补的引擎（工作量真正的来源）

1. **瑞士轮**（`swiss`）：轮数 = ⌈log2(n)⌉；每轮按战绩配对、不重复对阵；需要"同分对同分"的配对器。
   **这是新增**，现有代码一行都没有。
2. **循环赛**（`round-robin`）：单循环 / 双循环、组内排名（胜场 → 净胜局 → 相互战绩）。
   类型存在但无构建器，**要补**。
3. **校验器**（`validateStageChain`）：三守恒 + 第五节矩阵 → 返回"哪一段不成立、为什么"。

## 八、与现有代码的关系（不动的地方）

- `stageConfigs[]` 已经是**数组**且已存库 → **数据形状不用改**，只是"能填更自由的组合"；
- 现有四个构建器**全部复用**，不重写；
- 抽签 / 排期 / 报分**不需要改**（它们按场次工作，不关心赛段怎么来）。

## 九、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **表达力上去，误配也上去** | 办赛者能配上"32 队单段双败"这种打不完的赛制 | 校验器**硬拦** + 给"推荐组合"按钮 |
| 瑞士轮配对是最难的一块 | 同分不重复、轮空处理 | 先做**固定轮数 + 简单配对**，不做精细的 Buchholz 分 |
| 多段赛的"何时进入下一段" | 现在是人工推进阶段 | 复用现有的阶段推进（`advance-stage`），不新增机制 |
| 观感与配置界面的复杂度 | 段多了配置页会很重 | 配置页只显示"当前档位推荐的组合"，高级编辑折叠 |

## 十、建议的实施顺序

1. **先做校验器**（纯函数 + 单测）：给定一串段，判断是否成立、在哪一段不成立；
2. **把现在四套预设用新模型重写一遍**（行为完全不变，靠 39 套测试兜）—— 这一步证明模型够用；
3. **补循环赛引擎**（简单、场次可控）；
4. **补瑞士轮引擎**（最难，单独一步）；
5. 最后才动配置界面（让办赛者自由编排）。

**第 1、2 步不改变任何现有行为**，可以先做；第 3、4 步是纯新增引擎；第 5 步才是界面。

## 十一、需要你定的三件事

1. **第五节的档位划分**认不认可（16–24 / 25–32 / 33–48 的边界与推荐组合）？
2. **瑞士轮**要不要做（它是唯一需要"配对算法"的段类型，工作量最大）？
3. 配置界面的**自由度**：只给"档位推荐组合"（安全），还是允许完全自由编排 + 校验器兜底（灵活但可能误配）？
