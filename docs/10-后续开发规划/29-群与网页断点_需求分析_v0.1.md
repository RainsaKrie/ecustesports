# 群与网页的断点 —— 需求分析 v0.1（待负责人确认）

> 2026-10-19。负责人明确了目的与流程：
>
> **目的**：「降低赛事群与网页之间的隔阂或者说**断点**，让参赛体验更流畅、简单。」
> **流程**：可行性分析 → **需求分析** → 功能设计 → 实现。**不要一开始就到设计。**
>
> 本稿只做**需求分析的第一步：把断点找出来**。断点确认之前，不讨论怎么做。

## 一、先分清两端各自的角色

| | 群（QQ / 微信） | 网页 |
|---|---|---|
| **强在哪** | 即时触达、谁都在、说话方便 | 唯一可信数据源：名单、赛程、赛果、报名状态 |
| **弱在哪** | 信息会沉、口径会乱、找不到历史 | 要主动打开，没人提醒你该看 |
| **参赛者的真实动作** | 在群里问"我打谁""几点""算谁赢" | 偶尔打开网站查一次 |

**断点的本质**：**群负责"知道"，网页负责"准"** —— 两边不通，同一件事要说两遍、查两遍。

## 二、候选断点（需要负责人确认哪些是真的）

| # | 断点 | 现在怎么发生 | 涉及角色 |
|---|---|---|---|
| **A** | **群 → 网页没有入口** | 群里说"去官网看"，没人贴链接、没有二维码；手机上要自己搜 | 参赛者 |
| **B** | **网页 → 群没有入口** | 网站有群号 `1107657580`，但**没有二维码**，也没有"进群干嘛"的说明 | 参赛者 |
| **C** | **赛程变更传不到群里** | 网页上改完，群里靠人工喊一遍；喊漏了就有人跑空 | 主办方 → 参赛者 |
| **D** | **赛果要人工播报** | 网页有赛果，但群里还要再发一次"X 队赢了" | 主办方 |
| **E** | **约赛要跨两处** | 队伍先在群里私聊约时间，约完再回网页提交申请 —— **同一件事走两遍** | 参赛者 ↔ 参赛者 |
| **F** | **参赛管理码要靠人自己保管** | 码在群里或私聊发，丢了要找回；网页登录要手输 | 参赛者 |

**我的判断（待你确认）**：
- **E 是最重的断点** —— 它是**双向往返**（群里约 → 网页提交），而且发生在**参赛者之间**，主办方帮不上忙；
- **A / B 最便宜** —— 只是缺入口；
- **C / D 是主办方的人工负担**，但技术上受限（见可行性调查：QQ 官方机器人不能主动推送）。

## 三、需要负责人回答（这决定需求范围）

1. **哪几个断点是真让你或选手难受的？** 上面 A–F 哪些是真的、哪些是我臆想的？
2. **最烦的是哪一个？** 如果只能解决一个，你选哪个？
3. **主要痛在参赛者一侧，还是主办方一侧？**（决定做"选手体验"还是"运营减负"）
4. **约赛（E）现在的真实流程是什么？** 群里怎么约、约完谁去网页提交、有没有约完忘提交的？

> **这四个问题只能你回答** —— 属于你亲手办赛的经验，我不能推算。

## 四、暂不做的事

在断点确认之前，**不讨论**：用哪个平台、怎么对接、要不要机器人、接口怎么设计。
那些是"功能设计"，排在需求分析之后。

## 五、与可行性调查的关系

`28-QQ微信接入 —— 可行性调查 v0.1` 已给出平台侧的限制（QQ 官方机器人不能主动推送、
企业微信需要主体、公众号周期长）。**那份是"能不能"，这份是"要不要、要什么"**。
两者都齐了，才轮到"怎么做"。
