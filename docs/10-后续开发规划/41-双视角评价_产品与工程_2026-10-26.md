# 双视角评价：产品 / 工程（2026-10-26）

> 对象：华理瓦理杯赛事平台（ecustesports.top）。
> 规模：约 1.78 万行 TS/TSX、31 个页面、35 个 API、63 个测试脚本、1139+ 条断言。
> 真实数据：36 队 / 205 人 / 42 场（资格 4 + 入围 16 + 小组 8 + 淘汰 14）。
>
> 两份评价都只写**这个平台实际存在的东西**，不套通用模板。

---

# 第一部分 · 产品负责人视角

## 一、结论

**这是一个"运营工具"，不是"赛事平台产品"。**

它解决的是一个非常具体的痛：**一个人办 32 队规模的电竞比赛，信息流全在群里，靠人肉搬运。**
平台把这个流程收进了一处，做到了"一个人能独立办完整届比赛"。

**它的价值不在功能多，在于"把一个多角色协作流程压缩成一个后台"。**
报名、抽签、排期、报分、晋级、BP、改期审批、裁判派单、通知 —— 这些原本需要 3-5 个人分工的事，
现在一个人加几个裁判就能跑完。

**但它现在的形态决定了它的天花板**：单租户、单赛事范式、强依赖赛事负责人本人。
**它不是一个能直接卖的产品，是一个能直接复用的能力。**

## 二、目标用户与定位

| 维度 | 现状 | 判断 |
|---|---|---|
| 核心用户 | **赛事负责人**（就是作者本人） | 极其聚焦，但只有 1 个真实用户 |
| 次要用户 | 裁判（凭证登录）、参赛队伍（公开页） | 裁判端已成型，队伍端只是"看" |
| 实际解决的问题 | 信息流分散、人工转录、改期混乱 | 真问题，且已被验证（42 场跑通） |
| 不是它的目标 | 选手社交、战队管理、观赛体验、商业化 | 明确不做，是对的 |

**定位的优点**：不做大而全，只做"办赛"这一段，所以每个环节都够深。

**定位的风险**：**它的可用性等于"赛事负责人愿意学一个后台"。**
如果换一个不熟悉它的人来办赛，学习成本会很高 —— 界面虽然清楚，但**概念密度很高**
（阶段、轮次、签位、轮空、冻结、凭证、BP、改期审批…）。

## 三、核心功能完整度

**完整闭环，且每一环都有"防呆"设计**，这是它最强的部分：

| 环节 | 成熟度 | 亮点 |
|---|---|---|
| 报名 | 高 | 首发 5 人强校验、队长确认、改资料申请审批 |
| 抽签 | 高 | 种子池、段位排序、"一不打二"、同组不同半区 |
| 排期 | 高 | 冲突检测（场地/时间/队伍）、冻结机制 |
| 报分 | 高 | 裁判凭证、幂等、版本冲突 409、证据链 |
| 晋级 | 高 | 胜者/败者双路推进、待定席位自动填充 |
| BP | 中高 | 逐步 Ban/Pick、地图关系校验 |
| 改期 | 高 | 申请-审批-再校验闭环，改动留痕 |
| 通知 | 中 | 草稿生成，未接真实下发 |
| 分组积分 | 高 | 胜场-小分-相互战绩三层 |

**完整度的短板**：
- **通知只到"生成草稿"**，没有真实下发（微信群/QQ 群）—— 而"通知"恰恰是作者最想解决的痛点之一；
- **队伍端只能看**，不能自己提交赛果、申请改期（改期是队长发起的，但入口和体验不成体系）。

## 四、差异化

**真正的差异点只有一个：它懂赛制。**

市面上通用赛事工具（Challonge / Toornament / Battlefy）能做单败双败，
但**它们不懂"36 支队怎么按段位分档进资格赛"、"轮空为什么不能增加容量"、"取消一场决赛之后名次怎么算"**。

**这个平台把这些赛事规则写成了代码里的约束** ——
抽签有下限 17 上限 32 的硬门槛、轮空是配比开关、晋级链自动推进、
甚至"取消组内决赛后按平均段位定名次"这种规则都能落地。

**这是通用工具做不到的，也是它唯一真正的壁垒。**

## 五、体验与交互

**优点**：信息密度高、状态一目了然、危险操作有二次确认、错误提示带原因。
**短板**：
- **概念门槛高**：一个新人打开抽签页，要同时理解"阶段/签位/种子池/轮空/冻结"；
- **管理端页面偏多**（12 个），缺少一个"今天该做什么"的入口 —— 作者是靠自己知道流程；
- **移动端体验未知**（没有真机验证条件）。

## 六、商业模式与增长

**诚实结论：当前形态没有商业模式，也不该现在有。**

它的成本结构是：Vercel 免费 + Supabase 免费 + 一个人维护。
**换成 10 个学校用，边际成本几乎为零，但支持成本会爆炸** ——
每所学校都要重新配赛制、教学、处理特例。

**可能的三条路**（按现实性排序）：

1. **模板化**（最现实）：把它变成"赛事运营方法论 + 一套可复用的赛制模板"，
   打包给其他高校社团。**卖的是流程，不是软件。**
2. **SaaS 化**（中等）：多租户、自助开赛、赛制市场竞争。**要解决"每个学校赛制都不一样"这个根本问题。**
3. **开源 + 影响力**（最轻）：作为作品公开，换取行业认知。**对求职价值最大，商业价值最小。**

**我的判断：现在最该做的是第 1 条和第 3 条的组合** ——
**它最大的价值是证明"这个人能把复杂运营流程产品化"，不是"这个软件能卖钱"。**

## 七、竞品对比

| 类型 | 代表 | 它有什么 | 这个平台有什么 |
|---|---|---|---|
| 通用赛事工具 | Challonge / Toornament | 成熟的淘汰赛编排、多语言、公开赛 | **懂具体赛制**、裁判端、报名审核、改期审批 |
| 校园社团自建 | 各校 Excel + 群 | 零成本、灵活 | 自动化、防错、留痕 |
| 商业电竞赛事系统 | 各厂内部系统 | 直播/观赛/商业化 | 轻量、可自部署、无 vendor 锁定 |

**它不在任何一个成熟品类里竞争** —— 它抢的是"Excel + 群"的位置，
而这个位置的用户**最不愿意为软件付费**。这是它商业化的根本障碍，不是产品缺陷。

## 八、产品侧改进优先级

| 优先级 | 事项 | 为什么 |
|---|---|---|
| **P0** | **把"通知"真正打通**（QQ 群机器人） | 这是作者最初的痛点，也是唯一还没闭环的一环；QQ 官方机器人门槛低、免费 |
| **P0** | **管理端加"今日待办"入口** | 12 个页面靠人记流程，换人就断 |
| P1 | 队伍端自助（查赛程/改期申请/看证据） | 减少负责人 80% 的重复问答 |
| P1 | 赛制模板化（把本届赛制存成可复用模板） | 换届、换校的成本从"重配"降到"选模板" |
| P2 | 移动端适配验证 | 裁判在现场大概率用手机 |
| P2 | 数据看板（场次完成率、平均报分耗时） | 复盘和对外讲述都需要数字 |

# 第二部分 · 工程视角

## 一、结论

**工程质量明显高于"一个人 + AI 协作"的典型水平，但结构上带着明显的"生长痕迹"。**

最突出的三点：

1. **测试密度罕见** —— 63 个测试脚本、1139+ 条断言，覆盖规则、守卫、构建、样式语法、
   文档一致性。**这在个人项目里极少见，是它最值钱的工程资产。**
2. **架构守卫成体系** —— 文件行数棘轮、分层依赖检查、路由鉴权归属、审计留痕归属、
   CSS 语法、文档与代码数字一致。**它不靠自觉，靠门禁。**
3. **缺陷是"长出来的"，不是"设计坏的"** —— 同一概念被复制多份（场次校验曾 8 处）、
   阶段名与逻辑耦合、`StageConfig` 两个同名不同义的定义。

## 二、技术选型

| 项 | 选择 | 评价 |
|---|---|---|
| 框架 | Next.js（App Router） | **合适**。SSR 让公开页首屏快，API Route 省掉独立后端 |
| 数据 | Supabase（Postgres） | **合适**。免费额度够 160 人赛事，RLS + 迁移脚本可控 |
| 部署 | Vercel | **合适**。零运维，Preview 环境可用 |
| 样式 | Tailwind + CSS 变量分层 | **合理**。`--pub-*` / `--adm-*` 两套令牌，主题切换干净 |
| 测试 | 自建脚本（tsx 直跑） | **取舍正确**。不用 Jest/Vitest，启动快、无配置负担 |

**选型的合理性在于"约束匹配"**：一个人维护、免费、要能上线、要能长期跑。**没有为技术而技术。**

**唯一的遗憾**：没有用 ORM（Prisma/Drizzle），而是手写 SQL + 一个薄的 data-store 抽象。
在只有 35 个接口时这不构成问题，但表一多就会开始痛。

## 三、代码质量与可维护性

**好的部分**：
- 领域逻辑集中在 `src/lib/domains/`，按业务域分目录（registration / schedule / result / identity）；
- 纯函数 + 可测试，赛制推导、晋级推进、分组积分都是无副作用的；
- 注释写"为什么"，不是"是什么" —— 例如 `event-progress.ts` 开头解释了为什么需要单独一份进度判定。

**问题**：
- **8 个文件超过 400 行**，最大 `FormatDrawWorkspace.tsx` 约 980 行；
- **同一概念多次定义**（已修一部分）：场次公式曾有两份且默认值不同、阶段关键词曾有三份；
- **两个 `StageConfig` 同名不同义**（赛制阶段 vs 运营阶段），读代码时容易误判。

## 四、性能与稳定性

**已做的**：
- 公开页 SSR + 短缓存，API 大量 `force-dynamic`；
- 后台同步做了「在途保存计数」，避免用旧快照覆盖新结果；
- 乐观锁（`If-Match` 版本号）+ 内容级护栏（`detectScheduleLosses`）双层防覆盖。

**风险**：
- **没有性能基线**。42 场规模下一切很快，但**没有测过 200 场/500 人的情况**；
- **首屏 JS 偏大**（管理端有多处 800+ 行客户端组件），低端机可能吃力；
- **单点失败无降级**：Supabase 不可用时整个站点不可用（本地文件后端只在开发期存在）。

## 五、可扩展性与工程化

**强项**：门禁、守卫、迁移脚本、文档与代码一致性检查 —— **这套工程化水平超过多数三人团队**。

**弱点**：
- **多赛事支持是"能跑"不是"好用"**：赛制配置能存多份，但很多逻辑仍假设单一赛事范式；
- **赛制表达能力有限**：单败/双败/GSL/组内单败四种，**"4 队组只打 2 场"这种真实需求表达不出来**
  （这正是 10-22 那次连环故障的根源）；
- **没有 CI 跑 e2e**：界面层靠人工看，没有视觉回归。

## 六、安全与数据合规

**已做的（超出预期）**：
- 管理端会话用签名 cookie，服务端校验，不走 `localStorage`；
- 裁判端用**凭证**而非账号，凭证哈希存库，日志里不落明文；
- 所有写路由要求审计留痕（`route-guards` 组 5 强制）；
- 破坏性操作要求填 `reason`，服务端强制；
- 上传做了类型与大小校验。

**缺口**：
- **没有速率限制的实证**（有配置，但没有压测验证）；
- **个人数据（姓名/学号/QQ）没有脱敏导出**，赛后归档时是把整库备走；
- **没有隐私政策/数据保留期限** —— 校园场景影响小，但对外复用就是硬伤。

## 七、协作效率

**这套工程真正的价值在这里**：

一个人 + AI 能维护 1.78 万行、42 场实战，靠的不是写得快，是**门禁挡住了大部分低级错误**。

**但也暴露一个问题**：**门禁能挡住"改错"，挡不住"想错"。**
10-22 那批故障，每一条都过了门禁 —— 因为门禁检查的是"代码符合规则"，
而那批问题恰恰是"规则本身不适用"。

## 八、技术债务清单与优先级

| 优先级 | 债务 | 影响 | 建议 |
|---|---|---|---|
| **P0** | **赛制模型表达不出"少打一场"** | 每次赛事变更都要打补丁，10-22 的根源 | 赛制加"组内是否打决赛"开关，场次推导跟着变 |
| **P0** | **同一判据多处复制** | 改一处漏一处，靠人工 grep 找齐 | 收成一个函数；已加 `test:expected-guard` 棘轮防新增 |
| P1 | `FormatDrawWorkspace` 980 行 | 改不动、测不了 | 拆成"数据层 hook + 若干面板组件" |
| P1 | 无 e2e / 视觉回归 | 界面改动全靠人眼 | 引入 Playwright 截图比对（有环境就必须装通） |
| P1 | 无性能基线 | 规模上来才知道 | 加一个 200 场规模的合成数据压测 |
| P2 | `StageConfig` 同名不同义 | 读代码易误判 | 改名为 `FormatStageConfig` / `EventStageConfig` |
| P2 | 无 ORM | 表多了会痛 | 现在不必引入，等超过 20 张表再说 |

# 总结

**产品侧**：它是一个**把复杂运营流程压缩成一个人可执行**的工具，价值真实、边界清晰。
**最大的短板不是功能，是"通知没打通"和"换人接不住"。**

**工程侧**：**门禁体系是它真正的护城河**，测试密度和守卫覆盖超出个人项目水准。
**最大的债务是"赛制模型表达力不足"** —— 它不产出 bug，但会让每次变更都变成一场补丁战。
