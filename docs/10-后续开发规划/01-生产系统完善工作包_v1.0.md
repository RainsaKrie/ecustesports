# 生产系统完善工作包 v1.0

- 轨道：A
- 目标：在不扩张产品范围的前提下，提高线上稳定性、可恢复性、安全性和移动端任务完成率
- 优先级：高于生产 AI 接入
- 执行原则：真实故障优先，数据正确性优先，关键任务优先，普通视觉优化后置

## 1. 范围判断

### 必须继续完善

- 会导致报名、组队、抽签、排期、BP、报分或晋级无法完成的问题；
- 会造成数据覆盖、越权、错误晋级或无法恢复的问题；
- 手机端无法完成关键操作的问题；
- 生产监控、备份、恢复和发布流程缺口；
- 高风险写操作缺少审计的问题。

### 暂不扩大

- 通用账号中心和复杂组织权限；
- 与当前办赛无关的多游戏平台化；
- 低频统计大屏和运营装饰；
- 通用聊天机器人、自动战报等 AI 功能；
- 不影响任务完成的普通视觉细节。

## 2. SYS-00：冻结基线与建立唯一问题台账

### 目标

让后续所有 AI 从同一个事实基线工作，避免重复修复、覆盖协作者修改或把历史问题当作当前问题。

### 工作内容

1. 拉取远端并确认本地 `HEAD`、`origin/main` 和生产部署对应提交。
2. 运行完整质量门禁并记录结果。
3. 只读检查生产首页、健康接口、登录页和一条公开赛事路径。
4. 汇总真实用户反馈、未解决问题和已修复问题。
5. 建立唯一问题台账，字段至少包含：ID、场景、复现步骤、影响角色、严重度、证据、负责人、状态、关联提交。
6. 将问题分为 P0 数据/安全、P1 任务阻塞、P2 体验、P3 普通视觉。

### 允许修改

- 新建或更新问题台账文档；
- 不修改业务代码。

### 禁止

- 不使用生产数据执行写操作；
- 不重置、清空或重放真实赛事；
- 不凭历史截图直接判定问题仍存在；
- 不顺手修复问题。

### 交付物

- 当前基线提交和部署对应关系；
- 完整测试结果；
- 唯一问题台账；
- 下一波工作包建议。

### 完成定义

- 每个 P0/P1 问题都能被明确复现或标记为待复现；
- 已修复问题不进入待办；
- 生产环境没有被写入或改变。

## 3. SYS-01：统一质量门禁

### 目标

让每个协作者和 AI 的提交在合并前自动执行一致检查，避免只跑单个测试就宣称完成。

### 工作内容

1. 审计现有 GitHub Actions，保留承载测试但不让其代替代码质量门禁。
2. 新增普通提交/PR 使用的质量工作流。
3. 统一脚本，至少覆盖 lint、TypeScript、核心纯函数测试、完整闭环、BP、报名后台、发布、运营、AI 数据基线和构建。
4. 对需要密钥的云端测试与普通 PR 测试隔离。
5. 配置依赖缓存和并发取消，避免重复运行浪费。
6. 工作流失败时显示具体失败步骤。
7. 更新 README 或开发交接说明。

### 建议修改范围

- `.github/workflows/quality-gate.yml`；
- `package.json` 中的聚合检查脚本；
- 最小必要的开发说明文档。

### 禁止

- 不在仓库中写入生产密钥；
- 不让 PR 工作流访问生产 Supabase；
- 不删除现有 Gate6 承载工作流；
- 不借机升级 Next.js、React 或全部依赖。

### 验收清单

- [ ] 对 PR 和主分支推送触发；
- [ ] 普通测试不需要秘密变量；
- [ ] 任一步失败都会阻止整体成功；
- [ ] 本地聚合命令和 CI 命令一致；
- [ ] 构建产物不提交 Git；
- [ ] 完整门禁在当前主分支通过。

## 4. SYS-02：生产监控、备份与恢复值守

### 目标

将 Gate6 的一次性验证转成真实办赛期间可执行的运行手册和轻量检查能力。

### 工作内容

1. 复核健康接口只能证明哪些能力，避免把简单 200 当作业务健康。
2. 定义最小监控项：主页、健康接口、公开赛程读取、错误率、函数响应时间、Supabase 可用性和存储可用性。
3. 设计赛事期检查频率、告警接收人和升级路径。
4. 将备份、校验、恢复演练拆成可执行清单。
5. 对备份文件进行完整性校验，但不得把真实备份提交 Git。
6. 明确 Vercel/Supabase 免费额度和限额接近时的处理方式。
7. 形成发布前、比赛日、赛后归档三个运行清单。

### 建议修改范围

- `tools/gate6/` 下新增只读或安全检查脚本；
- `docs/08-MVP开发/`、`docs/09-测试与复盘/` 中的运行手册；
- 必要时扩展 `/api/health`，但不得泄露内部信息。

### 禁止

- 不在脚本中硬编码生产密钥；
- 不自动删除、恢复或覆盖生产数据；
- 不把外部监控服务强行加入项目依赖；
- 不把管理员登录或写操作作为周期性健康探测。

### 验收清单

- [ ] 新负责人能够只按文档完成一次备份和只读校验；
- [ ] 恢复演练仅在隔离环境执行；
- [ ] 监控失败有明确接收人和处理动作；
- [ ] 健康输出不包含 URL、密钥、表名或错误堆栈；
- [ ] 比赛日可以在 5 分钟内判断是前端、Vercel、Supabase 还是网络故障。

## 5. SYS-03：手机端关键路径回归与修复

### 目标

保证真实用户在常见手机宽度下完成任务，而不是只保证页面没有横向滚动条。

### 关键路径

玩家侧：

1. 首页进入当前赛事；
2. 未识别身份时报名或找回；
3. 已报名时查看报名资料；
4. 创建队伍、搜索队伍、按首发/替补/教练申请加入；
5. 队长处理申请和邀请；
6. 查看下一场、约赛状态和 BP 入口；
7. 查看公开赛程、赛果和对阵。

管理员侧：

1. 登录；
2. 选手审核；
3. 队伍名单确认；
4. 抽签；
5. 排期、约赛审批、BP、报分；
6. 赛事阶段和公开状态管理。

### 工作内容

1. 建立 360×800、390×844、430×932 和桌面视口检查矩阵。
2. 为关键路径记录可点击目标、首屏主任务、遮挡、溢出、键盘弹起和长文本表现。
3. 优先修复无法完成、按钮不可见、输入被遮挡、布局重叠和误导性入口。
4. 表格在移动端优先转换为信息卡或优先级列，不简单缩小字体。
5. 对阵图允许内部浏览时，页面本身不得横向溢出，并提供清晰操作提示。
6. 长游戏 ID、长队名和中文/英文混排必须纳入测试。
7. 增加关键断言；截图只用于视觉复核，不替代操作结果验证。

### 文件边界

- 可以修改玩家与管理员页面及局部组件；
- 不修改赛程状态机、比分规则、权限判断和数据结构；
- 不与 RPT-05/RPT-06 同时修改同一页面；
- 公共 CSS 改动必须检查全站影响。

### 验收清单

- [ ] 四种视口均无页面级横向溢出；
- [ ] 每条关键路径可以只用触屏完成；
- [ ] 固定头部、弹窗和底部操作不互相遮挡；
- [ ] 输入时软键盘不会遮住确认操作；
- [ ] 长 ID 和长队名不会形成逐字竖排；
- [ ] 关键按钮文字与实际结果一致；
- [ ] 浏览器控制台无新增错误；
- [ ] 现有业务回归全部通过。

## 6. SYS-04：高风险操作审计与安全补齐

### 目标

确保会改变报名、队伍、赛程、赛果、晋级、发布状态和凭证的操作可追溯且不能被轻易越权。

### 工作内容

1. 建立所有写接口清单并标记身份、权限、限流、同源、幂等、并发和审计状态。
2. 重点检查管理员赛程整表保存、报分、抽签发布、赛事阶段变化、名单操作和令牌重置。
3. 将缺失的高风险操作写入统一审计，不在日志中记录原始令牌和个人信息。
4. 检查错误响应是否泄露内部实现。
5. 确认公开 API 只返回完成任务所需的最小字段。
6. 对共享管理员身份的局限形成明确记录；在不阻塞当前办赛的前提下提出多管理员迁移方案。
7. 新增越权、重复操作、过期状态和并发冲突测试。

### 文件边界

- 先完成只读审计报告，再申请修改；
- `src/proxy.ts` 和鉴权文件必须与 RPT-02 错峰修改；
- 已执行的 Supabase migration 不得编辑，只能增加新迁移。

### 验收清单

- [ ] 所有高风险写操作都有明确身份和权限；
- [ ] 写操作均有请求大小和速率限制策略；
- [ ] 不能用前端隐藏替代服务端权限；
- [ ] 并发写不会静默覆盖新数据；
- [ ] 审计记录不包含敏感原文；
- [ ] 共享管理员问题有迁移路径和风险接受人；
- [ ] 安全测试通过且不触碰生产数据。

## 7. SYS-05：文档、配置与生产清单收口

### 目标

解决路线图、开发交接、真实代码和生产状态之间的漂移。

### 工作内容

1. 更新项目路线图中的真实 Gate 状态。
2. 更新开发交接中的仓库路径、生产域名、当前版本和最新测试。
3. 明确 staging、production、本地数据边界。
4. 将真实密钥轮换、协作者离开、赛事归档和下一届建赛写入清单。
5. 删除或标记已经失效的操作说明，但保留历史决策证据。
6. 文档引用统一指向当前计划，不复制多份互相漂移的结论。

### 验收清单

- [ ] 新 AI 只读入口文档后能判断当前状态；
- [ ] 不会把匿名测试赛当作生产赛事；
- [ ] 不会把 staging 地址当作正式入口；
- [ ] 不会按过期指令暂停或启动 AI；
- [ ] 文档不包含密钥和真实个人信息。

## 8. 轨道 A 完成条件

轨道 A 不要求消灭所有 UI 问题。满足以下条件即可进入稳定维护：

- P0 数据和安全问题为 0；
- P1 关键任务阻塞为 0；
- 手机端关键路径全部可完成；
- 质量门禁自动运行；
- 备份和隔离恢复演练可执行；
- 高风险写操作清单完成并补齐关键缺口；
- 生产故障有负责人、判断方式和恢复步骤；
- 剩余问题均已进入 P2/P3 台账，不阻塞裁判报分和 AI 离线验证。
