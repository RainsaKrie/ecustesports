## 2. 极低频，但我建议保留

这一节是「用不到 ≠ 该删」。项目自己有一条原则：
**敢不逐项核对的真正理由不是信任模型，是错了能退。** 下面这些就是「能退」的通道。

### 2.1 破坏性但必要的收尾操作（报名与队伍页）

| 操作 | 用在哪 | 为什么不能删 |
|---|---|---|
| 整队退赛 | 队伍不打了 | 不处理，退赛队伍会卡住抽签与赛程 |
| 解散队伍 | 队伍组错了 | 同上 |
| 移出名单 / 换人 | 人员变动 | 开赛前后都可能发生 |
| 开放名单调整 | 已确认名单要改 | 确认后改名单的唯一正规路径 |
| 修改队名 | 队名写错 | 极低频，但塞进「编辑队伍」更合适（见 3.4） |
| 撤销操作 | 误操作兜底 | 操作记录里有历史，可撤销 |

### 2.2 赛果纠错

| 操作 | 位置 | 说明 |
|---|---|---|
| 受控更正 | 异常赛果页第 2 个标签 | **已生效赛果的唯一修正途径**，必留 |
| 归档并重抽 | 赛程页 | 整个赛程作废重来，用在抽签本身抽错时 |

### 2.3 异常赛果裁决（需要你确认，见 4.1）

队列只接收两类：**半决赛/决赛的强制复核提交**，以及**结果冲突**（同场已有效果但胜者相反）。

按 32 队赛制，半决赛 + 决赛约 4–5 场。所以：

- **若这届开裁判报分**（你在做 AI 识图，说明计划是开）→ 一届约 4–5 条，值得保留
- **若仍是你本人在赛程页手工报分** → 手工报分直接生效、不进队列，**这个页面会恒空**

### 2.4 赛事收尾（赛事设置 → 发布概览）

| 操作 | 频率 |
|---|---|
| 发布到玩家侧 / 从玩家侧撤回 | 每届 1–2 次 |
| 归档为往届赛事 | 每届 1 次 |
| 永久删除测试赛事 | 仅用于清测试赛事（如「海斗杯（测试）」），有 3 道限制 |
| 保存为以后赛事的通用规则 | 每届最多 1 次，**对下届有复用价值** |

## 3. 建议处理（5 项）

### 3.1 ★ 「官网内容」是顶级导航，实际只编辑 2 个字段，其中 1 个与别处重复

**事实**

- 顶部导航第 2 个位置常驻「官网内容」，听起来是整站内容管理
- 点进去实际只有：**首页赛事简介**（textarea，280 字上限）+ **页脚状态**（input，100 字上限）
- 而「赛事设置 → 玩家页面」分区已经在编辑 **赛事简介**、奖项说明、赛事海报

**问题**：`event.description` 这一个字段有两个编辑入口。

**两个入口的校验还不一致**：

| 入口 | 保存路径 | 对 description 的限制 |
|---|---|---|
| 赛事设置 → 玩家页面 | `PATCH /api/admin/events` | `text(v, 500)` —— 只截断到 500，**无下限** |
| 官网内容 | `PATCH /api/admin/site-content` | **必须 10–280 字**，否则 400 |

**会踩的坑**：在「赛事设置」把简介写成 5 个字或 300 个字，保存会成功。
之后打开「官网内容」页想改**页脚**，会因为 payload 里带着那个越界的简介而被拒
（该接口每次都把两个字段一起发出去），提示「首页赛事简介应为 10—280 字」——
**想改的和报错的不是同一个字段**。

**建议**（三选一，你定）

1. 最低成本：两边校验对齐（都用 10–280）
2. 更进一步：把「官网内容」从顶级导航降级为「赛事设置 → 玩家页面」里的一个区块，
   简介只留一个入口，页脚单独成一个「站点级」设置
3. 保持现状，只改校验

> 另一处相关设计：**页脚状态是全局字段**（`brand.footerStatus`，不属于任何赛事），
> 却只能从一个「当前赛事」的页面进去改，且当前内容写的是
> 「第三届瓦理杯已结束 · 冠军：疾风战队」。
> 下届开赛时这段文字要手改，容易忘。

### 3.2 裁判分配不支持批量 —— 已确认为「不需要做」

`doAssign` 一次只分配**一场**比赛（选裁判 + 选比赛 → 提交）。
原判断是「50 场就是 50 次下拉，建议加批量」。

**该建议的前提已被推翻。** 负责人说明的实际流程是
**裁判自己认领可工作的比赛**（见第 7 节），不是负责人逐场指派。
既然认领权在裁判手上，批量指派就没有使用场景。

→ **2026-09-15 负责人确认：不做。**

保留管理端的指派能力仅作兜底（某场没人认领时用），
它的低频正好说明不需要批量。

> 记录这个结论的理由：**建议的前提可能被业务事实推翻**。
> 频率判断依赖「谁在用、怎么用」，而这一点只有业务方能回答。
> 拿到答复后要重新审视原建议，而不是照着旧清单继续做。

### 3.3 两个刷新按钮调同一个函数

- 顶部工具条：「刷新约赛」
- 约赛审批区内：「刷新申请」

两者都是 `void refresh()`。下方那个只在有约赛申请或待发通知时才渲染，算是上下文入口，
但**名字不同、行为相同**，容易让人以为是两件事。

**建议**：合并成一个「刷新」，或给下方那个改成明确语义（如「重新拉取申请」）。

### 3.4 极低频的小操作占了独立弹窗 —— 已撤回，改做另一件事

原文写：

| 操作 | 现状 | 建议 |
|---|---|---|
| 修改队名 | 独立弹窗，只有 1 个输入框 | 并入「编辑队伍」（队名 + 成员一起看） |
| 开放名单调整 | 独立弹窗 | 保留（它是个状态流转，不只是改字段） |

**★ 2026-09-15 核对代码后，这条建议撤回。原文有三处不准：**

1. **不是「只有 1 个输入框」**。改名弹窗是「新队名 + **改名原因（必填）**」两个字段。
2. **原因不是界面要求，是服务端强制的**：
   `registration-admin-ops.ts` 里 `if (!input.reason.trim()) return fail(state, "修改队名必须填写原因。")`，
   并通过 `commit(..., "rename-team", "队伍 X 更名为 Y", reason)` 写入审计。
   它和「解散队伍 / 整队退赛 / 开放调整」是同一种东西——**有据可查的变更**，不是随手改个字段。
3. **没有「编辑队伍」这个入口可并**。而且卡片上已经完整展示了两队名单（含每人的
   调整/换人/移出），所以「队名 + 成员一起看」这件事**本来就是成立的**。

**若强行合并会更差**：要么稀释「必须填原因」的纪律，要么合并后的弹窗还是得要求填原因——
那合并就毫无意义。

**按钮数量也不是问题**：报名中显示 4 个（确认名单/改名/解散/退赛），
已冻结显示 3 个；且「改名」（报名中）与「开放调整」（已冻结）**按状态互斥，从不同时出现**。

### 3.4b 实际改掉的是：操作按钮的字号

核对时发现真正的小毛病在**字号**上。

`globals.css` 的根字号是**自适应**的：

```css
html { font-size: 150%; }                 /* 桌面：根 24px */
@media (max-width: 760px) { html { font-size: 100%; } }   /* 移动端：根 16px */
```

而队伍卡片的 6 个操作按钮用了 `text-[0.625rem]`，本文件其余地方主流是 `text-xs`（44 处）。
换算后：

| 宽度 | 改前 | 改后 |
|---|---|---|
| 移动端（根 16px） | **10px** | **12px** |
| 桌面（根 24px） | **15px** | **18px** |

两侧都低于本文件自身的约定，移动端 10px 尤其难读。
改成 `text-xs` 后与全站一致，**移动端 12px / 桌面 18px**。

涉及 6 个按钮：确认名单 / 开放调整 / 改名 / 解散队伍 / 整队退赛 / 撤销这次操作。

**实测**（真实赛事数据，全程只读，git 状态前后一致）：
360/390/430/1440px 四档**均无横向溢出**；触控高保持 44px（桌面 66px）。

> **一处我自己的换算错误，记下来**：首次分析时我按「根字号 = 16px」估算，
> 得出「10px，低于可读下限」。实际是**桌面 24px / 移动 16px 两套**，
> 那个 10px 只出现在移动端。后来是靠**在真实浏览器里量计算结果**（`getComputedStyle`
> 报 18px）才发现的——**rem 换算不要心算，去页面里量。**

## 4. 我判断不了的（需要你回答）

### 4.1 这届到底走哪条报分路线

这决定三件事的频率，而我在代码里看不出你的决定：

| 路线 | 后果 |
|---|---|
| **裁判报分 + AI 识图** | 异常赛果页会用（约 4–5 条/届）；裁判管理要维护分配；通知流程要跑 |
| **你本人在赛程页报分** | 异常赛果页恒空；裁判管理可以不用；但 AI 识图也用不了（识别接口与裁判报分共用同一个开关） |

**注意**：AI 识图端点在代码里检查 `refereeReportingEnabled()`。
**开裁判报分是开 AI 识图的前提**，两者绑在一起。

### 4.2 约赛改期走哪个入口

代码里有两条并存的路径：

- **公开端申请**（队伍提交 → 你批准/驳回）→ 赛程页「刷新约赛」「刷新申请」「批准并更新赛程」「驳回」
- **负责人调整**（你直接改某场比赛时间）→ 场次详情 →「负责人调整」

若队伍实际都在 QQ 群里口头找你改，那公开申请那条路就是空的，
「刷新约赛」「驳回」这些就属于**为流程而流程**。

### 4.3 通知是不是真在走系统

赛程页有「待发送通知」区，操作是 **复制通知** + **标记已发布**。
也就是说：系统只生成文案，你手动复制到 QQ 群里发，再回来点「已发布」。

**问**：你会真的回来点「标记已发布」吗？如果不会，这个状态就会一直停在草稿，
数字会越积越多（侧边栏的「待完成事项」会一直提示）。

### 4.4 抽签的手动控制要不要留

抽签页有：抽下一队 / 一键抽完 / 重新开始 / 重新抽签。

「抽下一队」是为了**当着队伍的面一步步抽**（仪式感与可核查）。
如果实际是你在后台一键抽完再公布结果，那这几个按钮就只用「一键抽完」一个。

## 5. 总结

**真正的高频只有三处**：报名与队伍的审核/组队、赛程页的排期与报分、抽签。

**极低频但必须留的**是「错了能退」的那批：整队退赛、解散队伍、受控更正、归档并重抽、
永久删除赛事。删掉它们省不了多少界面，但出事时没有退路。

**唯一建议动手的**是 3.1（`event.description` 双入口、校验不一致）——它是**会真实咬人**的：
改页脚却报「简介字数不对」，而且看不出原因。

3.2 / 3.3 / 3.4 / 3.5 属打磨，不影响办赛。
4.1 是**前置决策**：它的答案决定「异常赛果」「裁判管理」这两个页面是活的是死的。

### 6.2 由答复得出的结论

### 6.3 ★ 原报告漏掉的问题：约赛申请会挂在「待对手确认」，而管理端没有按钮

**原报告只写「若队长只私下商量，公开申请那条路是空的」——不够准确。**

实际情况是：队长确实会上平台填时间（这是流程的第一步），只是**对手不会再上来点确认**。
代码里的状态机是三步：

```
队长填写 → 待对手确认 → 对手确认 → 待审批 → 负责人批准
```

而管理端只给「待审批」渲染按钮：

```jsx
{request.status === "待审批" && <div>驳回 / 批准并更新赛程</div>}
```

于是「待对手确认」的申请**显示在列表里，却一个按钮都没有**：不能批准、不能驳回；

## 7. 裁判分配模式改为自助认领（2026-09-15）

### 7.1 负责人说明的实际流程

> 裁判自己认领可工作的比赛，也就是所有队伍先在规定时间段完成约赛，得到一个比赛列表，
> 裁判再自己看比赛列表里哪些自己能裁判，然后直接选中自己做裁判。

原实现是**负责人逐场指派**（管理端选裁判 + 选比赛 → 提交）。
50 场比赛就是 50 次下拉操作，而且负责人得先把每场和某个裁判对上——
在「队伍先约赛、时间陆续确定」的情况下，这个对应关系是逐步出现的，指派会变成持续的负担。

### 7.2 改动

**新增裁判端能力**（`/api/referee/claim`，GET 列表 / POST 认领或释放）：

| 动作 | 说明 |
|---|---|
| 列出可认领的比赛 | 已排期 + 未完成 + 尚无人认领，按时间升序 |
| 认领 | 认领后该场进入「我的比赛」，可直接报分 |
| 释放 | 只释放**自己认领**的场次，被指派的不行 |

**管理端指派能力保留**，用作「某场没人认领」时的兜底。
管理端现在能区分「裁判认领」与「负责人指派」（绿色 / 灰色标签）。

### 7.3 ★ 两个不明显的设计决定

**① 抢单冲突必须在数据库锁内判定**

`assignMatchOp` 原本只防「同一裁判重复分配」，**不防两人抢同一场**——
负责人指派时靠人避免撞车。改成自助认领后这会变成真实的并发问题。

处理方式：把「该场是否已被他人认领」的判定放进 `updateEventData` 的 updater 内
（生产是 PostgreSQL 事务、本地是赛事级写锁）。
**如果放在锁外先读再写，两名裁判同时点同一场会双双通过检查**——
各自读到的台账都还是空的——结果是这场有两个裁判都以为自己负责。

另外给 `assignMatchOp` 补了同样的检查：已被认领的场次不能被指派覆盖，
否则会出现「裁判刚认领、负责人又指派给别人」。

**② 时间重叠只提示、不拦截**

一个人无法同时执裁两场，这个冲突值得指出。但**时段长度来自
`config.boDurations` 的估算值**（BO3 = 90 分钟），配错就会误拦。

所以标记 `overlapsMyMatch` 让裁判自己判断，而不是硬挡。
判断权交给实际执裁的人——他比配置更清楚这场会打多久。

**③ 被指派的场次不能由裁判自己丢掉**

释放只对 `selfClaimed` 的分配生效。若被指派人可以自行释放，
「负责人指派」这个兜底手段就形同虚设——他可以单方面卸责。

### 7.4 顺带

- 管理端两个刷新按钮：顶部「刷新约赛」改名「**刷新数据**」（它刷新的是整页数据，
  不只是约赛）；区块内那个改成**文字链接**并注明与顶部是同一操作——
  不删的理由是页面头部不吸顶，翻到底部时手边需要一个刷新入口。
- demo seed 的比赛补上 `endTime`（原来为空，导致时间重叠永远算不出来），
  并加了第三场刻意重叠的比赛用于验证提示。

### 7.5 删除测试赛事「海斗杯（测试）」`event-mtio5q5y`

- 2026-09-01 创建，`draft` / `private`，**从未使用**
- 走**真实删除 API**（不直接改文件），以复用业务校验：
  名称确认、必须非公开、必须是 draft/archived、至少保留一场赛事
- 删前确认：`archives` 无引用、`currentEventId` 不指向它、其它赛事数据无引用、
  无对应数据目录（测试数据早已清过）
- 删除结果：赛事数 2 → 1；正式赛事「第三届瓦理杯」**所有已有字段值一个未变**

> **一处需要说明的差异**：删除给正式赛事补了一个 `eventQqGroup: ""` 空字段。
> 这是 `updateSiteConfig` 按 schema 写回时的规范化（该字段是后加到 schema 的），
> **不是数据损坏**——所有原有字段的值都没变。核对时要把「已有字段被改坏」
> 与「新增空字段」分开判断，混在一个比较里会误报。

## 8. 自助认领引出的两个缺口（2026-09-15）

加完自助认领后追查「改期会怎样」，发现 `approveRequestOp` 只改写赛程文档
（`ScheduleState`），**完全不知道裁判台账（`RefereeLedger`）的存在**。
于是产生了两个缺口。

### 8.1 已修：「我的比赛」内部时间重叠没有任何提示

**场景**

1. 裁判认领 M1（12:00–13:30）与 M2（15:00–16:30）——当时不冲突，两场都能裁
2. 两队协商把 M2 改到 12:30–14:00
3. 裁判的「我的比赛」里两场撞在一起，**系统一声不响**

**为什么这是缺口而不是「小事」**

我先前只给「可认领的比赛」加了重叠标记（认领时提示），
但**认领之后**的改期没有对应保护。裁判是按当时看到的时间决定接不接的，
而那个时间可以在他不知情的情况下变掉。

**改法**：`projectMyMatches` 也计算重叠（`overlapsMyMatch`），
界面上对「我的比赛」里的冲突给出提示。

判据与「可认领列表」保持一致：**只提示、不拦截**——
时段长度来自 `config.boDurations` 的估算值，配错会误拦，判断权交给执裁的人。

**边界都测了**：首尾相接不算重叠（13:30 结束 / 13:30 开始）、
只有一场时不可能重叠、未排期的场次不参与判定、
别人认领的场次不影响我的判断。

### 8.2 待定：改期后裁判不知道「时间变了」

**场景**：裁判认领 M1（周六 12:00）→ 后来改到周日 → 裁判不主动打开工作台就不会知道。

**现状的缓解**（所以不算紧急）：

- 改期批准时会生成通知，文案里已包含「请双方队伍与裁判知悉」
- 通知由负责人复制到赛事群 → 裁判在群里能看到
- 裁判打开工作台会看到新的时间

**所以后果是「多一道人工传达」，不是「没人知道」。**

**若要修，做法是记快照**：在认领时把 `startTime` 存进分配记录
（如 `claimedStartTime`），之后与当前时间比对，不一致就标记
「这场在你认领后改过时间，请确认还能裁」。

**为什么先不做**：

- 需要给分配记录加字段（涉及既有数据的兼容处理）
- 现在这条信息由负责人口头/群里传递，实际不会漏
- **优先级低于「重叠提示」**——重叠会让人同时被两场占用，是硬冲突；
  改期只是需要重新确认，而负责人本来就知道自己改了

判断依据：**先修「会静默出错」的，再修「需要人工传达」的。**
重叠属于前者（没人提示就可能漏裁），改期属于后者（至少有人知道）。
