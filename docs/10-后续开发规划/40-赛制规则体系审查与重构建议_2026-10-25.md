# 赛制规则体系审查与重构建议（2026-10-25）

> 审查对象：阶段划分、场次推导、名次判定、轮次识别、局制升级这五类规则的定义位置与相互关系。
> 方法：`grep` 全量清点 + 逐条比对公式，**不是读代码猜**。
> 结构：问题清单 → 原因分析 → 优化方案。

---

## 一、问题清单

### P0-1 · 场次推导有两份公式，且默认值不一致（**已确认会算出不同结果**）

| 位置 | 函数 | `groupCount` 缺省时 |
|---|---|---|
| `bracket-blueprint.ts:92` | `expectedStageMatches` | `groupCount ?? 0` → **GSL 算成 0 场** |
| `staged-format.ts:57` | `groupStageExpectedMatches` | `groups ?? 4` → **GSL 算成 20 场** |

**触发条件**：任意一个 GSL 阶段没有显式填 `groupCount`。
**潜在影响**：同一个阶段，对阵图页说"最多 0 场"，抽签门控说"最多 20 场" —— **互相矛盾**，
用户看到的两处提示必然有一处是错的，且无法判断哪处对。

`single-elim-groups` 分支同样不一致：A 用 `groups ?? 1`，B 用 `groups ?? 4`。

### P0-2 · 阶段识别有两套判据，口径不同

| 位置 | 判据 |
|---|---|
| `group-standings.ts:26` | `GROUP_PHASE_HINTS = ["小组赛", "组内", "GSL"]` + `includes` |
| `PublicSchedule.tsx:175` | `m.phase.includes("淘汰")` |

**问题**：
- 前者是**白名单**（列了三个词），后者是**子串匹配**（任意含"淘汰"即可）；
- 白名单里没有"淘汰"相关的词，**任何新增阶段（如"季军赛"）都不会被任一处认出**；
- 阶段「小组赛」被识别时用的是**名字**，不是**类型** —— 一旦用户把阶段改名（"分组赛"），
  分组积分就不显示了，而且**不报错**。

**潜在影响**：改阶段名 → 界面静默少一块。这正是 2026-10-22 那次"分组积分整块消失"的同类隐患。

### P1-3 · 场次校验复制成 8 份（已修，但结构没变）

2026-10-22 那次连环报错的直接原因。现在 8 处都改成了"多于才报错"，
但**仍然是 8 份独立代码**：赛程页 1 份 + `staged-format` 6 份 + `staged-format-draw` 1 份。

**为什么是隐患**：这次是靠人工 grep 找齐的。下次新增一个阶段（比如"季军赛"），
**新写的那份一定又会漏掉**。

### P1-4 · 轮次靠字符串后缀识别，存在边界歧义

```ts
if (!round.endsWith("决赛") || round.endsWith("半决赛")) continue;   // 认「X 组 决赛」
if (!round.endsWith("半决赛")) continue;                            // 认「X 组 半决赛」
```

**问题**：「半决赛」本身以「决赛」结尾，所以必须**先排掉它**——代码注释里已经写了这个坑。
但这意味着：**任何以「决赛」结尾的新轮次名（如"季军决赛"）都会被当成小组决赛**，
从中提取出"组名 = 季军"，进而**污染名次表**。

**触发条件**：双败之外再加任何"XX 决赛"轮次。
**潜在影响**：名次表里凭空多出一个不存在的"组"，淘汰赛抽签凑不齐 8 支。

### P1-5 · `double-elim` 只支持 8 队（硬编码）

```ts
if (stage.type === "double-elim" && stage.teamCount === 8) return 14;
return null;
```

**问题**：**16 队双败**返回 `null`，即"不校验场次"。看起来宽容，
实际是**校验形同虚设** —— 16 队双败少打了几场、多打了十几场都不会报警。

**潜在影响**：该赛制下的数据错误**完全没有防护**。

### P2-6 · 阶段名硬编码 52 处

`grep '"资格赛"|"入围赛"|"小组赛"|"淘汰赛"'` 在 `src/` 下命中 **52 处**（已排除测试）。

**问题**：阶段名是**配置项**（用户可改），却被当**常量**用了 52 次。
改名 = 全站静默失效。

### P2-7 · 局制升级靠"例外名单"

```ts
const BO_EXEMPT_ROUNDS = ["胜者组决赛", "败者组决赛", "总决赛"];
```

这是 2026-10-22 那次"淘汰赛不显示对阵图"的根因（名单漏了"胜者组决赛"）。
现在补全了，但**仍然是名单** —— 赛制一变，名单就得跟着变。

## 二、原因分析

### 2.1 规则的存在形式错了

现在的规则**不是数据**，是**散落在代码里的判断**：
- "场次怎么算" → 一个函数（而且是两份）；
- "哪些阶段算小组" → 一个字符串白名单；
- "哪些轮次升 BO5" → 一个数组；
- "阶段叫什么" → 52 处字面量。

**规则既然是配置驱动的（用户能改赛制），它就应该以数据形式存在于一处**，
代码只负责**读规则、执行规则**。

### 2.2 同一概念没有单一出处

同一个"场次公式"两份、同一个"阶段归属"两套。
**不是有人偷懒，是不同时间由不同逻辑各自需要，就地写了一份。**

### 2.3 用"名字"承载"语义"

"小组赛""淘汰赛"这些**字符串**同时承担了三件事：
- 给人看的标题；
- 代码里的阶段标识；
- 规则的匹配依据。

**改名 = 改语义**，但改名是用户行为。**这是最根本的设计问题。**

## 三、优化方案

### 3.1 建立唯一的赛制规则表（P0）

把散落的规则收进**一个文件** `src/lib/domains/schedule/stage-registry.ts`：

```ts
export const STAGE_RULES = {
  "single-elim":        { matches: (s, next) => ..., roundPattern: "single-elim",      boUpgrade: {} },
  "gsl-groups":         { matches: (s) => (s.groupCount ?? DEFAULT_GROUPS) * 5, ... },
  "single-elim-groups": { matches: (s) => ..., ... },
  "double-elim":        { matches: (s) => 2 * s.teamCount - 2 + ..., ... },   // 任意队数
} as const;
```

**要解决的问题**：P0-1（两份公式）、P1-3（8 份校验）、P1-5（只支持 8 队）。
**预期效果**：
- 场次公式只有一份，`groupCount` 缺省值只有一个；
- 校验只需调用 `expectedMatches(stage)`，不再复制；
- 双败支持任意队数（公式 `2n-2` 通用）。
**优先级：P0**。

### 3.2 阶段识别改用"类型 + 显式标记"，不用名字（P0）

`StageConfig` 已经 `type` 字段。再加一个 `role` 字段：

```ts
type StageRole = "qualifier" | "group" | "knockout";
```

界面与门控**只看 `role`**，不看 `phase` 字符串。

**要解决的问题**：P0-2（两套识别）、P2-6（52 处硬编码）。
**预期效果**：用户随便改名，逻辑照常工作；新增阶段只需声明 `role`。
**优先级：P0**，但需要迁移现有配置（加一次 `role` 回填）。

### 3.3 轮次改为结构化，不再靠后缀匹配（P1）

现在是 `round: "A 组 决赛"` 这种**拼出来的字符串**。建议拆成：

```ts
match.round = { group: "A", stage: "final" }   // 或 roundKey: "A/final"
```

名次提取按 `roundKey` 精确匹配，不再 `endsWith`。

**要解决的问题**：P1-4（边界歧义）。
**预期效果**：新增"季军决赛"不会被误判成小组决赛。
**优先级：P1**，改动面较大（涉及所有轮次生成与展示），建议赛后做。

### 3.4 局制升级写进赛制配置（P1）

```ts
boUpgrade: [{ round: "winner-final", bo: "BO5" }, ...]
```

**要解决的问题**：P2-7（例外名单）。
**预期效果**：改赛制不用改代码。
**优先级：P1**。

### 3.5 给"场次校验"加一条护栏测试（P1，成本最低）

写一个测试：**遍历 `src/lib` 下所有 `.ts`，禁止出现
`length !== <预期场次>` 这种写法**（白名单明确标注的除外）。

**要解决的问题**：P1-3 的复发。
**预期效果**：下次谁再复制一份，门禁直接红。
**优先级：P1，但可以先做** —— 半小时的事，能防住这一类问题。

## 四、优先级汇总

| 编号 | 问题 | 优先级 | 说明 |
|---|---|---|---|
| P0-1 | 场次公式两份、默认值不一致 | **P0** | 已确认会算出不同结果 |
| P0-2 | 阶段识别两套、靠名字 | **P0** | 改名即静默失效 |
| P1-3 | 场次校验 8 份 | P1 | 已修好但会复发，建议先加护栏测试 |
| P1-4 | 轮次靠后缀识别 | P1 | 新轮次名会污染名次表 |
| P1-5 | 双败只支持 8 队 | P1 | 16 队双败等于不校验 |
| P2-6 | 阶段名硬编码 52 处 | P2 | 改名成本高 |
| P2-7 | BO 例外名单 | P1 | 漏项会吞掉整块界面 |

## 五、一句话总结

**这些规则的共同病根是：把"可配置的规则"写成了"代码里的判断"，并且同一概念写了好几份。**

所以问题不是"某条规则写错了"，而是**规则没有住处** —— 它在 52 处字面量、2 份公式、
3 套识别、8 处校验里各活一遍。

**真正的解法是给它一个唯一的家**（3.1 + 3.2），让代码只负责执行。

在这之前，**3.5 的护栏测试是性价比最高的一步** —— 半小时，能防住"复制判据"这一类复发。
