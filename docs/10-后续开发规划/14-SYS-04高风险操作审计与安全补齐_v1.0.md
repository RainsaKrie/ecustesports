## 1. 保护机制总览（四层）

先明确一件事：**并发与鉴权的保护是集中的，不是每个路由各写一遍。** 逐路由看容易误判（本次审计过程中我自己就先误判了一次，见第 6 节）。

| 层 | 位置 | 覆盖范围 | 说明 |
|---|---|---|---|
| ① 网关 | `src/proxy.ts`（matcher `/admin/:path*`、`/api/:path*`） | **全部**路由 | 限流 + 同源 + 后台页面重定向 + 写接口未登录 401 |
| ② 路由 | 各 `route.ts` 内的 `isAdmin()` / `verifySessionToken()` / 凭证校验 | 管理员 9/14、裁判 5/5、data 3/3、公开 5/7 | 见第 3 节缺口 A |
| ③ 数据层 | `src/lib/supabase-data-store.ts` | **全部**写入 | 乐观并发控制（版本 CAS）+ 多文档原子 RPC |
| ④ 留痕 | `operation_audit` 表 + 各领域业务台账 | 见第 4 节 | 两层：粗粒度管理员动作 + 领域内可追溯操作 |

### 1.1 网关层（proxy.ts）

- **白名单是精确匹配**：`PUBLIC_WRITE_PATHS.includes(pathname)`。未列入的写接口一律要求管理员会话 → **失败方向是「拒绝」**（fail-closed），新路由不会意外变成公开接口。
- **限流**：`WRITE_LIMITS.find(c => pathname.startsWith(c.prefix))` 取**首个**匹配，数组顺序即优先级。因此存在一条兜底规则：

  | 规则（按匹配优先级） | 限额 |
  |---|---|
  | `/api/admin/login` | 10 次 / 15 分钟 |
  | `/api/admin/upload` | 10 次 / 1 小时 |
  | `/api/public/register` | 12 次 / 10 分钟 |
  | `/api/public/participant/recover` | 6 次 / 15 分钟 |
  | `/api/public/team` | 40 次 / 10 分钟 |
  | `/api/public/schedule/request` | 30 次 / 10 分钟 |
  | `/api/data/bp` | 90 次 / 1 分钟 |
  | `/api/referee/login` | 10 次 / 15 分钟 |
  | `/api/referee`（submit / upload / recognize / claim） | 60 次 / 10 分钟 |
  | **`/api`（兜底，其余全部写接口）** | **180 次 / 10 分钟** |

  → **不存在「无限流的写接口」**，每个写接口至少受兜底规则约束。

  ⚠️ **一处维护脆弱性（当前无害，值得记录）**：规则用 `find` + `startsWith` 取**首个**匹配，
  所以「宽前缀在前」会让「窄前缀在后」永久失效。当前顺序是对的（`/api/referee/login` 在
  `/api/referee` 之前，所以登录拿到更严的 10/15min；兜底 `/api` 放在最后）。
  但**将来新增规则时若插错位置会静默失效**——建议在 `WRITE_LIMITS` 上方补一句注释说明
  「顺序即优先级，窄前缀必须放在宽前缀之前」。

  另：`/api/public/team` 作为前缀同时覆盖了 `/api/public/team/request` 与
  `/api/public/team/member`（三者同为 40/10min），这应是预期行为。
- **同源校验**：仅在 `isHostedRuntime()`（生产）启用；本地开发跳过（否则本地没法调）。允许来源取 `APP_ORIGIN` / `VERCEL_URL` / `VERCEL_PROJECT_PRODUCTION_URL` / `VERCEL_BRANCH_URL`；若一个都没有，返回 503 而不是放行。
- **限流服务故障时**：托管环境返回 503（拒绝），本地仅打印日志 → 同样是 fail-closed。

### 1.2 数据层（并发保护的真正位置）

| 写原语 | 机制 | 是否会静默覆盖 |
|---|---|---|
| `insertIfMissing` | `POST` + `resolution=ignore-duplicates` | 否（只在不存在时插入） |
| `compareAndSwap` | `PATCH` + `version=eq.N` | 否（版本不符则 0 行，进入重试） |
| `compareAndSwapMany` | RPC `update_app_documents_atomic`（多文档同事务） | 否 |

- `write()` 与 `update()` 都是「读 → 带版本 CAS → 失败则重试」的循环；重试耗尽后抛
  「数据已被其他操作连续修改，请刷新后重试」，**不会静默覆盖**。
- 读取层对 **PGRST303 时钟偏差**有专用重试（1000/1500/2000ms）；**其它 401 立即失败**，
  以免掩盖凭证配置错误。
- 上限：`content-length > 2MB` 时 `data/schedule`、`data/format` 返回 413。

**结论**：工作包验收项「并发写不会静默覆盖新数据」**成立**，且是在数据层统一保证的，
不依赖各路由自觉。

## 3. 缺口 A：4 个管理员路由只有一层鉴权

**现象**：这 4 个路由的 `route.ts` 内部**没有** `isAdmin()` / `verifySessionToken()` 校验，
完全依赖 `proxy.ts`：

| 路由 | 方法 | 敏感性 | 说明 |
|---|---|---|---|
| `/api/admin/site-config` | PUT | **高** | 整体重写站点配置（含全部赛事条目） |
| `/api/admin/site-content` | PATCH | 中 | 改首页简介与页脚文案 |
| `/api/admin/upload` | POST | 低 | 上传图片（另有 10 次/1 小时限流） |
| `/api/admin/logout` | POST | **最低** | 仅清自己的会话 cookie；未登录调用也无副作用，**可不改** |

其余 9 个管理员写路由都是「网关 + 路由」两层（`login` 本身即登录入口，不适用）。

**先明确这不是漏洞**：proxy 是服务端代码，matcher 覆盖 `/api/:path*`，
所以这些接口**当前确实被鉴权保护**。工作包验收项「不能用前端隐藏替代服务端权限」**不构成违规**。

**风险在于纵深防御**：只剩一层，且这一层是**隐式**的——

1. 任何改变 matcher 或路径前缀的改动（例如把 API 挪到 `/api/v2/`）会**静默**让它们失去保护；
   两层路由即使网关出问题仍自保。
2. 代码审阅时不明显：只看 `route.ts` 会以为接口是裸的（本次审计中我就因此一度误判）。
3. `site-config` PUT 的敏感度**不低**：它整体重写站点配置（含全部赛事条目）。

**建议**：给 `site-config`、`site-content`、`upload` 补上与其他管理员路由一致的 `isAdmin()` 检查。
改动量极小（每个约 3 行），不改行为，只加一层保险。`logout` 建议保持原样（改反而可能影响会话失效流程）。
**属 SYS-04 建议修改项，但需另开工作包。**

## 4. 缺口 B：5 处写操作没有可追溯记录

`operation_audit` 表已存在且设计正确（RLS 开启、`anon`/`authenticated` 全部 revoke、
仅 `service_role` 可读写）。目前已接入 6 类管理员动作：
登录（成功/失败）、赛事增删改、发布/撤回、阶段变化、赛制变更。

**未接入、且**在业务数据里也没有台账的写操作：

| 操作 | 敏感性 | 当前状况 |
|---|---|---|
| `admin/rule-library` PUT | 中（覆盖规则库） | 无记录 |
| `admin/events/switch` POST | 低（只改「当前焦点赛事」指针） | 无记录 |
| `admin/site-config` PUT | **高**（整体重写站点与赛事配置） | 无记录 |
| `admin/site-content` PATCH | 中（改首页/页脚文案） | 无记录 |
| `admin/upload` POST | 低（上传图片） | 无记录 |

**已充分留痕、不需要补的**（审计中一度误判，特此更正）：

| 操作 | 留痕方式 |
|---|---|
| 名单操作（审核/更正/换人/退赛） | 领域台账 `operationLogs`，**服务端强制 reason** + 前后状态 |
| 赛果提交 / 裁决 / 受控更正 | 赛果台账，含 actorType、actorId、reason、版本 |
| 裁判创建 / 停用 / **重置凭证** / 指派 / 认领 / 释放 / 撤销指派 | 领域台账 `RefereeAuditEntry`，带 actorId |
| 赛程改动 | `versions[]` 版本历史 + reason |
| 发布 / 撤回 / 阶段变化 / 赛制变更 / 赛事增删改 | `operation_audit` |

→ 工作包点名「重点检查」的 **令牌重置确实已有留痕**（`reset-credential` 写在 `ledger.audit`），
**但不在 `operation_audit`**：两套台账分处不同位置，查一件事要翻两个地方。

**建议**：`site-config` PUT 优先补（敏感度最高）。其余 4 项一并补，成本低。

### 4.1 2026-10-12 追加：这条边界改成「强制登记」了

本节上面那段「两层留痕」的划分本来只写在文档里。守卫测试里对应的是一份**手写的 9 文件清单**
（`api-route-guards.test.ts` 的组 5），它只能证明「登记过的确实有留痕」，
**证明不了「没有漏登记的」** —— 新加一个高风险管理端写路由时，组 0 会拦住并要求登记鉴权，
但没有任何断言会问「它留痕了吗」。而那正是缺口 B 的成因。

现在改成：**每个管理端写路由都必须恰好落在三张表之一** ——
①`operation_audit` ②领域台账（必须在登记里写明是哪本台账，并断言对应的领域操作调用真的存在）
③显式豁免（上限 2 项，且必须写明理由）。14 个管理端写路由：①10 个、②3 个、③1 个。

**顺带核实（避免误判为缺口）**：`/api/admin/registration`、`/api/admin/review`、`/api/admin/referees`
全文不含 `recordOperationAuditSafely`，看着像漏了。实际不是：它们走的就是本节表格里那三本领域台账，
逐条写入且带 actorId 与 reason。**弱的是守卫，不是实现。**

变异验证 6 次（含 1 次对照组）记录在 `docs/10-后续开发规划/17-代码审计与架构优化方案_v1.0.md`
的「第十批」。

## 5. 缺口 C：共享管理员身份无法归因（OPN-07）

### 5.1 现状与根因

- 登录只有一个 `ADMIN_PASSWORD` 环境变量；会话 token 是 `过期时间戳.HMAC(时间戳)`，
  **不含任何身份字段**，`verifySessionToken()` 只返回布尔值。
- 因此 `operation_audit.actor_hash` 只能是**「密钥 + 客户端 IP」的 SHA-256**。
  它是位置标识，不是人的标识：**同一网络下多人登录得到完全相同的哈希**。

**这是一处刻意的设计取舍**，不是遗漏——决策 D-044 写明「当前团队规模小，
共享账号可接受，但不同赛事数据不能互相影响」，后者已通过赛事级数据隔离实现。

**当前风险等级**：这一届赛事实际只有负责人一人在操作后台，共享账号带来的归因缺失
**目前不产生实际影响**。但一旦有第二名工作人员，破坏性操作（删除赛事、重置裁判凭证、
覆盖赛程）就无法定位到人。

### 5.2 多管理员迁移方案（不阻塞当前办赛）

**原则：可分批、可回退、期间不断服务。**

**阶段 0（现在，零代码）**：接受现状，在台账记录该局限与本届的风险承担人（负责人本人）。
10.7 开赛不受影响。

**阶段 1（身份可区分，向后兼容）**
- 新增 `admin_users` 表：`id / display_name / password_hash / disabled_at / created_at`。
  首个管理员由负责人手工插入。
- `createSessionToken()` 增加 `actorId` 参数 → token 变为 `过期时间戳.actorId.HMAC(全部)`；
