## 0. 这次做了什么、没做什么

做了什么：

- 静态通读数据层、鉴权层、代理层，以及全部 36 个 API 路由。

## 1. 漏洞

### V1 【高危 · 已修复】管理端保存赛程时会静默覆盖裁判已报的赛果

**这是什么。** 负责人在管理端赛程页做任意一次赛程操作（排期、批准改期、报分），保存时会把**裁判已经上报的比赛结果**抹掉：比赛从「已完成」退回「已排期」，逐局比分与 BP 选图一起消失。两条路径都不报错，负责人和裁判都不会知道。

**怎么确认的。** 写了一段复现脚本（`.workbuddy/repro-schedule-overwrite.ts`），按两条路径的原始逻辑逐步走：

```
前置：   M-Q1 状态 = 已排期，version = 5
步骤1：  裁判报分 → M-Q1 状态 = 已完成（2 局），version 仍 = 5   ← 关键：版本号没动
步骤2：  管理端保存旧快照 → 未被版本校验拦下
最终：   M-Q1 状态 = 已排期，局数 = 0，version = 6
```

即：裁判的报分被丢掉，且没有任何一方收到错误。

**根因是三件事叠在一起。**

1. `schedule` 这份文档有四个写手：管理端整份保存、裁判报分、BP 完成、队长约赛。
2. 后三条路径都**不递增 `schedule.version`**。而 `version` 正是管理端「整份覆盖」时用的乐观锁。
3. 管理端赛程页只在挂载时读一次，之后不再刷新，手里一直留着旧快照。

所以版本号一致 ≠ 内容是最新的，护栏因此形同虚设。

**为什么不能简单地把「让所有写手都递增版本」当成解法。** 裁判报分用的是一句严格比对：

```ts
if (input.basedOnScheduleVersion !== ctx.scheduleVersion) { 拒绝 }
```

一旦报分自己也递增版本，那么裁判报完第一场之后，其他裁判页面上揣着旧版本的提交会全部被拒。所以「不递增」对报分路径而言是**刻意的**，它是用一个护栏的失效，换另一个流程的可用。这是一个真实的设计取舍，不是笔误。

**修法（本次已实施）。** 保留版本号原有语义不动，在整份保存处补一道**内容级**护栏：

- 新增纯函数 `detectScheduleLosses`：只检查「同一场比赛在前后两份里都存在」的情况，若比赛从「已完成」退回、逐局比分变少、或 BP 选图变少，就判为丢失。
- 新增纯函数 `applyScheduleSave`：先比版本号，再比内容，最后才合并写入；三种结果分别是「保存」「版本冲突」「会丢成果」。
- 路由把「会丢成果」以 409 返回，并点名是哪一场、丢了什么。
- 管理端收到 409 后**自动重载最新赛程**，并提示负责人，而不是让他对着过期数据反复提交。

**为什么护栏的口径刻意写窄。** 只覆盖「同一场比赛前后都在」这一种情况，是为了不误伤两条正当流程：「归档并清空赛程」和「从抽签重新导入对阵」都会正当地让比赛消失，它们各自有自己的归档与版本记录。判据用「变少」而不是「不相等」，所以正常补写比分、补选地图不会被拦。

**验证。** 新增 `npm run test:schedule-loss`，16 项断言分四组：判据正确性、裁决优先级、存储层回归（复现原路径并确认已被拦下）、以及**变异验证**——同一份夹具在摘掉护栏时必须真的丢数据。最后一组是为了防止「夹具没有区分度导致测试恒真」这种假绿。

### V2 【中 · 已修复】版本号作为乐观锁，对三条写手路径仍然不生效

V1 修的是「赛果与 BP 会被抹掉」这一种后果。但根因没变：`version` 对报分、BP、队长约赛三条路径仍然没有约束力。下面这些后果**护栏没有覆盖**：

- 队长提交的**待处理约赛申请**会被管理端的旧快照丢掉（申请不在比赛对象里，护栏看不到）。
- BP 完成时写入的**通知草稿**会一起消失。
- 管理端看到的是过期赛程（页面不轮询），而它下一次保存不会再被拦——因为它根本不知道有变更。

**已按原定方案实施（2026-10-12，与 V1 同批）。** 做法是把两个被混用的含义拆开：

- `schedule.version` 退回它本来的含义——「这份文档变过没有」。**五条写入路径全部递增**，共同的递增入口是 `schedule-ops.ts` 的 `stampScheduleVersion`（内容没变时不递增，避免无意义地让别人的编辑器失效；成功后一律 `current.version + 1`，不采信客户端传来的版本值）。
- 裁判那条严格比对换成了**逐场前置条件**：比赛仍存在、且当前对阵与裁判回传的两队队名一致（新的 `MATCH_CHANGED`，路由以 409 返回）。`basedOnScheduleVersion` 降级为审计字段，仍写进提交记录供复核队列展示。

**一个意外的佐证。** 改完之后发现 `rule-engine.ts` 的 `validateReschedule` 里早就留着一句「`void currentVersion;`」，注释写着这条 `basedOnVersion === currentVersion` 的规则「**2026-10-09 去掉，因为它在实战中必然误报**：版本号是**全局**的 —— 任何一场比赛报分、任何一次改期都会让它 +1」。

也就是说，代码里另一处已经**按「版本号全局递增」这个前提**做过一次判断，而当时那个前提并不成立（报分其实不递增）。这次统一是把前提补成事实，而不是又加一层补丁。这也顺带确认了：`validateReschedule` 不读 `currentVersion`，所以让 `version` 变得更频繁地变化**不会**让约赛申请集体失效。

**为什么必须两件事同批做。** 只递增版本、不动裁判那条比对，会让裁判报分在整个赛程里被别人的操作反复拒掉；只改比对、不递增版本，V1 的丢失路径依然敞开。两者是同一个契约的两半。

**一处刻意的取舍。** 换掉版本比对之后，原型里「抽签重排把 `M01` 换成另一对队伍、而裁判页面还是旧对阵」这一种情况，靠回传队名拦（而不是靠版本号）。代价是裁判端要回传两个队名；换来的是判定**只依赖这场比赛自己**，两名裁判同时报不同场次不再互相影响。

**验证。** `npm run test:result` 与 `test:reporting` 各新增三条断言，其中一条专门锁「别的场次让版本号 +1 后本场仍可提交」（旧实现在这里会误拒）。另新增 `npm run test:schedule-write-contract`：用**源码断言**把契约钉住——全仓库写入 `schedule` 的位置必须与冻结清单一致（新增写入点立刻失败），每个非豁免写入文件必须真的调用递增入口。这条守卫做过变异验证：把 `reporting-data.ts` 的 `stampScheduleVersion(` 调用摘掉后，它确实变红（第一版只判断「出现了这个名字」，被 import 行蒙混过关，已改成「剥掉 import 后必须存在带括号的调用」）。

### V3 【中 · 已修复】`/api/data/registration` 未校验赛事 ID，非法 ID 返回 500

同一个目录下的三个路由本是同构的，但这个路由漏了两件事：

- `data/schedule` 与 `data/format` 都会把 `eventId` 和站点配置比对后再用，只有它直接把 query 原样透传。后果是持有合法会话的人可以读到任意（例如已删除赛事）的报名数据。
- 数据层的 `assertSafeEventId` 是**抛错**的，而这里没有 try/catch，于是非法 ID（含斜杠等）会变成 500 而不是 401。

已按两个同级路由的写法对齐。附带说明：路径穿越本身不成立——`assertSafeEventId` 的正则是 `^[a-zA-Z0-9_-]{1,60}$`，点和斜杠都被挡掉。

### V4 【低 · 经查证不成立】限流按 `x-forwarded-for` 第一段取值，不构成绕过

代理层用 `x-forwarded-for` 的第一段做限流键。这是常见的 IP 伪造绕过点，所以我先去查了 Vercel 的实际行为，而不是凭印象判断。

结论：**不成立。** Vercel 官方文档明确写着它自己填充该头并**覆盖**任何传入值，用来防止 IP 伪造；官方知识库也确认「Vercel 位于最外层时，最左边的条目可靠地就是真实客户端 IP」。本站域名直接挂在 Vercel 上，正是这个前提。

需要记住的是它的**失效条件**：如果在 Vercel 前面再加一层 CDN 或反向代理，`x-forwarded-for` 就会变成上游代理的 IP，届时所有用户共用一个限流桶（不是被绕过，而是所有人一起被限）。那时应改用 `x-vercel-forwarded-for`。这条记在这里，不是待办。

### V5 【低 · 已修复】路由守卫测试只覆盖 `/api/admin`，另外 16 个路由没有同类护栏

现有的 SYS-04 守卫测试质量很高——它会先剔除本地函数定义再找调用，避免「删掉调用但保留定义」这种回退被漏检。但它的枚举根目录写死成 `src/app/api/admin`。

我机械核对了全部 29 个写路由的鉴权归属，结果是**没有发现越权写**：`/api/data/*` 有路由内的会话校验（`data/format`、`data/schedule` 与代理层构成双保险），`/api/referee/*` 由裁判凭证推导身份且逐操作校验，`/api/public/*` 各自按领域规则校验。也就是说现状是安全的，**缺的是「下一次新增路由时有人提醒」这个机制**。

**已实施（2026-10-12）。** 枚举根目录扩到全部 `api`（原文件 `admin-route-guards.test.ts` → `api-route-guards.test.ts`），并加了一份**冻结的写路由清单**（28 条）：新增或删除任何写路由都会让测试失败，迫使作者显式登记这条路由由谁鉴权。公开写路由另有一张自鉴权登记表，记下每条「怎么解决身份问题」以及断言用的调用标记（光登记不实现同样会被拦下）。

同样做了变异验证：临时新增一个 `/api/public/temp-mutation-check` 路由，测试立刻变红；移除后恢复绿。

### V6 【低 · 已核实缓解】演示数据播种代码在生产包内

`src/lib/referee/reporting-data.ts` 里有一个演示赛事 ID 与一个播种函数：任何请求命中 `DEMO_EVENT_ID`（`demo-referee`）时，会在该赛事下写入一份演示赛程与裁判台账。

### V7 【低 · 设计限制，非缺陷】单一共享口令 + 无服务端吊销

- 管理员是**单一共享口令**，审计记录里无法区分到人。
- 会话是 7 天无状态签名 token，**服务端没有吊销机制**——唯一失效手段是轮换 `AUTH_SECRET`，而那会同时踢掉所有人。
- 因此登录限流（10 次 / 15 分钟 / IP）是爆破的唯一防线。对当前规模够用，但参赛规模上来后值得重新评估。

### V8 【中 · 已修复】裁判端「凭证无效」在 `submit` 上回 400，并把内部码当成提示文案

**怎么发现的**：不是读代码发现的，是**写本地端到端脚本时**用无效凭证逐个打了六个裁判接口 —— 只有 `submit` 表现不一样，其余五个都是 401。这也说明这类「同一件事有六处各写一遍」的问题，静态通读很难看出来。

**原状**：`claim` / `upload` / `recognize` 三处各自把「哪些失败码算未授权」写了一遍（`recognize` 里其实写了两遍），`matches` 与 `login` 靠调用方硬编码一句中文兜住，而 `submit` **完全漏了这一层**：所有失败一律 400，并且把领域层返回的内部码 `INVALID_CREDENTIAL` **原样当 `message` 返回**。

**两层后果**：
1. 裁判屏幕上显示的是一串大写英文，他不知道该重新登录；
2. 负责人看到同一串英文，无从判断「是这个裁判的凭证问题，还是系统坏了」，也就不知道该不该重置凭证。

顺带把两类失败混成了一类：`MATCH_CHANGED`（对阵已变更，客户端应刷新后重看）本就该用 409 与「校验失败」区分开 —— 而 `submit` 自己的注释里就写着这句 —— 实测却也是 400，客户端只会当成「输入不合法」原地重试。

**改法**：新增 `src/lib/referee/failure-response.ts` 作为单一出处，六个接口的路由全部改走它。

关键设计：这个函数**返回 `Response` 而不是只返回状态码**。这样状态码与文案必然成对产生，调用点不可能出现「改了状态码、忘了换文案」—— `submit` 当初就是这么漏的。个别路由的正常竞争结果（已被人认领 → 409、对阵已变更 → 409）作为 `extra` 参数传入，保持默认表不被污染。

`NOT_ASSIGNED`（这场没分给你）为什么仍判 **401** 而不是语义更准的 403：沿用既有约定，staging 端到端脚本已按 `未指派的比赛被拒（401）` 断言过。要改就四处一起改，不在这一处单独改。

顺带修掉同一类泄漏：`reporting-data.ts` 里 `refereeLogin` / `refereeMyMatches` 把内部码塞进 `error` 字段（靠调用方硬编码中文兜住），`refereeOpenMatches` 干脆没有 `code` —— 于是 `claim` 的 GET 只能硬编码 401 兜住，形状一改就错。

**验证**：`src/lib/referee/failure-response.test.ts`（39 项，其中第 4 组要求**每一档未授权失败码都要有中文文案、且不能是内部码**）+ 端到端脚本第 1 节（七个调用点，见第八批）。

## 2. 冗余与死代码

先给一个方法上的提醒：本节的结论来自脚本枚举，而「无人引用」有两类——**真的没人用**，和**只在自己文件里用**（那只是 `export` 关键字多余）。下面分开列。

### 2.1 整个文件零引用

> **本小节的初版结论有一处错的，已更正。** 初版把 `src/types/index.ts` 也列为零引用，那是**方法错误造成的假阳性**：我用「路径字面量」搜 `types/index`，而这个文件是被 `from "@/types"` 这样**按目录解析**到 `index.ts` 的，字面量搜索看不见。改用模块解析规则重新枚举后确认：它被 7 个文件 import，**是活的**。
>
> 教训：报「零引用」之前，必须确认搜索范围与解析规则真的覆盖了全部引用方式。目录解析、同目录相对导入（`from "./X"`）这两种最容易漏。

真正的孤儿共 6 个，**本次已全部删除**（删除前逐个重验过引用）：

| 文件 | 外部引用数 | 说明 |
|---|---|---|
| `src/components/ui/Card.tsx` | 0 | 旧设计（圆角 + 投影），与现行设计系统（无圆角、无阴影、1px 墨色结构线）相冲突，留着只会被误用 |
| `src/components/ClientRedirect.tsx` | 0 | —— |
| `src/lib/scheduling/bracket.ts` | 0 | 整文件只有一句 `export * from "./bracket-engine"`，纯转口，无附加逻辑 |
| `src/lib/scheduling/referee-session.ts` | 0 | 裁判会话机制整套（签发、校验、cookie 名、类型），无人 import |
| `src/lib/scheduling/useFormat.ts` | 0 | 一个赛制状态 hook，无人 import |
| `src/app/api/public/team/member/route.ts` | 0 | 见 2.2 |

### 2.2 死路由

## 3. 架构优化方案

### 3.1 现状分层

四层，职责总体是清楚的：

1. **数据层** `src/lib/data-store.ts` 及其驱动。双后端（本地 file / 生产 supabase），提供 `read`/`write`/`update`/`updateMany`/`deleteEvent`。生产侧有数据库行级版本 CAS 与批量事务函数，本地侧有赛事级写锁与失败回滚。

### V9 【中 · 已修复】备份导出工具：缺一份可选文档就让整份备份导不出来，且 `passed` 恒为真

`tools/gate6/backup-restore.ts` 是「库里那份是唯一一份」时**唯一的救命工具**（Supabase 免费版无自动备份）。
2026-10-12 开赛后复查，发现三处问题：

1. **遇到任一文档缺失就 `throw`** —— 「这场赛事还没做过 BP」是**正常**的，却会让**整份备份一个字都写不出来**。
   → 在良性的缺口上 fail-closed 是错的失败方式。改成记成「导出时即不存在」、照常导出、在报告里点名；
   但留一条底线：**全部缺失仍然失败**（空备份等于没有备份）。

   —— 它会让读报告的人以为有保护，实际上那个字段什么都没在报告。
   → 改成只回答「这份备份可信吗」；「缺了哪几份」交给独立的 `absentDocuments`。
3. **生成端与校验端各有一份 `stable()` / `checksum()`** —— 两边悄悄走偏的后果是校验工具对
   **完好的**备份报错，从此没人再信它。→ 抽到 `tools/gate6/backup-format.ts`，两端 `import`。

另加两道护栏：**不许静默覆盖已有备份**（上一次的副本可能就是唯一一份好的，要顶掉得显式 `--overwrite`）；

**一处我先前说重了，在此更正**：`tools/data/migrate-local-to-supabase.ts:87` 里也有一个 `stable()`，
本节初稿把它写成「第三份同类冗余」。查过用法后不成立 —— 它唯一的用途是第 122 行
`if (stable(stored) !== stable(value))`：**同一个进程、同一个函数、比较自己刚算出的两个值**。
它不需要与备份那套算法一致，因此没有「两边走偏」这回事，只是个重复实现的写法问题。
备份那一份不同：生成端与校验端**跨进程、跨时间**，必须共用同一套算法 —— 那才是真契约。
（判据可以记住：**「同一个进程里自己比自己」不是契约，「换个时候/换个地方再算一次」才是**。）

**2026-10-12 补充（第十一批）**：上面这条更正只说到「不是契约」，没说「那就留着」。
但它仍是**第二份逐字相同的实现** —— 两份拷贝不会互相走偏，却会**各自被后人改**：
有人给其中一份加了 `Date` 处理，另一份还是老样子，从此同一个函数名在两处行为不同。
已把那处改成 `import`（`stable` 只在 `backup-format.ts` 里实现一份），并加了一条源码断言守住它。
理由与「为什么这次不再说『可以等到要加第二款游戏时再做』」见第十一批。

### 第十二批：把「路由级鉴权」从 12 份拷贝收成一份，并让守卫能证明它在验签

第十一批收尾时注意到一件事：**这套守卫已经因为「只认名字」栽过一次**（组 5 的留痕归属）。
于是回头逐条问：「组 1 那条鉴权断言，真的能拦住什么？」——查下去发现同一个毛病又犯了一次。

**V12 【中 · 已修复】组 1 只证明「调用了鉴权」，证明不了「那个东西真的在校验」**

组 1 当时的判据是：管理端写路由里必须出现 `isAdmin(` 或 `verifySessionToken(` 调用
（而且还专门修过一次，先剥掉本地函数定义再找调用 —— 那一版是对的方向）。
但它管不了**被调用的东西的里面**：`isAdmin` 原本是**每个路由文件各写一份**的本地函数，
把其中一份的函数体改成 `return true`，名还在、调用还在，**整套守卫仍然全绿**。

**实测确认（这条是本批的出发点）**：把 `/api/admin/site-config` 的 `isAdmin` 改成
`function isAdmin(request) { void request; return true; }` → 运行守卫 → **28 项 + 9 组全部通过，EXIT=0**。
也就是说：一个把管理员校验彻底写成恒真的改动，CI 拦不住。

**修法**（与 `stable()` / 游戏配置同一套路：**收成一份实现 + 让守职能断言它**）：

1. **收掉 12 份拷贝**：新增 `src/lib/auth.ts` 的 `isAdminRequest(request)`，
   12 个管理端路由文件（`events` ×3、`registration` ×2、`referees`、`review`、
   `rule-library`、`site-config`、`site-content`、`upload`、`registration/export`）
   删掉各自的 `function isAdmin`，改为 `import { isAdminRequest } from "@/lib/auth"`。
   共 18 处调用点，用脚本改（干跑 → 写盘 → 自检调用点数一致）。
2. **守卫加两条断言**：
   - 管理端写路由**不得再自写鉴权函数**（出现 `function isAdmin` 即红，并点名是哪个路由）；
   - 共享实现的函数体必须**返回** `verifySessionToken(...)` —— 不能恒真、不能带旁路。

**边界（写清楚，免得被当成「已经全仓统一」）**：`src/proxy.ts` 与 `data/*` 路由、赛事页预览模式等处
仍**直接调 `verifySessionToken`**。那是**同一个底层函数**的不同调用形态，不是第二份实现，
所以不在禁止之列 —— 真正被收掉的只是「同一个包装被抄了 12 份」。

**为什么这一条排在赛事期也值得做**：它是**鉴权**（不是界面）。
而且这次改动是「表达式原样搬家」，外加 12 个文件里**唯一**会变的是「从哪取这个函数」。
仍然做了三层验证：类型检查 → 端到端 HTTP 实测 → 全门禁。

**变异验证（含对照）**：

| 变异 | 期望 | 实测 |
|---|---|---|
| M1 把共享实现 `isAdminRequest` 改成 `return true` | 红 | ✅ 报出实际函数体，指出「必须返回 verifySessionToken 的结论」 |
| M2 把本地 `function isAdmin` 塞回 `site-content` | 红 | ✅ 报 `/api/admin/site-content` 不得自写鉴权函数 |
| **M3 对照组**：还原后 | 绿 | ✅ 28 项 + 9 组全通过 |

**端到端 HTTP 实测（真起 dev server，7/7）**：登录 200 并下发 cookie ｜ 带凭证访问
`/api/admin/referees` → 200 ｜ 不带凭证 → 401 且文案是可照着做的中文 ｜
**签名被改过 → 401** ｜ **签名正确但已过期 → 401** ｜ **自造的有效 token → 200（对照组，
证明上一条不是被别的原因拒的）**。
→ 后三条合起来才说明「它真的在验签」，而不是「看到一个叫 admin_session 的 cookie 就放行」。

**顺手踩到并记下的一个坑**：脚本判断「某个导入是否还在被使用」时按「文中是否出现这个名字」，
结果被**注释里提到它**骗过（`referees` / `review` 的头部注释写着「鉴权复用……verifySessionToken」）
→ 保留了没用的导入，被 lint 的 `no-unused-vars` 抓出来 2 个警告。
→ **教训：判断「是否还被使用」不能只按词出现（注释、字符串都算）；这类判断要交给 lint/typecheck 兜底。**

### 第十三批：赛程写入契约守卫的两处盲区（都发生在**唯一确认过的数据丢失区**）

上一批把「鉴权」那条约束收成了可断言的东西。这一批顺着同一个问题往下问：
**「守卫只认存在」这个毛病，还有哪些守卫犯？** 去查了赛程写入契约 —— 那是 V1（裁判赛果被管理端旧快照
静默覆盖）的守卫，也是全仓库唯一**已经造成过真实数据丢失**的地方。

**V13 【中 · 已修复】这份守卫「看见了自己的证据却不拿它比较」，且只认「调用发生过」**

两处盲区，都用变异实测确认过：

**① 条数粒度太粗。** 守卫确实算出了「每个文件里有几条写入 `schedule` 的路径」，
**甚至把它打印出来**（`app/api/data/bp/route.ts×2`），但断言只比对**文件名列表** ——
所以往一个**已登记的文件**里再加第二条写入路径，它完全看不见。

> 变异实测：给 `app/api/data/bp/route.ts` 加第二条 `updateEventData(…, "schedule", …)`
> 且不递增 version → 守卫**12/12 通过**，而它上一行刚刚打印了 `bp/route.ts×2`。
> **「算出来了但没拿来比」是这次最刺眼的一处** —— 证据就在眼前，断言却绕过了它。

**② 只认「调用发生过」，不认「结果被用上」。** 组 2 只查该文件里出现过 `stampScheduleVersion(`，
于是下面这种形状照样全绿：

```ts
stampScheduleVersion(schedule, next);   // 算出了新版本
return schedule;                         // 却把旧快照返回去 —— 版本护栏再次静默失效
```

变异实测确认：把 `bp/route.ts` 的 `return stampScheduleVersion(...)` 改成裸调用 + `return schedule`
→ 守卫仍全绿。**这正好是那次数据丢失的形状。**

**修法（把两处都变成可断言的）：**

| 补的断言 | 挡住的形状 |
|---|---|
| 每个文件的写入条数也必须与冻结清单一致（清单加 `sites` 字段） | 往已登记文件里新增 / 删除一条写入路径 |
| `sites` 必须是正整数 | 写 0 或漏写，让上面那条失去意义 |
| 递增调用的结果必须出现在**捕获位置**（`return` / `=` / `=>`） | 调完就扔、把旧快照返回去 |

清点结果：5 个文件 6 条写入路径（`schedule/route.ts` 1、`bp/route.ts` 1、
`public/schedule/request/route.ts` 2、`reporting-data.ts` 1、`admin/events` 1 豁免）。
断言数 12 → **18 项**。

**变异验证 3 次（含 1 次对照组）：**

| 变异 | 期望 | 实测 |
|---|---|---|
| M1 给 `bp/route.ts` 加第二条 `…, "schedule", …` 写入路径 | 红 | ✅ 条数断言红，列出「发现 ×2 / 登记 ×1」 |
| M2 `return stampScheduleVersion(...)` → 裸调用 + `return schedule` | 红 | ✅ 结果未被用上，报出该文件 |
| **M3 对照组**：改成合法重构 `const next = stampScheduleVersion(...); return next;` | **绿** | ✅ 绿 —— 说明捕获位置的判据不是「只认字面上的 `return`」 |

**M3 这条对照是必要的**：不写它，就无法排除「断言只是恰好匹配了当前写法」。
（同第九批、第十二批：**新加的约束要能证明它不误伤合法写法。**）

**这一类的第四次。** 目前已经出现四次「断言只认存在」，每次都换一层：

### 第十四批：「用哪个数据后端」由 4 份拷贝收成一份，并统一取最严的那一档

第十二批把「鉴权」收成了单一份实现，第十三批补了赛程契约守卫的两处盲区。这一批继续沿着
**「同一个决策写了多份」**往下清，这次是数据层最容易踩的那个坑：**本地 file / 生产 supabase**。

**V14 【中 · 已修复】`selectedBackend()` 在 4 个文件里各写一份，其中 3 份的行为比第 4 份宽 —— 会静默降级**

四处是：`data-store.ts`（数据层）、`asset-store.ts`（图片）、`referee/evidence-store.ts`（裁判截图）、
`rate-limit.ts`（限流计数）。它们读同一个环境变量、回答同一个问题，**但其中三份少了一个分支**：

| | 取值是 `file` / `supabase` | 取值**无法识别**（例如 `supabse`） | 未设置 |
|---|---|---|---|
| `data-store.ts` | 用它 | **抛错** `不支持的数据后端：supabse` | 托管抛错 / 本地 `file` |
| 另外三份 | 用它 | **静默退回 `file`** | 同左 |

也就是说：**同一个写错的值，有的模块当场报错、有的悄悄降级**。而「两套数据后端」正是本仓库
最容易踩的坑 —— 降级到 `file` 在托管环境意味着写到临时文件系统，写进去的东西下次部署就没了。

> 注：在托管环境里 `isHostedRuntime()` 为真，那三份也会抛错，所以生产上没炸；
> 分歧主要发生在本地与演练环境。但「同一个配置错误有两种表现」本身就是该收掉的东西 ——
> 它让「我这里好好的」变成一句不可靠的话。

**修法两步：**

1. 新增 `src/lib/data-backend.ts`，`resolveDataBackend()` 是**唯一**读 `process.env.DATA_BACKEND` 的地方，
   统一取**最严**的一档（无法识别的非空值一律抛错）。四处改为 import。
   顺带把托管环境那句话说准确：原来 `data-store` 写「Vercel 环境…」、另外三处写「托管环境…」，
   统一为「托管环境」（`isHostedRuntime()` 也覆盖 `REQUIRE_PRODUCTION_SECRETS`，不只是 Vercel）。
2. 新增 `src/lib/data-backend.test.ts`（**11 项**，已接入 `test:all`，套件数 30 → **31**）。
   它与本文件其它源码扫描守卫不同 —— **第 1 组是真跑**：改环境变量、真调 `resolveDataBackend()`，
   逐档验行为；第 2 组才是源码扫描「只有一处读它」。

**★ 为什么这一批坚持要「真跑」而不是只做源码扫描**：扫描只能证明「没有第二份」，
证明不了「这一份算得对」。而这次的问题恰恰是**这一份算错了**（少一个分支）。
行为断言才是能抓住它的那个。

**变异验证 2 次（含对照）：**

| 变异 | 期望 | 实测 |
|---|---|---|
| M1 让某个消费方自己再读一次 `process.env.DATA_BACKEND` | 红 | ✅ 报出 `["…data-backend.ts","…data-store.ts"]`，并指出哪个消费方没改走共享函数 |
| M2 **把严格分支去掉**（即还原成原先那三份的行为） | 红 | ✅ 两条行为断言变红，失败信息写明「没有抛错 —— 这就是原先那三份拷贝的行为」 |
| M3 对照组：还原后 | 绿 | ✅ 11/11 |

**M2 这条是本批的关键**：它证明「如果当初只有行为断言，这次的分歧会被当场测出来」；
反过来也说明，只做源码扫描的守卫对这个 bug 是无效的。

**一处刻意没做的（如实记下，不是漏了）**：同一批里还发现「取 `SUPABASE_URL` + `SUPABASE_SECRET_KEY`、
缺失就抛错」这个形状在 **6 处**各写一份（`asset-store` / `evidence-store` / `operation-audit` /
`rate-limit` / `supabase-data-store`，另有一处 `health` 是探活、语义不同）。
它们彼此**只有错误文案不同、没有行为分歧**，收益主要是整洁；但收口牵动
`api-route-guards` 组 8 里一条断言（它锁着 `throw new Error("图片存储缺少 Supabase 配置")` 这串字面量，
而那条断言的用意是「缺配置必须是普通 Error、由路由泛化」）。为一次零行为变化的整理去动
**线上数据层 + 一条安全相关断言**，性价比不划算 —— 留给「赛事期指挥台」那轮一起做。
（判据：**有行为分歧的重复优先收；只有文案差别的重复，等一个本来就要动那些文件的时机。**）
