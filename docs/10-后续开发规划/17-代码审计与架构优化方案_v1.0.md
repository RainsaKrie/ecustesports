# 代码审计与架构优化方案 v1.0

日期：2026-10-12
范围：`src` 下 193 个 TS/TSX 文件、36 个 API 路由、数据层与服务端领域逻辑

## 0. 这次做了什么、没做什么

做了什么：

- 静态通读数据层、鉴权层、代理层，以及全部 36 个 API 路由。
- 用脚本机械化核对两件事：每个写路由归谁鉴权、哪些导出全仓库无人引用。
- 对最可疑的一条做了**实测复现**（见 V1），不是只靠读代码下结论。

没做什么（后续可补）：

- 没有做线上渗透测试，没有对生产 Supabase 的库结构、行级安全策略做审计。
- 没有跑依赖漏洞扫描（`npm audit` 之类）。

一句结论：**系统的基础安全做工比预期好**（无状态签名会话、恒定时间比较、批量事务 CAS、错误按业务/内部分流、限流兜底完整、路径穿越有白名单校验），**真正的风险集中在「同一份数据有多个写手、却没有统一的写入契约」这一处**，而且它已经造成过一次可复现的数据丢失。

## 1. 漏洞

### V1 【高危 · 已修复】管理端保存赛程时会静默覆盖裁判已报的赛果

**这是什么。** 负责人在管理端赛程页做任意一次赛程操作（排期、批准改期、报分），保存时会把**裁判已经上报的比赛结果**抹掉：比赛从「已完成」退回「已排期」，逐局比分与 BP 选图一起消失。两条路径都不报错，负责人和裁判都不会知道。

**怎么确认的。** 写了一段复现脚本（`.workbuddy/repro-schedule-overwrite.ts`），按两条路径的原始逻辑逐步走：

```
前置：   M-Q1 状态 = 已排期，version = 5
步骤1：  裁判报分 → M-Q1 状态 = 已完成（2 局），version 仍 = 5   ← 关键：版本号没动
步骤2：  管理端保存旧快照 → 未被版本校验拦下
最终：   M-Q1 状态 = 已排期，局数 = 0，version = 6
```

即：裁判的报分被丢掉，且没有任何一方收到错误。

**根因是三件事叠在一起。**

1. `schedule` 这份文档有四个写手：管理端整份保存、裁判报分、BP 完成、队长约赛。
2. 后三条路径都**不递增 `schedule.version`**。而 `version` 正是管理端「整份覆盖」时用的乐观锁。
3. 管理端赛程页只在挂载时读一次，之后不再刷新，手里一直留着旧快照。

所以版本号一致 ≠ 内容是最新的，护栏因此形同虚设。

**为什么不能简单地把「让所有写手都递增版本」当成解法。** 裁判报分用的是一句严格比对：

```ts
if (input.basedOnScheduleVersion !== ctx.scheduleVersion) { 拒绝 }
```

一旦报分自己也递增版本，那么裁判报完第一场之后，其他裁判页面上揣着旧版本的提交会全部被拒。所以「不递增」对报分路径而言是**刻意的**，它是用一个护栏的失效，换另一个流程的可用。这是一个真实的设计取舍，不是笔误。

**修法（本次已实施）。** 保留版本号原有语义不动，在整份保存处补一道**内容级**护栏：

- 新增纯函数 `detectScheduleLosses`：只检查「同一场比赛在前后两份里都存在」的情况，若比赛从「已完成」退回、逐局比分变少、或 BP 选图变少，就判为丢失。
- 新增纯函数 `applyScheduleSave`：先比版本号，再比内容，最后才合并写入；三种结果分别是「保存」「版本冲突」「会丢成果」。
- 路由把「会丢成果」以 409 返回，并点名是哪一场、丢了什么。
- 管理端收到 409 后**自动重载最新赛程**，并提示负责人，而不是让他对着过期数据反复提交。

**为什么护栏的口径刻意写窄。** 只覆盖「同一场比赛前后都在」这一种情况，是为了不误伤两条正当流程：「归档并清空赛程」和「从抽签重新导入对阵」都会正当地让比赛消失，它们各自有自己的归档与版本记录。判据用「变少」而不是「不相等」，所以正常补写比分、补选地图不会被拦。

**验证。** 新增 `npm run test:schedule-loss`，16 项断言分四组：判据正确性、裁决优先级、存储层回归（复现原路径并确认已被拦下）、以及**变异验证**——同一份夹具在摘掉护栏时必须真的丢数据。最后一组是为了防止「夹具没有区分度导致测试恒真」这种假绿。

### V2 【中 · 未修复】版本号作为乐观锁，对三条写手路径仍然不生效

V1 修的是「赛果与 BP 会被抹掉」这一种后果。但根因没变：`version` 对报分、BP、队长约赛三条路径仍然没有约束力。下面这些后果**护栏没有覆盖**：

- 队长提交的**待处理约赛申请**会被管理端的旧快照丢掉（申请不在比赛对象里，护栏看不到）。
- BP 完成时写入的**通知草稿**会一起消失。
- 管理端看到的是过期赛程（页面不轮询），而它下一次保存不会再被拦——因为它根本不知道有变更。

想彻底解决，需要把两个被混用的含义拆开：

- `schedule.version` 退回它本来的含义——「这份文档变过没有」，任何写手都必须递增。
- 裁判那条严格比对改为**只校验这场比赛本身的前置条件**（比赛还在、状态没被取代、分配未撤销），而不是整份文档的版本。

这个改动会动到已冻结的赛果域契约（`result-ops` 与 `reporting-service` 两套测试都锁着 `VERSION_CONFLICT` 行为），需要你点头再动。

### V3 【中 · 已修复】`/api/data/registration` 未校验赛事 ID，非法 ID 返回 500

同一个目录下的三个路由本是同构的，但这个路由漏了两件事：

- `data/schedule` 与 `data/format` 都会把 `eventId` 和站点配置比对后再用，只有它直接把 query 原样透传。后果是持有合法会话的人可以读到任意（例如已删除赛事）的报名数据。
- 数据层的 `assertSafeEventId` 是**抛错**的，而这里没有 try/catch，于是非法 ID（含斜杠等）会变成 500 而不是 401。

已按两个同级路由的写法对齐。附带说明：路径穿越本身不成立——`assertSafeEventId` 的正则是 `^[a-zA-Z0-9_-]{1,60}$`，点和斜杠都被挡掉。

---

### V4 【低 · 经查证不成立】限流按 `x-forwarded-for` 第一段取值，不构成绕过

代理层用 `x-forwarded-for` 的第一段做限流键。这是常见的 IP 伪造绕过点，所以我先去查了 Vercel 的实际行为，而不是凭印象判断。

结论：**不成立。** Vercel 官方文档明确写着它自己填充该头并**覆盖**任何传入值，用来防止 IP 伪造；官方知识库也确认「Vercel 位于最外层时，最左边的条目可靠地就是真实客户端 IP」。本站域名直接挂在 Vercel 上，正是这个前提。

需要记住的是它的**失效条件**：如果在 Vercel 前面再加一层 CDN 或反向代理，`x-forwarded-for` 就会变成上游代理的 IP，届时所有用户共用一个限流桶（不是被绕过，而是所有人一起被限）。那时应改用 `x-vercel-forwarded-for`。这条记在这里，不是待办。

---

### V5 【低 · 未修复】路由守卫测试只覆盖 `/api/admin`，另外 16 个路由没有同类护栏

现有的 SYS-04 守卫测试质量很高——它会先剔除本地函数定义再找调用，避免「删掉调用但保留定义」这种回退被漏检。但它的枚举根目录写死成 `src/app/api/admin`。

我机械核对了全部 29 个写路由的鉴权归属，结果是**没有发现越权写**：`/api/data/*` 有路由内的会话校验（`data/format`、`data/schedule` 与代理层构成双保险），`/api/referee/*` 由裁判凭证推导身份且逐操作校验，`/api/public/*` 各自按领域规则校验。也就是说现状是安全的，**缺的是「下一次新增路由时有人提醒」**这个机制。

建议把该测试的枚举根目录扩到全部 `api`，并把「哪些路由必须自鉴权」写成一份显式清单（现有 AUTH_EXEMPT 已经是这个形状，扩展即可）。

---

### V6 【低 · 未修复】演示数据播种代码在生产包内

`src/lib/referee/reporting-data.ts` 里有一个演示赛事 ID 与一个播种函数：任何请求命中 `DEMO_EVENT_ID`（`demo-referee`）时，会在该赛事下写入一份演示赛程与裁判台账。

实际风险很低（真实赛事很难恰好叫这个名字），但“往生产包塞一段会写数据的演示代码”本身是可以避免的。建议限定在非托管运行时执行。

---

### V7 【低 · 设计限制，非缺陷】单一共享口令 + 无服务端吊销

- 管理员是**单一共享口令**，审计记录里无法区分到人。
- 会话是 7 天无状态签名 token，**服务端没有吊销机制**——唯一失效手段是轮换 `AUTH_SECRET`，而那会同时踢掉所有人。
- 因此登录限流（10 次 / 15 分钟 / IP）是爆破的唯一防线。对当前规模够用，但参赛规模上来后值得重新评估。

## 2. 冗余与死代码

先给一个方法上的提醒：本节的结论来自脚本枚举，而「无人引用」有两类——**真的没人用**，和**只在自己文件里用**（那只是 `export` 关键字多余）。下面分开列。

### 2.1 整个文件零引用

| 文件 | 外部引用数 | 说明 |
|---|---|---|
| `src/types/index.ts` | 0 | 6 个导出（`TournamentFormat`/`RoundInfo`/`BPActionRecord`/`NavItem`/`AIContent` 等），无人 import |
| `src/lib/scheduling/referee-session.ts` | 0 | 裁判会话机制整套（签发、校验、cookie 名、类型），无人 import |
| `src/lib/scheduling/useFormat.ts` | 0 | 一个赛制状态 hook，无人 import |

`referee-session.ts` 这条值得单独看：它与「裁判入口事实上从未可用」是同一个信号——一套会话机制被写出来，但从没接上任何入口。

### 2.2 死路由

`/api/public/team/member` 的 `POST` 恒返回 `410 已停用`，而且它不在代理层的公开白名单里，未登录根本到不了。即双重不可达。它当初是被 `/api/public/team/request`（申请/邀请流程）替代的。

### 2.3 部分死亡的文件

| 文件 | 在用 | 已死 |
|---|---|---|
| `src/lib/mock-data.ts` | 仅 `mockEvent` | 其余 6 个导出（`mockTeams`/`mockPlayers`/`mockMatches`/`mockBPSession`/`getTeamById`/`getMatchesByRound`） |
| `src/lib/utils.ts` | 仅 `getStatusInfo`、`formatDate` | 其余 7 个导出（`generateId`/`formatDateTime`/`getRoundName`/`getTotalRounds`/`getTeamStatusInfo`/`getMatchStatusInfo` 等） |
| `src/lib/operation-audit.ts` | `recordOperationAuditSafely` | 会抛异常的 `recordOperationAudit` 与 `OperationAuditInput` |

`mock-data.ts` 还有一处结构问题：生产模块 `src/lib/configured-events.ts` 从名为 `mock-data` 的文件里 import 一个 `mockEvent`。名字说的是假数据，用途是真的兜底配置，容易误导。

### 2.4 多余的 `export` 关键字（不是死代码）

约 40 个符号是「导出但只在自己文件内使用」，包括 `OUTPUT_CONTRACT`、`READING_GUIDE`、`buildVisionPrompt`（识图提示词契约，确认真接进了调用点）、`issueCredential`（裁判凭证签发）等。它们**功能正常**，只是没必要对外暴露，收掉能缩小公共面。

### 2.5 本次已清理

- 3 条 lint 警告全部清零：`tools/gate6/atomic-batch-verify.ts` 未用的局部变量 `docs`、`recognize-result.test.ts` 未用的 `assert` 导入、`reporting-service.ts` 里 `projectOpenMatches` 一个**从未使用也因此无人传参**的可选参数 `squadsByTeamId`。
- 清理前 lint 为 0 错 3 警，清理后为 0 错 0 警。

## 3. 架构优化方案

### 3.1 现状分层

四层，职责总体是清楚的：

1. **数据层** `src/lib/data-store.ts` 及其驱动。双后端（本地 file / 生产 supabase），提供 `read`/`write`/`update`/`updateMany`/`deleteEvent`。生产侧有数据库行级版本 CAS 与批量事务函数，本地侧有赛事级写锁与失败回滚。
2. **领域层** `src/lib/scheduling/*`（大量纯函数 + `*-ops.ts`）与 `src/lib/referee/*`。这是最健康的一层：逻辑是纯的、可测的，测试覆盖密。
3. **接口层** 36 个 `route.ts`，多数很薄（读参数 → 校验 → 调领域函数 → 回响应）。
4. **UI 层** 组件。这里有问题，见 A4。

### 3.2 五个结构问题

**A1 · 同一份文档多写手，缺统一的写入契约（P0，V1/V2 的根因）**

`schedule` 有四个写手，各自对「并发」的理解不同：管理端理解成「版本号乐观锁」，报分理解成「我的版本必须等于当前版本」，BP 与队长约赛则完全没管。三套理解并存，就必然出现谁也不知道自己覆盖了谁。

建议：为每份文档写明「谁是唯一所有者、其他写手必须遵守什么」。就 `schedule` 而言，把它拆成「排期事实」与「比赛结果」两个所有权，或明确 `version` 由所有写手递增、裁判改按比赛级前置条件校验（即 V2 的方案）。

**A2 · 守卫测试以目录为范围，而不是以「全部路由」为范围（P0，成本极低）**

机制已经写好了，只是枚举范围小了一圈。扩范围 + 显式清单即可，是本次性价比最高的一项。

**A3 · 游戏配置硬编码在各处，与「涵盖主流游戏」的产品主张冲突（P0）**

产品主张已明确为「面向校园乃至第三方个体赛事，涵盖主流游戏」。但目前这些全部写死为《无畏契约》：

- 地图表（`VALORANT_MAPS`）
- 段位表与段位计分（`RANK_VALUE`）
- 位置（先锋/决斗/…）
- 队伍规模 5 人
- 识图提示词里的 `game: "valorant"`

赛事级虽然有一个 `game` 字段，但它不驱动上面任何一处。要兑现主张，需要抽出**一层游戏配置**（地图池、段位体系、位置、人数、赛制模板），让赛程、规则、BP、识图都从它取值。这是目前最大的一块结构性工作。

**A4 · 若干 UI 文件体量过大（P1）**

最大的五个：`RegistrationOperationsWorkspace.tsx` 75 KB、`FormatDrawWorkspace.tsx` 48 KB、`EventSettingsWorkspace.tsx` 42 KB、赛程页 41 KB、`RefereeWorkbench.tsx` 38 KB。单文件到这个体量，改一处要通读全部上下文，是维护成本的主要来源。建议按「面板」拆组件，而不是继续在单文件里加分支。

**A5 · 历史层与死代码没有清（P1，见第 2 节）**

`mock-data`、`legacy-site-content`、`types/index` 三代残留并存。清掉能显著降低「我该改哪个」的判断成本。

**A6 · 界面所见的赛程可能是过期的（P1）**

管理端只在挂载时读一次。这次已让它在冲突时自动重载，但常态下它仍然不会主动发现变更。作为赛事指挥界面，「手里这份是不是最新的」这件事应该常驻可见。

### 3.3 建议顺序

| 顺序 | 内容 | 为什么排这里 |
|---|---|---|
| 1 | A2 扩守卫测试范围 | 成本最低，防的是下一次同类遗漏 |
| 2 | A1/V2 `schedule` 写入契约统一 | 唯一已确证会造成数据丢失的一类问题 |
| 3 | A5 清死代码与历史层 | 后续任何改动都受益，且不改变行为 |
| 4 | A3 抽游戏配置层 | 兑现产品主张的结构前提，工作量最大 |
| 5 | A4 拆巨型 UI 文件 | 与 A6 一起做更划算 |
| 6 | A6 界面新鲜度 | 需要先定「赛事期指挥台」的形态 |

## 4. 需要你决定的事

1. **`schedule` 的写入契约是否按 V2 的方案统一**（所有写手递增版本 + 裁判改按比赛级前置条件校验）。这会动到已冻结的赛果域契约，需要你同意再改。
2. **第 2 节的死文件是否删除**。我按你的规矩没有动：`types/index.ts`、`referee-session.ts`、`useFormat.ts`、`/api/public/team/member` 路由，以及 `mock-data.ts`/`utils.ts` 里的死导出。
3. **守卫测试是否扩展到全部 API 路由**（A2）。我倾向直接做，成本很低。
4. **A3 游戏配置层是否排入下一批开发**。它是产品主张的结构前提，但会牵动赛程、规则、BP、识图四处。
