## 2. 关键决策的论证（为什么这么定）

### 2.1 决策 3：提交即生效（负责人拍板）

**结论**：普通比赛由裁判提交、规则校验通过后直接生效，不经过管理员逐场复核。

**论证**：

- 若每场都需管理员确认，裁判报分只替管理员「填了表」，逐场看一遍一个没省，闭环不产生增量价值——管理员无法从「所有比赛的数据录入员」变成「少数异常的处理者」。
- 负责人判断：**填错小分不会导致太大问题，真正的风险只在「胜负双方搞反」**。

**关键代码事实（已核对 `schedule-ops.ts`）**：现有系统不存在「裁判填胜负」的输入框——`winnerTeamId` 由 `reportGameResultsOp` 内的 `winsA > winsB` 自动判定（第 422-424 行）。因此「胜负搞反」不是独立操作，而是「填错比分 → 代码算错胜负」的**同一件事**。

**由此派生的防呆设计（RPT-05 必做）**：提交前回显「系统判定的胜者」给裁判，裁判对照截图确认后才写入。这一步不增加管理员时间，但堵住了「填错比分 → 算错胜负 → 污染晋级链」这个唯一真正的风险。

### 2.2 决策 3、5、6 是绑定三件套

「提交即生效」的激进效率选择，只有在「错了能安全纠正」成立时才成立：

- 决策 3（提交即生效）→ 制造「错误会直接进正式结果」的风险；
- 决策 5（禁止自动撤销）→ 保证错误**可逆**、可追溯、不原地覆盖留下半更新状态；
- 决策 6（下游恢复矩阵）→ 保证纠正上游时，下游晋级链不塌。

三者不可拆开单独生效。

### 2.3 决策 4：强制复核场次

淘汰赛前半段出错可被后续追平，半决赛/决赛出错直接改名次，复核收益最高。异常（低置信 / 冲突 / 超时申诉 / 比分规则不符）无条件进队列。

### 2.4 决策 7：队长申诉首期不做

申诉低频、可人工兜底，首期聚焦裁判报分闭环本身。但**保留队长「查看赛果」入口**，不让队长连结果都看不到。

## 4. 状态机（已冻结）

```text
draft
  └─ 裁判提交 ─→ submitted
                    ├─ 规则一致、非强制复核 ─→ accepted（直接生效）
                    ├─ 异常/关键场次 ───────→ needs-review
                    └─ 状态已过期 ─────────→ rejected

needs-review
  ├─ 管理员确认 ─→ accepted
  └─ 管理员驳回 ─→ rejected

accepted
  ├─ 新提交替代 ─→ superseded
  └─ 安全撤销 ───→ superseded / reverted decision
```

**硬规则**：`accepted` 之后禁止原地修改。更正必须形成新提交和新决策。

**status 与正式赛果的关系**：只有 `accepted` 能触发 `reportGameResultsOp` 的正式赛果更新与晋级推进；`draft` / `submitted` / `needs-review` / `rejected` 一律不碰正式赛果。

## 5. 权限矩阵（已冻结）

| 角色 | 可执行 | 禁止 |
|---|---|---|
| 裁判 | 查看被分配比赛、上传凭证、核对预填、确认胜者、提交赛果、补充说明 | 改未分配比赛、处理申诉、改规则 |
| 管理员 | 分配裁判、审核异常、受控更正/撤销赛果、处理申诉、恢复错误晋级 | 无记录覆盖历史赛果 |
| 队长 | 查看本队赛果、时限内发起申诉（首期群聊兜底） | 提交正式赛果、确认对手胜负 |
| AI | 读取单次任务截图、输出结构化候选结果和不确定项 | 提交赛果、调用晋级、判断作弊/处罚 |
| 规则系统 | 校验结构化结果、计算胜者、控制晋级 | 理解截图、替代人工确认 |

**服务端权限铁律**：每次写操作由「身份 + 分配关系」在服务端推导权限，**不相信客户端传入的 `refereeId` 或角色字段**。

## 6. 下游恢复决策表（决策 6，已冻结）

| 下游状态 | 上游赛果更正处理 |
|---|---|
| 后续对阵仅有占位队伍，未排期 | 允许重新填充队伍 |
| 已排期但未 BP | 阻止自动生效；管理员确认后重新校验排期 |
| BP 已开始/完成 | 禁止自动覆盖，进入人工恢复 |
| 已报分或继续晋级 | 禁止自动覆盖，生成受影响比赛清单 |
| 赛事已结束/归档 | 只允许受控更正，不自动重放整届 |

## 7. API 草案

具体 URL 由本文件冻结，实现 AI 不得临时决定。

| 能力 | 说明 |
|---|---|
| 裁判登录 / 退出 | 发凭证、建受控会话 |
| 读取我的比赛 | 仅返回被分配比赛 |
| 创建草稿 / 上传凭证 | 凭证先传、草稿挂起 |
| 提交赛果 | 携带 `basedOnScheduleVersion`；幂等；版本冲突返 409 |
| 读取异常队列 | 管理员专属 |
| 接受 / 驳回 / 要求重提 | 管理员 |
| 受控更正 / 撤销 | 管理员，形成决策记录 |
| 管理裁判与分配 | 管理员 |

**关键要求**：

1. 接受赛果、更新正式赛果、产生决策必须在**同一受控更新**内完成。
2. 重复请求返回同一结果，不双重晋级。
3. 版本冲突返 409，不静默覆盖。
4. 图片先传后提交，需要草稿与过期清理机制。
5. 高风险操作写审计；审计故障策略明确区分「业务提交是否已成功」。
6. 返回数据最小化，公开端只展示已接受的正式赛果。

## 8. 功能开关方案（决策 10）

- 服务端功能开关，默认**关闭**。
- 关闭时：裁判写操作全部不可用；**现有管理员手工报分保持可用**（回退兜底）。
- 开启条件：RPT-07 综合验收在隔离环境通过 + 产品负责人确认 + 至少一名真实裁判试用通过。
- 发布负责人单独制定上线与回滚步骤。
