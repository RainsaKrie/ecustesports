# 校园赛事平台 · 架构重构方案 v1.0

> 2026-10-17。**依据**：对本仓库当前代码的实测盘点（不是设想）。
> 目标参照：第三方团队做的无畏契约巅峰赛系统 —— 完成度与观感到"能被官方采纳"。
> 配套文档：`08-MVP开发/系统架构总览_v1.0.md`（现状）、`08-MVP开发/数据流转与写入点登记表_v1.0.md`。

## 一、现状诊断

### 1.1 实测规模

| 区域 | 规模 | 说明 |
|---|---|---|
| `src/lib/scheduling/` | **34 文件 / 8129 行** | 报名、裁判、赛果、证据、BP、赛制、抽签、赛程 **全在里面** |
| `src/lib/referee/` | 9 文件 / 2185 行 | 与 `scheduling/referee-*` **职责重叠** |
| `src/lib/games/` | 3 文件 / 256 行 | 唯一做对的一件事：游戏数据的单一真源 |
| `src/lib/` 根 | 约 15 个散落文件 | site-config / data-store / 缓存 / 限流 混在一起 |
| 页面与组件 | 14 个 admin 页面 / 35 个 API / 16 admin 组件 / 9 玩家组件 | 其中 5 个组件 600–950 行 |
| 测试 | 36 套 | **这是最大的资产**，但按"功能"组织、不按"领域" |

**五个最大的文件**（都在 UI 层）：
`FormatDrawWorkspace` 947 · `schedule/page` 892 · `RefereeWorkbench` 881 ·
`RegistrationOperationsWorkspace` 748 · `EventSettingsWorkspace` 609

### 1.2 问题一：领域边界塌了

`lib/scheduling` 里同时住着**六件不相干的事**：

```
scheduling/
├─ registration-*.ts          ← 报名与名单
├─ referee-*.ts / reporting-* ← 裁判与报分
├─ result-*.ts / evidence-*   ← 赛果与证据
├─ bp-*.ts                    ← BP 选图
├─ format-* / stage / bracket-* / staged-format / rule-engine ← 赛制与抽签
├─ schedule-* / bulk-schedule / team-swap / schedule-mode     ← 赛程与排期
└─ useSchedule / useRegistration / useParticipant / usePublic* ← ⚠️ React hooks
```

**实际影响**：
- 改「报名」要在一个 8129 行的目录里找入口，且目录名 `scheduling` 完全不指向报名；
- 目录名与内容不一致，**新人/新会话只能靠 grep 猜**（这是本方案要解决的第一件事）；
- 领域层被 React 绑定（`useXxx` 在 `lib/` 下）→ 纯 Node 脚本无法直接复用，
  本仓库已经因此踩过「server-only 模块在纯 Node 下不可 import」的坑。

### 1.3 问题二：同一件事有两个家

| 事 | 位置 A | 位置 B |
|---|---|---|
| 裁判 | `lib/referee/*` | `lib/scheduling/referee-domain.ts`、`referee-ops.ts` |
| 报分 | `lib/referee/reporting-data.ts` | `lib/scheduling/reporting-service.ts`、`result-ops.ts` |
| 术语 | `result-*` / `reporting-*` / `referee-*` 三个词指同一件事 | —— |

**实际影响**：改一处漏一处。维护时必须在两个目录之间来回对照，而这正是
《数据结构真源与变更登记》里记的那类事故的来源。

### 1.4 问题三：UI 层过重，决策散在页面里

5 个 600–950 行的组件在**替领域层做决策**：赛制计算写在 `FormatDrawWorkspace`、
"可调整签位"的筛选写在 `schedule/page`、编排参数写在设置页。

**实际影响**：
- **页面无法测试**（仓库里 36 套测试没有一套覆盖页面）→ 每次改界面都靠手点；
- 同一套判断在页面与领域层各写一遍 → 两处漂移（已在「待排期语义」上发生过一次）；
- 观感无法统一：每个页面各写一遍布局，间距/字号/空态各不相同 → **这是"美观度不够"的结构性原因**。

### 1.5 问题四：没有"层"的概念

现在只有目录，没有层。层级关系靠约定俗成，于是：
- 页面直接读数据存储（跨层）；
- 领域文件互相 import 实现细节（横向耦合）；
- 根目录的 `site-config` / `data-store` / 缓存 与领域文件平级（内核与业务混排）。

## 二、目标架构

### 2.1 五层，依赖只能向内

```
L4  界面层      页面（page）· 页面骨架 · 功能组件
L3  接口层      路由处理（route）· 服务端动作 · React hooks
L2  应用层      用例编排（一次操作跨几个领域）
L1  领域层      七个领域，每个领域固定四件套
L0  内核层      数据访问 · 鉴权 · 审计 · 缓存 · 限流 · 配置
```

**硬规则（可写成守卫）**：

1. **依赖只能向下**：L4→L3→L2→L1→L0。禁止反向，禁止跨层（页面直接碰 L0）。
2. **L1 之间不互相 import 实现**：跨领域只允许两条路 —— 走 L2 编排，或依赖对方**只读的 policy/DTO**。
3. **L1 里不许出现 React**：hooks 一律放 L3。领域层必须能在纯 Node 下被测试与脚本复用。
4. **L2 里不许出现 SQL/存储调用细节**：只调 L1 的 service。
5. **单文件上限 400 行；单页面上限 300 行**，超了必须拆（现在 5 个组件都超）。
6. **一个名字只指一件事**：赛果统一叫 `result`，停用 `reporting`/`referee-*` 这类混称。

### 2.2 L1 的七个领域（每个领域固定四个文件）

| 领域 | 职责 | 现状落点 | 迁移动作 |
|---|---|---|---|
| `identity` | 参赛者 / 管理员 / 裁判的身份与凭证 | `participant-auth`、`referee-auth`、`lib/referee` 部分 | 合并 |
| `event` | 赛事配置、阶段、赛制模板、规则库 | `site-config*`、`format-templates`、`stage`、`rule-library` | 迁入 |
| `registration` | 报名、名单、冻结、队伍状态 | `registration-*`、`public-roster`、`participant-recovery` | 迁入 |
| `format` | 抽签、对阵、晋级关系 | `bracket-*`、`staged-format`、`team-swap`、`format-data/support` | 迁入 |
| `schedule` | 排期、改期、赛程版本 | `schedule-*`、`bulk-schedule`、`schedule-policy`、`schedule-mode` | 迁入 |
| `result` | 报分、赛果校验、证据、BP | `result-*`、`reporting-*`、`evidence-*`、`bp-*`、`lib/referee/*` | **三处合一** |
| `content` | 站点内容、公告、发布检查 | `site-content-*`、`publication-check`、`news` | 迁入 |

**每个领域的固定结构**（这就是"嵌套规则"）：

```
domains/<name>/
  types.ts      数据形状（与存储字段一一对应）
  policy.ts     纯函数：判定与规则，无 IO、无 React、可穷举测试
  ops.ts        状态流转：输入旧状态 → 输出新状态（纯函数，可测）
  service.ts    读写编排：唯一接触 L0 的地方
```

> 这不是新发明 —— 仓库里**已经有一半是对的**：`rule-engine`、`bulk-schedule`、`team-swap`
> 都是纯函数且有 36 套测试护着。方案要做的，是**把已经做对的部分变成制度**，
> 而不是推倒重来。

### 2.3 L2 应用层（用例，不是领域）

```
application/
  draw-and-publish      抽签并发布（format + schedule + identity）
  advance-stage         晋级推进（result + format）
  bulk-schedule         批量排期（schedule + event）
  reschedule            改期闭环（schedule + identity + result）
  report-result         报分与证据（result + identity）
```

L2 是**唯一允许跨领域**的地方，而且只做编排：读 A 的 policy、调 B 的 service、写 C 的 ops。

### 2.4 L3 / L4 的拆分规则

- **L3**：`app/api/**/route.ts` 只做「解析请求 → 调 L2 → 返回」，**不许写业务判断**；
  hooks（`useSchedule` 等）移到 `src/hooks/`，只负责"取数 + 乐观更新 + 冲突重试"。
- **L4**：页面拆成 **页面骨架（Shell）** + **功能组件（Feature）**。
  骨架只管布局（页头/上下文条/主体），功能组件只管一块业务。
  **这是提升观感的关键**：现在 5 个巨型组件各自写布局，所以每个页面长得都不一样。

### 2.5 设计系统（观感的制度基础）

现有 `--adm-*` 令牌与 `.adm-btn/.adm-chip/.adm-note` 已经不错，缺的是**页面级组件**：

```
ui/
  shell/     PageShell（页头 + 上下文条 + 主体）、Section、EmptyState、ContextBar
  data/      DataTable（排序/空态/加载/错误四态齐全）、StatRow、Timeline
  feedback/  Toast、Confirm、ProgressSteps
```

规则：**页面不许直接写间距与字号**，一律用骨架组件；这样"换个页面观感一致"才有保证。

## 三、可视化表达

### 3.1 目标架构（分层 + 依赖方向）

见对话中的架构图。要点：**箭头只向下**；L1 内部七个领域横向不连；L2 是唯一跨领域的层。

### 3.2 现状 → 目标的模块归位

| 现在的位置 | 新位置 | 说明 |
|---|---|---|
| `lib/scheduling/registration-*` | `domains/registration/` | 迁入 |
| `lib/scheduling/referee-*` + `lib/referee/*` | `domains/identity/` + `domains/result/` | **合一，消除双家** |
| `lib/scheduling/result-* / reporting-* / evidence-* / bp-*` | `domains/result/` | 合一 |
| `lib/scheduling/format-* / stage / bracket-* / staged-format` | `domains/format/` + `domains/event/` | 拆开 |
| `lib/scheduling/schedule-* / bulk-schedule / team-swap` | `domains/schedule/` | 迁入 |
| `lib/scheduling/useXxx.ts` | `src/hooks/` | **移出领域层** |
| `lib/site-config* / data-store / 缓存 / 限流` | `kernel/` | 收拢成内核 |
| 5 个 600–950 行组件 | `features/<模块>/` + `ui/shell/` | 拆骨架 + 功能 |

### 3.3 核心 / 边缘

- **核心（不能坏）**：`result`（赛果）、`schedule`（赛程）、`format`（抽签与晋级）、`kernel`（隔离与审计）。
- **支撑**：`registration`、`identity`、`event`。
- **边缘（可延后、可薄）**：`content`（公告/内容）、`ui/data`（表格的高级能力）、AI 相关全部。

## 四、事项归位

| 事项 | 归属 | 处置 |
|---|---|---|
| 四阶段赛制 / 组内单败 / 淘汰赛抽签 | `format` + `event` | **核心保留** |
| 批量排期 / 排期模式二分 | `schedule` + `event` | **核心保留**（已带测试） |
| 调整对阵（理由 + 留痕） | `format` + `schedule` | **核心保留** |
| 赛果丢失护栏 / 写入契约 | `kernel` + `result` | **核心保留** |
| 裁判报分链路（63 项端到端） | `identity` + `result` | **核心保留**，但要"合并双家" |
| 报名与冻结 / 公布期筛选 | `registration` | 保留 |
| 赛程页 / 设置页 / 抽签页 | L4 拆分 | **合并**为骨架 + 功能组件 |
| 站点内容与公告 | `content` | 保留但**降级**（非核心） |
| AI 赛果识别 | `result`（作为可选能力） | **延后**（卡清晰样本） |
| AI 影子运行 / 开放 API / 直播媒体 | —— | **延后**（校园赛用不上） |
| 生产监控 / 定时自动化 | —— | **已否，不再提** |

## 五、演进路线

| 阶段 | 内容 | 产出物 | 对完成度/观感的作用 |
|---|---|---|---|
| **P1 领域归位** | 目录迁移 + `referee` 双家合一 + hooks 迁出；**不改任何行为** | 新目录树 + 门禁全绿（36 套照旧） | 观感无变化，但**迭代速度**与"找得到东西"大幅改善 |
| **P2 分层落地** | 引入 L2 用例层；页面里的判断搬回领域层 | `application/` + 页面瘦身 | 修复"同一条规则两处写"的漂移风险 |
| **P3 设计系统** | `ui/shell` + `ui/data` + 5 个巨型组件按骨架重写 | 页面骨架规范 + 组件库 | **观感与一致性直接跃升**（这是"官方级"门槛） |
| **P4 公开面** | 赛事主页 / 赛程公开页 / 战队档案改版 | 对外可展示的页面 | **被"采纳"看的就是这一层** |

**顺序理由**：P1/P2 是"把地基摆正"，看不见但决定后面能不能加速；P3 是观感的分水岭；
P4 才是对外亮相。**先做 P4 会返工** —— 因为没有组件规范，改一个页面要重写一遍。

## 六、差距分析（对标官方级平台）

| 维度 | 官方级平台 | 我们 | 优先级 |
|---|---|---|---|
| 公开页信息架构 | 赛事主页 / 赛程 / 战队 / 赛果四条主线，一屏看懂 | 有页面但各自为政，缺"赛事主页"这一层 | **高** |
| 设计系统 | 组件级一致（表格/空态/动效/字号） | 只有令牌与少量原子类，页面各自写布局 | **高** |
| 战队与选手档案 | 有档案页、历史战绩、晋级路径 | **没有** | 中高 |
| 数据可视化（对阵图/晋级） | 交互式对阵图、点击看详情 | 有对阵图，交互与信息层次弱 | 中 |
| 移动端 | 全站响应式 | 裁判工作台面向手机，其余偏桌面 | 中 |
| 实时与媒体（直播/回放） | 官方的强项 | 校园赛用不上 | 低（不做） |
| 开放 API / 生态 | 有 | 内部用 | 低（不做） |

**优先补齐三件**（与 P3/P4 对应）：
1. **页面骨架与组件规范** —— 观感差距的根因；
2. **赛事主页（公开）** —— 评委与观众看到的第一屏；
3. **战队档案** —— "像官方"的体感来自这里。

## 七、本方案的边界（不做什么）

- **不重写业务逻辑**：36 套测试与写入护栏是资产，P1 只搬家不改行为；
- **不引入新框架**：Next.js + Tailwind + 现有令牌足够，问题是组织方式不是技术选型；
- **不做多游戏抽象**：`games` 层已留好口子，等真有第二个游戏再说；
- **不做实时/直播/开放 API**：校园赛规模不需要。
